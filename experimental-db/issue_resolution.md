### Cross-Risk Conflict & Newly Introduced Risk Summary
- **Resolution vs Latency (`RISK-03/04` + `RISK-18` vs `RISK-36`):** Replacing custom unverified WAL rings and fast 500ms routing swaps with real PostgreSQL physical sync standbys (`RISK-03`) and mandatory `12.0s` async promotion safety windows (`RISK-18`) eliminates split-brain and undocumented data loss, at the cost of +1–3ms Pro commit latency and a 12s minimum failover floor on abrupt Async Cell loss.

  3. Fly `/init` orphan zombie/shutdown race and potential omission of `prjquota`/cgroup controllers in `fly-kernel` (mitigated via `PR_SET_CHILD_SUBREAPER`, `300s` `SIGTERM` drain, and `envprobe` 1s `/proc` zero-module fallbacks in `RISK-05`, `RISK-06`, `RISK-17`).

## Deliverable 2: Detailed Technical Research (`RISK-01` through `RISK-14`)

### RISK-01: PostgreSQL Template Cloning & Cluster Identity
1. **Risk ID & Title:** `RISK-01` — PostgreSQL Template Cloning & Cluster Identity
2. **Severity:** `P0`
3. **Root Cause:** An initialized PostgreSQL data directory (`PGDATA`) is not stateless template data: `initdb` writes a unique 64-bit random `Database system identifier` (`pg_control.system_identifier`) into `$PGDATA/global/pg_control` and stamps every WAL segment page header (`XLogLongPageHeaderData.xlp_sysid`) with that same ID. Cloning a pre-initialized directory (via `cp -a` or `XFS FICLONE`) clones an identical `system_identifier` across tenants.
4. **Failure Scenario:** Tenant A and Tenant B are both cloned from one `PGDATA` template on Cell #1 (or across Cell #1 and Cell #2). A backup pipeline or operator accidentally crosses a WAL file or `basebackup` prefix, or an orchestration bug attaches Tenant B's standby/archive consumer to Tenant A's WAL stream. Worse, if `pg-cell-agent` crashes mid-`initdb` while populating an unpooled directory or suffers a concurrent claim race, two API requests bind to the same directory or boot an incomplete `PGDATA` missing `pg_control`, corrupting both clusters immediately upon startup (`PANIC: could not locate a valid checkpoint record`).
5. **Technical Explanation:** In PostgreSQL source (`src/bin/initdb/initdb.c` and `src/include/catalog/pg_control.h`), `system_identifier` is derived from epoch seconds, microseconds, and PID at `initdb` time and serves as the cluster's global identity key across `IDENTIFY_SYSTEM`, `pg_receivewal`, `pg_basebackup`, `pg_rewind`, and `restore_command` (`%f`). PostgreSQL's `XLogReaderValidatePageHeader` explicitly compares `xlp_sysid` against `ControlFile->system_identifier`, halting WAL replay if they differ, yet *accepting* foreign WAL segments from another cluster if both share the exact same cloned `system_identifier`! Even `pg_resetwal` does **not** automatically change `system_identifier` safely for live production clusters without discarding replication alignment, rewriting WAL segments, and risking OID/frozenxid inconsistencies if templates had post-`initdb` SQL run cleanly vs uncleanly. While Neon uses immutable tenantless storage branches separated by Safekeeper timeline IDs, and Supabase/RDS either run `initdb` per container/VM or `CREATE DATABASE` inside a dedicated single-tenant VM, shared-host multi-cluster cells must guarantee strictly disjoint `system_identifier` values per cluster.
6. **Industry-Standard Solutions:**
   - Fresh `initdb` execution per tenant cluster (standard in RDS single-tenant instances, CloudNativePG, Zalando Spilo/Patroni).
   - Pre-warmed, un-assigned **Two-Phase `initdb` Standby Pool** verified with `pg_controldata` + Control Plane transactional uniqueness constraint (`UNIQUE (system_identifier)`).
   - Storage-engine page-level CoW (`Neon` Pageserver) where tenant timelines are globally unique UUIDs inside an object-indexed storage engine rather than POSIX `PGDATA` copies.
7. **Solution Comparison:**
   - *Option A — XFS `FICLONE` of a single template `PGDATA`:* Fastest clone (`<5ms`, minimal disk), **rejected** because it duplicates `system_identifier`, requires XFS (absent on stock Fly.io `ext4`), and ties ongoing CoW fragmentation/accounting to a frozen parent template (`RISK-13`, `RISK-14`).
   - *Option B — Synchronous on-demand `initdb` per `POST /databases`:* Zero pool management, guaranteed unique `system_identifier`, **sub-optimal UX** because synchronous `initdb` consumes 400–850ms CPU + `fsync` I/O on the request path.
   - *Option C — Recommended: Pre-warmed Two-Phase `initdb` Pool + Transactional Control DB Registration:* Achieves `<5ms` disk claim latency *and* 100% independent clusters generated via real PG17 `initdb`, with automatic on-demand `initdb` fallback if the ready pool empties.
8. **Recommended Design (`ADR-001`):** Run a background `nice -n 19` pool worker on every Cell creating fresh PG17 clusters into `/vol/pool/staging/{uuid}` (`initdb --auth=scram-sha-256 --encoding=UTF8 --data-checksums`). Verify via `pg_controldata` that `Database cluster state` equals `shut down`, parse the 64-bit `Database system identifier`, write `pool_meta.json`, `fsync()` the directory, and atomically `os.Rename()` to `/vol/pool/ready/{uuid}`. On provision, `pg-cell-agent` pops one entry under mutex -> renames to `/vol/tenants/claiming/{tenant_id}` -> registers `(tenant_id, system_identifier, cell_id)` in the Control Plane HA PostgreSQL table enforcing `UNIQUE (system_identifier)` -> runs a final `pg_controldata` verification -> renames to `/vol/tenants/{tenant_id}/pgdata`. Boot recovery deletes all `/vol/pool/staging/*` and purges unverified `/vol/pool/ready/*` directories.
9. **Architecture Changes:** Add `internal/cell/pool` two-phase state machine; add `clusters (tenant_id PK, system_identifier UNIQUE, cell_id, epoch)` schema in Control Plane HA DB; remove all XFS `FICLONE` / `pg_resetwal` cloning code paths.
10. **Dependencies:** Fly `ext4` volume behavior (`RISK-13`), Control Plane HA DB availability (`RISK-32`), idempotent API handling (`RISK-33`).
11. **Trade-Offs:** Each pooled ready cluster consumes ~40–45 MB uncompressed `ext4` space (20 ready clusters = ~850 MB per Cell) vs `<5ms` fast claim; background `initdb` uses brief burst CPU/IOPS throttled via `nice`/ionice.
12. **Security Implications:** Eliminates accidental WAL cross-replay between tenants sharing an identical cloned `system_identifier`; enables `pg_basebackup` data checksums (`--data-checksums`) cleanly at birth; prevents exposure of incomplete staging catalogs.
13. **Failure Recovery Strategy:** If Control Plane insert hits duplicate `system_identifier` (practically impossible across CSPRNG/time entropy, caught defensively) or fails mid-claim, roll back `/vol/tenants/claiming/{tenant_id}` to quarantine/delete via `control-reconcile-queue`; on agent crash mid-`initdb`, startup wipes `/vol/pool/staging/*` cleanly before serving claims.
14. **Validation Method:** `EXP-A1` (Identity & WAL uniqueness audit), `EXP-A2` (1,000 concurrent claims + `UNIQUE` collision check), `EXP-A3` (`SIGKILL` mid-`initdb` and mid-claim crash test).
15. **Acceptance Criteria:** `100%` unique 64-bit `system_identifier` values across 1,000 concurrently provisioned clusters; `0` half-initialized or unverified clusters assigned across 50 injected crash restarts; steady-state claim `<15ms` p99.
16. **Remaining Uncertainty:** Exact steady-state disk space consumed by a PG17 `--data-checksums` cluster on Fly's specific `ext4` block/inode configuration and real concurrent `initdb` refill throughput under OLTP neighbor load (`UQR-02`).

### RISK-02: FIEMAP Physical Delta Backup Validity
1. **Risk ID & Title:** `RISK-02` — FIEMAP Physical Delta Backup Validity
2. **Severity:** `P0`
3. **Root Cause:** Scanning XFS extents with `FS_IOC_FIEMAP` operates at the Linux VFS block-extent layer *below* PostgreSQL's shared buffers, dirty page writeback, checkpoint synchronization, and relation-fork lifecycle, violating PostgreSQL physical backup consistency rules documented in [PostgreSQL Continuous Archiving](https://www.postgresql.org/docs/current/continuous-archiving.html).
4. **Failure Scenario:** A tenant runs bulk inserts/truncations while `pg-cell-agent` calls `FS_IOC_FIEMAP`. Newly written relation data sits in Linux page cache marked `FIEMAP_EXTENT_DELALLOC` (`0x00000004`) + `FIEMAP_EXTENT_UNKNOWN` with no physical extent offset yet; or `postgres` writes 4 KB of an 8 KB data page while `pg-cell-agent` reads half-old/half-new bytes (torn page) *after* the last checkpoint; or a file is unlinked (`DROP TABLE`) mid-scan. Restoring the delta onto the base produces silently corrupt heap tuples or `invalid page in block ...` panics that `full_page_writes` cannot repair because no valid `backup_label` LSN boundary exists.
5. **Technical Explanation:** According to Linux Kernel documentation (`Documentation/filesystems/fiemap.rst`) and PostgreSQL physical backup guarantees: (1) Without `FIEMAP_FLAG_SYNC`, dirty delayed-allocation extents carry `FIEMAP_EXTENT_DELALLOC` and unknown physical addresses; even *with* `SYNC`, concurrent Postgres writes outside `pg_backup_start()`/`pg_backup_stop()` cause fractured 8 KB pages because OS page writes are 4 KB. (2) CoW shares 4 KB/extent blocks, not full relation files—partially rewritten files contain interleaved shared and unshared extents, requiring exact sparse hole (`ZERO_RANGE`/`TRUNCATE`) and size metadata tracking across every relation fork (`_fsm`, `_vm`). (3) Deleting or truncating files isn't recorded by pure changed-extent scans without directory manifest diffs. (4) Fly.io Volumes provide `ext4`, not XFS reflinked templates! Meanwhile, PostgreSQL 17 introduced native incremental backups (`summarize_wal = on`, WAL summarizer background process writing `.wal_summary` files in `pg_wal/summaries/`, `pg_basebackup --incremental=<prev_manifest>`, `pg_combinebackup`, and `pg_verifybackup`).
6. **Industry-Standard Solutions:**
   - **PostgreSQL 17 Native Physical + Incremental Backups:** `pg_basebackup` (base + `--incremental`) + `pg_combinebackup` + `pg_verifybackup` + continuous WAL archiving (`pg_receivewal` / `archive_command`).
   - **Block-Level CoW Volume Snapshots (when cluster is quiesced or `pg_backup_start` brackets atomic hardware snapshot):** Used by AWS EBS/RDS and GCP Persistent Disks, where a *single atomic point-in-time block snapshot* captures all files in one freeze instant—unlike `FIEMAP` file-by-file scanning!
   - **Logical `pg_dump` / Logical Replication Snapshots:** Version-agnostic logical export, unsuitable for large-DB fast binary recovery.
7. **Solution Comparison:**
   - *Option A — Custom `FIEMAP` Extent Scraper:* Low delta volume, **rejected (unsafe)** due to torn 8 KB pages, `DELALLOC` races, directory/unlink omission, missing `backup_label`, and `ext4` incompatibility on Fly.io.
   - *Option B — Full `pg_basebackup` Only:* 100% PostgreSQL-supported, simple chainless recovery, higher R2 storage and egress/ingress cost on write-light DBs.
   - *Option C — Recommended: PG17 Native Base + `--incremental` + `pg_verifybackup` + Full Fallback:* Uses PostgreSQL 17's own verified block-tracking WAL summarizer, falls back automatically to Option B in Stages 0–1 (until proven) or whenever `pg_available_wal_summaries()` shows a gap, and verifies every archive via SHA-256 `pg_verifybackup` before R2 upload.
8. **Recommended Design (`ADR-002`):** Enable `summarize_wal = on` and `wal_summary_keep_time = '48h'` (requires `wal_level >= replica`). Capture backups via `pg_basebackup` (base and `--incremental=<parent_backup_manifest>`); verify locally/in-staging via `pg_verifybackup`; wrap streams in per-tenant AES-256-GCM DEK encryption; publish atomically to R2 (`tenants/{id}/epoch_{e}/...`); update `manifest.json` only after verifying parent-chain + continuous WAL + DEK unwrap. On restore, allocate `>=2.2x` target size free on `/vol/staging`, extract base + incremental chain, run `pg_combinebackup -o /restore/out`, verify with `pg_verifybackup /restore/out`, and replay WAL via `restore_command`.
9. **Architecture Changes:** Remove all `FIEMAP` / XFS extent code; add `internal/cell/backup` orchestrating `pg_basebackup`, `pg_available_wal_summaries()` continuity checks, `pg_verifybackup`, `pg_combinebackup`, and zstd + envelope encryption.
10. **Dependencies:** PostgreSQL 17 binaries on Cells (`RISK-13`), R2 atomic manifest & lifecycle verification (`RISK-15`), WAL continuity (`RISK-16`), Cell staging disk headroom (`RISK-17`).
11. **Trade-Offs:** `pg_combinebackup` requires unpacking tarballs (doesn't combine compressed `.tar.zst` streams directly) and temporarily uses ~`2.2x` restored cluster size during recovery; `summarize_wal` adds minor background sequential read overhead on the primary.
12. **Security Implications:** All backup manifests use SHA-256 checksums checked by `pg_verifybackup` *before* envelope DEK encryption, detecting bit-rot or tampering before restore boots untrusted relation pages.
13. **Failure Recovery Strategy:** If `--incremental` fails or `pg_available_wal_summaries()` shows missing summary ranges (e.g., after crash/expiration), automatically trigger a fresh full `pg_basebackup`. If the latest incremental backup corrupts, restore falls back to `(latest valid base or earlier complete chain) + archived physical WAL`.
14. **Validation Method:** `EXP-D4` (Backup integrity & corruption rejection) and `EXP-D5` (End-to-end `pg_basebackup --incremental` + `pg_combinebackup` + `pg_amcheck` restore drill on PG17 binaries).
15. **Acceptance Criteria:** `0` verification errors (`pg_verifybackup` and `pg_amcheck --heapallindexed`) across 50 chained backup-crash-restore iterations; automatic full-backup fallback confirmed when summary files are manually removed.
16. **Remaining Uncertainty:** Real CPU, wall-clock duration, and temporary staging `/vol` IOPS overhead of `pg_basebackup --format=plain` -> `zstd` -> R2 upload vs tar extraction + `pg_combinebackup` across 1 GB–10 GB tenant datasets on Fly `ext4` NVMe (`UQR-03`).

### RISK-03: WAL Replication & `RPO=0` Durability Semantics
1. **Risk ID & Title:** `RISK-03` — WAL Replication & `RPO=0` Durability Semantics
2. **Severity:** `P0`
3. **Root Cause:** Conflating `pglogrepl` (which primarily targets logical replication slots in Go applications unless full physical wire framing is built), async WAL uploads to R2/queues, and PostgreSQL's synchronous commit latch (`SyncRepWaitForLSN`), while claiming `RPO=0` without proving end-to-end synchronous flush before commit acknowledgment.
4. **Failure Scenario:** A tenant on a "Zero Data Loss" tier receives `COMMIT` OK from `pg-gateway`, and 20ms later its Compute Cell VM loses host power or NVMe access. Because WAL was buffered asynchronously in an upload queue (`pg_receivewal` batch -> R2 every 5s), the newly promoted Cell lacks the last 4 seconds of WAL. The client's committed payment ledger row vanishes permanently.
5. **Technical Explanation:** Under [PostgreSQL Streaming Replication Protocol](https://www.postgresql.org/docs/current/protocol-replication.html), physical standby synchronization executes exact protocol steps: startup with `replication=true` -> `IDENTIFY_SYSTEM` (verifying `systemid`, current `timeline`, `xlogpos`) -> optional `TIMELINE_HISTORY tli` -> `START_REPLICATION [PHYSICAL] XXX/XXX [TIMELINE tli]` -> bidirectional `CopyBothResponse`. The primary `walsender` transmits raw 16 MB segment streams (`XLogData`), and the standby periodically returns `StandbyStatusUpdate` carrying `write_lsn`, `flush_lsn`, and `apply_lsn`. On commit, when `synchronous_commit = on` and `synchronous_standby_names` matches an active replica in `sync` state, PostgreSQL blocks the backend in `SyncRepWaitForLSN` *after* local WAL `fsync` and *before* returning `CommandComplete` (`'C'`) until a matching `StandbyStatusUpdate` confirms `flush_lsn >= commit_lsn` (`apply_lsn >= commit_lsn` for `remote_apply`). Async uploads (`archive_command`, async `pg_receivewal`, or S3/R2 PUT) never participate in `SyncRepWaitForLSN` and therefore always have `RPO > 0`.
6. **Industry-Standard Solutions:**
   - **Native PostgreSQL Physical Standby Replication** with `synchronous_standby_names` (`FIRST 1` or `ANY 1` quorum across separate zones/hosts) + async WAL archiving to object storage (`RDS Multi-AZ`, `CloudNativePG`, `Patroni`).
   - **Purpose-Built Consensus WAL Storage** (`Neon Safekeepers` running Paxos over PostgreSQL's physical `walreceiver` wire protocol, or `Aurora` 4-of-6 quorum storage nodes).
   - **Single-Node Async WAL Archiving** (`pgBackRest` / `WAL-G` -> S3/R2) explicitly sold with bounded async `RPO` rather than `RPO=0`.
7. **Solution Comparison:**
   - *Option A — Async `pg_receivewal` / Queue -> R2 on all tiers:* Zero standby VM cost, 0ms commit RTT tax, **cannot achieve `RPO=0`** (`RPO <= archive interval`).
   - *Option B — Custom Go consensus WAL Sink in Stage 1:* Amortizes 1 quorum VM set across many tenants, **high correctness & schedule risk** (must re-implement full PG physical `walsender`/`walreceiver` protocol, segment splitting, `.history` tracking, crash-safe slot state, and warm restore latency).
   - *Option C — Recommended: Two Explicit Tiers Using Native PG17 Primitives:* **Standard Tier (Async)** uses local `pg_receivewal` + R2 upload (`RPO <= 5s` honest SLA, 0ms commit penalty); **Pro Tier (`RPO=0` Scoped)** uses a **real PostgreSQL 17 Physical Standby** in a separate Fly zone (`--volume-requires-unique-zone`) + `synchronous_standby_names` + `pg_receivewal` to R2.
8. **Recommended Design (`ADR-003`):** Use Standard Async (`RPO <= 5s` via `pg_receivewal` + R2 5s flush + cooperative drain flush on sleep) by default. For Pro Tier, run a real PG17 Physical Standby on a distinct Fly zone Cell with a durable physical replication slot (`max_slot_wal_keep_size` bounded), `synchronous_standby_names = 'FIRST 1 (pg_standby_z2)'`, and `synchronous_commit = on`. Define **`RPO=0` Scoped Guarantee** explicitly as: zero loss of client-acknowledged `COMMIT`s during single primary Cell/host/NVMe failure *provided* the standby was `sync` in `pg_stat_replication` and acknowledged `flush_lsn >= commit_lsn`. Explicitly exclude multi-zone destruction, simultaneous primary+standby loss, software bugs, or forced emergency promotion during degraded async mode.
9. **Architecture Changes:** Add `fly.standby.toml` placed via `--volume-requires-unique-zone`; extend `internal/control/failover` to inspect `pg_stat_replication` state before authorizing `RPO=0` status or fenced promotion; remove `pglogrepl` logical-only assumptions and `RPO=0` marketing claims on Standard tier.
10. **Dependencies:** Cross-zone Fly placement (`RISK-29`), `6PN` network latency (`RISK-30`), write-boundary fencing (`RISK-18`), R2 WAL segment archival (`RISK-15`, `RISK-16`).
11. **Trade-Offs:** Pro Sync adds ~1–3ms cross-zone intra-region `6PN` RTT + standby `fsync` per commit, plus dedicated standby process RAM (~45–60 MB/tenant) and second-zone Fly VM cost, and stalls Pro writes during total standby disconnection unless operator/policy degrades `synchronous_standby_names` (`CAP`: CP choice for `RPO=0`).
12. **Security Implications:** Replication role (`rep_user`) restricted to `replication` privilege only; `pg_hba.conf` enforces `hostssl replication` + SCRAM/mTLS over encrypted `6PN` WireGuard mesh.
13. **Failure Recovery Strategy:** On abrupt primary loss, Control Plane confirms standby `sync` status and latest `flush_lsn` >= fenced primary lease state, promotes standby via `pg_promote()` (creating Timeline `tli+1` + `.history` file archived immediately to R2), updates route `epoch++`, and spins up a replacement standby cleanly via `pg_basebackup` from the newly promoted primary.
14. **Validation Method:** `EXP-D1` (Primary `SIGKILL` immediately post-`COMMIT`), `EXP-D2` (Standby partition/disconnect commit blocking vs recovery), `EXP-D6` (Split-brain & stale primary quarantine).
15. **Acceptance Criteria:** `0` lost committed ledger rows across 50 injected primary `SIGKILL`s immediately post-`COMMIT` ACK on Pro Sync tier; confirmed timeline `.history` archival and unbroken R2 PITR across failover.
16. **Remaining Uncertainty:** Real p50/p95/p99 `COMMIT` latency across Fly.io same-region availability zones over `6PN` + standby NVMe `fsync` latency under multi-tenant load (`UQR-04`).

### RISK-04: NATS JetStream vs PostgreSQL Sync Standby
1. **Risk ID & Title:** `RISK-04` — NATS JetStream Is Not Automatically a PostgreSQL Synchronous Standby
2. **Severity:** `P0`
3. **Root Cause:** Treating a distributed messaging broker (NATS JetStream) as an equivalent substitute for PostgreSQL's stateful physical replication standby (`walreceiver` + disk WAL writer + `PGDATA` replay engine) without accounting for Raft sync/disk flush behavior, WAL framing/timeline semantics, slot state, and recovery reconstruction.
4. **Failure Scenario:** Primary sends raw WAL chunks into a 3-node NATS JetStream cluster deployed with default file-storage caching (where clustered Raft prioritizes quorum replication in memory/page cache before forced OS `fsync` on every publish—per NATS documentation) OR all 3 NATS nodes land on the same physical Fly host. A host power failure drops the un-flushed OS page cache across all 3 nodes simultaneously, or out-of-order/duplicated frames across timeline switches break reassembly into valid 16 MB WAL segments, causing total cluster corruption on failover.
5. **Technical Explanation:** According to official [NATS JetStream documentation](https://docs.nats.io/nats-concepts/jetstream): JetStream uses Raft consensus (`R=3` quorum of `2`, `R=5` quorum of `3`) and `FileStorage`, yielding linearizable append order and at-least-once consumer delivery; *however*, in clustered Raft mode JetStream relies on distributed replication rather than calling synchronous `fsync()` per individual message publish by default, creating a correlated host-power-loss window unless `sync` + multi-zone physical placement (`--volume-requires-unique-zone`) are strictly configured. Even *with* synced multi-zone JetStream, NATS only stores opaque pub/sub byte payloads—it has **no native understanding** of PostgreSQL's 16 MB WAL segment boundaries (`000000010000000000000001`), LSN monotonicity checks, `IDENTIFY_SYSTEM` handshakes, durable `slot.restart_lsn`, `.history` timeline branches, partial trailing records across crashes, or instant standby SQL failover (`pg_promote()`). Every failover would still require downloading a cold R2 base backup, reconstructing WAL segments in userspace, handling orphan uncommitted tails, and running full PostgreSQL crash recovery.
6. **Industry-Standard Solutions:**
   - **Real PostgreSQL Physical Standbys** (`walsender` -> `walreceiver`) running in isolated fault zones (`CloudNativePG`, `Patroni`, `RDS Multi-AZ`).
   - **PostgreSQL-Protocol-Aware Paxos WAL Quorum (`Neon Safekeepers`)** purpose-built specifically around PostgreSQL's `wal_control`, `commit_lsn`, term fencing, and `START_REPLICATION` physical protocol.
   - **Message Queues (JetStream / Cloudflare Queues / Kafka) strictly decoupled** for asynchronous usage metering, audit logs, and lifecycle jobs—never synchronous commit durability.
7. **Solution Comparison:**
   - *Option A — NATS JetStream as WAL Commit Ring:* Lower per-tenant standby idle memory vs warm standbys, **rejected for Stages 0–3** because building/proving a stateful `IDENTIFY_SYSTEM` + partial-segment + epoch-fenced + Raft-fsynced WAL reassembly layer adds massive correctness risk, slow cold-R2-restore RTO, and NATS cluster ops overhead.
   - *Option B — Native PG17 Physical Standby + Cloudflare Queues (async events only):* Eliminates maintaining a 3-to-5-node NATS Raft cluster on Fly completely; delegates commit durability to PostgreSQL's battle-tested `walsender`/`walreceiver` engine; delegates billing/GC messaging to managed Cloudflare Queues HTTP Pull consumers.
8. **Recommended Design (`ADR-003`, `ADR-004`):** Completely remove NATS JetStream from the PostgreSQL durability path and replace NATS messaging roles with **Cloudflare Queues** (`cloudflare-go/v7` HTTP Pull API) for async `billing-usage-queue`, `lifecycle-freeze-queue`, and `control-reconcile-queue`. Use real PG17 Physical Standbys placed on distinct Fly zones for Pro synchronous replication, and `pg_receivewal` -> R2 for Standard async archival. Any future shared WAL Sink architecture remains post-Stage-3 R&D gated by passing full protocol-equivalence & chaos parity against the native PG17 standby reference.
9. **Architecture Changes:** Decommission planned NATS JetStream Fly cluster; integrate Cloudflare Queues HTTP Pull workers in `pg-control-plane` (`internal/queue`); route Pro replication directly between Primary and Standby `pg-cell-agent`/PG17 instances over `6PN` mTLS.
10. **Dependencies:** Pro multi-zone Fly placement (`RISK-03`, `RISK-29`), Cloudflare Queues API & idempotent `usage_ledger` (`RISK-28`).
11. **Trade-Offs:** Gives up JetStream's theoretical multi-tenant shared WAL multiplexing (requiring ~45–60 MB RAM per active Pro standby instead), while removing an entire stateful Raft distributed system from operational burden and critical-path durability risk.
12. **Security Implications:** Removes internal NATS authentication/ACL/TLS surface and eliminates cross-tenant WAL payload co-mingling on shared JetStream streams.
13. **Failure Recovery Strategy:** Standby crash triggers `max_slot_wal_keep_size` WAL buffering on primary (alerting past threshold); Control Plane provisions replacement standby from R2 + primary streaming. Cloudflare Queue transient failure buffers usage batches locally in Gateway `bbolt` WAL (`RISK-28`).
14. **Validation Method:** `EXP-D1`, `EXP-D2`, `EXP-D3` (Physical standby `kill -9`, zone isolation, slot retention overflow, timeline promotion vs R2 PITR).
15. **Acceptance Criteria:** `0` custom queue/WAL serialization code in the PG commit path for Stages 0–2; Pro Physical Standby passes 100% of Group D durability chaos tests; Cloudflare Queue pull/ack loses 0 persisted billing batches across consumer restarts.
16. **Remaining Uncertainty:** Real standby RAM footprint and warm-standby idle cost ceiling when scaling past 500 concurrent Pro tenants (`UQR-05`).

### RISK-05: Shared Compute Cell Failure Domain & Defense-in-Depth Isolation
1. **Risk ID & Title:** `RISK-05` — Shared Compute Cell Is Still a Shared Failure Domain
2. **Severity:** `P0`
3. **Root Cause:** Running multiple tenant `postgres` OS processes on one Linux guest VM exposes a single shared Linux kernel, shared page cache, shared `ext4` NVMe volume, shared NIC, shared `/dev/shm`, and global PID/network tables. Linux `cgroups v2` throttles resource quantities (`memory.max`, `io.max`, `cpu.max`) but does **not** restrict filesystem visibility, `/proc` snooping, IPC, or outbound SSRF TCP connections over `6PN`.
4. **Failure Scenario:** Tenant A exploits a SQL/extension flaw or writes an unbounded sort/temp spike: (a) opens TCP connections to Fly internal DNS/`fdaa::3` metadata or Control Plane API (`6PN` SSRF); (b) leaks POSIX DSM segments into shared `/dev/shm` after OOM kill; (c) triggers a guest kernel panic or consumes all file descriptors/RAM before cgroup enforcement kills it, taking down all 80 co-located tenants on the Cell simultaneously.
5. **Technical Explanation:** According to Linux kernel `cgroups v2` documentation (`Documentation/admin-guide/cgroup-v2.rst`): `memory.max` invokes the in-cgroup OOM killer (or with `memory.oom.group = 1`, terminates the entire cgroup cleanly), and `io.max` caps device BPS/IOPS. However, within one Firecracker microVM: (1) Fly injects `/init` as PID 1 and dynamically scales `/dev/shm` to ~50% of VM RAM (`--shm-size` does not apply); PostgreSQL uses `dynamic_shared_memory_type = posix` in `/dev/shm`, so OOM-killed processes can orphan segments on a shared `/dev/shm`. (2) `fly-kernel` may omit optional cgroup controllers or modules. (3) Host hardware failure, Firecracker exit, or guest kernel oops impacts the entire Cell VM as a single blast radius.
6. **Industry-Standard Solutions:**
   - **Hardened OS Container/Namespace Jail + Dedicated VM Tier** (`Supabase` dedicated projects, `RDS` VM-per-instance, `Cloud Run`/`Fly` microVMs).
   - **Defense-in-Depth Namespaces + `seccomp-bpf` + `cgroups v2`** for dense multi-tenant shared Cells, paired with strict Cell size limits bounding blast radius.
7. **Solution Comparison:**
   - *Option A — Bare UIDs + `cgroups v2` only:* Leaves `/proc`, host filesystem paths, `/dev/shm`, and outbound `6PN` network exposed to compromised SQL/C code—**rejected**.
   - *Option B — 1 Firecracker Fly Machine per Tenant:* Strongest hypervisor boundary, **economically unviable for idle/free/micro tiers** due to Fly API write rate limits (`~10 writes/min`) and `$0.15/GB-month` stopped rootfs/volume floor (`RISK-29`).
   - *Option C — Recommended: Defense-in-Depth Linux Sandbox Inside Shared Firecracker Cells + Dedicated VM Tier for Pro/High-Risk:* Isolates every shared tenant inside strict namespaces, loopback netns, `seccomp-bpf`, and `cgroups v2` (with zero-module fallbacks), caps shared Cell blast radius explicitly, and offers 1-VM-per-tenant Dedicated Cells as an enterprise tier.
8. **Recommended Design (`ADR-005`):** Wrap every tenant `postgres` process in: (1) `CLONE_NEWPID` (sees only itself), (2) `CLONE_NEWIPC` (isolated IPC), (3) `CLONE_NEWNS` + `pivot_root` exposing only read-only minimal PG17 bins & `PGDATA` (`0700` owned by UID `10000+slot`, `nosuid,nodev,noexec`), plus a **private per-tenant `tmpfs` `/dev/shm` (`size=64m,mode=1777,nosuid,nodev,noexec`)**, (4) **loopback-only `CLONE_NEWNET`** (zero outbound TCP/`6PN` egress; communicates strictly over bind-mounted Unix socket `/run/pg/{id}/.s.PGSQL.5432`), (5) `CapBnd = 0` & `PR_SET_NO_NEW_PRIVS = 1`, (6) `seccomp-bpf` blocking `ptrace`, `bpf`, `kexec_load`, `mount`, `unshare`, raw sockets, (7) `cgroups v2` (`memory.max`, `memory.oom.group=1`, `pids.max=64`, `cpu.max`, `io.max`, 20% `memory.low` reserved for OS/agent). On boot, `internal/cell/envprobe` probes delegated cgroup controllers and always enforces module-free fallbacks (`oom_score_adj = -900` on `pg-cell-agent` / `+500` on tenants, `RLIMIT_NPROC`/`NOFILE`/`FSIZE`, 1s `/proc/<pid>/statm` + `/proc/<pid>/io` poller). Bound Cell blast radius to max 80–100 active / 500 total tenants per 8 GB Cell VM (`RISK-31`).
9. **Architecture Changes:** Build `internal/cell/envprobe` and `internal/cell/isolation` in `pg-cell-agent`; configure bind-mounted Unix socket bridge from Gateway `6PN` proxy into tenant `CLONE_NEWNS`.
10. **Dependencies:** PostgreSQL extension lockdown (`RISK-10`), Cell memory/disk quotas (`RISK-09`, `RISK-17`), Fly kernel verification (`RISK-13`), Cross-Cell failover (`RISK-19`).
11. **Trade-Offs:** Loopback `CLONE_NEWNET` blocks extensions requiring outbound network calls (`postgres_fdw`, `dblink`, HTTP UDFs) on shared Cells; `seccomp-bpf` adds `<1%` syscall overhead; shared kernel failures still impact up to ~80 active tenants simultaneously until Cross-Cell failover completes.
12. **Security Implications:** Eliminates outbound `6PN` SSRF from SQL engines, prevents cross-tenant `/proc` or `/vol` snooping, prevents `/dev/shm` DSM leakage across restarts, and isolates OOM kills to a single tenant cgroup.
13. **Failure Recovery Strategy:** Tenant OOM or `seccomp` crash kills only that tenant's namespace cleanly via `memory.oom.group=1`; agent logs fault event, frees private `tmpfs` automatically upon namespace teardown, and restarts cluster via standard WAL crash recovery (`PGDATA`). Whole-Cell VM failure triggers `3x1s` hysteresis failover (`RISK-19`).
14. **Validation Method:** `EXP-C1` (Escape/SSRF/proc/noexec penetration), `EXP-C2` (Tenant A OOM + fork bomb + CPU flood vs Tenant B `pgbench`), `EXP-C5` (Whole-Cell `SIGKILL` recovery).
15. **Acceptance Criteria:** `100%` failure (`EACCES`/`ENETUNREACH`/`EPERM`) on SSRF, sibling dir read, `/proc` peek, and `noexec` attempts; Tenant B `pgbench` p99 latency stays within SLA while Tenant A is OOM-killed cleanly; whole-Cell failure recovers all tenants cleanly via Failover/R2.
16. **Remaining Uncertainty:** Exact set of `cgroups v2` controllers delegated inside Fly.io's unprivileged container runtime under `/init` and exact Firecracker guest `fly-kernel` `seccomp`/`userns` support (`UQR-01`).

### RISK-06: Process-Per-Tenant Lifecycle Management
1. **Risk ID & Title:** `RISK-06` — Process-Per-Tenant Lifecycle Management
2. **Severity:** `P1`
3. **Root Cause:** Fly Machines inject Fly's own `/init` binary as PID 1 and terminate VMs with `kill_signal = "SIGINT"` and a 5-second `kill_timeout` by default. Under naive Go process supervision: reparented Postgres backends attach to Fly `/init` instead of `pg-cell-agent` (causing `wait4()` `ECHILD` races/zombies), 5 seconds is far too short to flush dozens of clusters cleanly, agent crashes orphan live `postmaster` processes, and concurrent starts risk dual-primary corruption on `PGDATA`.
4. **Failure Scenario:** A rolling deploy sends `SIGINT` to the Cell VM; Fly kills the Firecracker VM 5 seconds later mid-checkpoint across 60 active clusters, forcing crash WAL recovery on every reboot. Worse, `pg-cell-agent` crashes, restarts, ignores an existing live `postgres` PID, deletes stale-looking `postmaster.pid`, and launches a *second* `postgres` against the same `PGDATA` -> instant shared-buffer & catalog corruption.
5. **Technical Explanation:** PostgreSQL's single-instance defense (`CreateLockFile` creating `postmaster.pid` + SysV/mmap shared-memory key collision) fails if an orchestrator naively deletes `postmaster.pid` during recovery! Furthermore, on Linux `prctl(PR_SET_CHILD_SUBREAPER, 1)` instructs the kernel to reparent any orphaned descendant processes to the calling daemon rather than PID 1 (`/init`). Coupling `pg-cell-agent`'s `PR_SET_CHILD_SUBREAPER` with an **independent OS advisory lock** (`unix.Flock(LOCK_EX | LOCK_NB)` on `PGDATA/agent.lock` held by a lightweight supervisor descriptor or wrapper FD owned outside the tenant's namespace) guarantees mutual exclusion even across restarts or crashes.
6. **Industry-Standard Solutions:**
   - Per-instance `systemd` units inside dedicated VMs (`Patroni`/`RDS`).
   - Lightweight PID/FD supervisor daemon (`s6`, `runit`, or Go `PR_SET_CHILD_SUBREAPER` + `flock` + `/proc` re-adoption).
7. **Solution Comparison:**
   - *Option A — `systemd` transient units:* Heavy per-unit memory overhead, fights Fly's non-systemd `/init` runtime—**rejected**.
   - *Option B — Recommended: Go `pg-cell-agent` Subreaper (`PR_SET_CHILD_SUBREAPER`) + `flock` + `SIGTERM 300s`:* Minimal RAM (~15 MB agent total), works natively under Fly `/init`, survives agent restarts cleanly via `/proc` scan + `postmaster.pid` validation, and parallelizes clean deploys via a 16-goroutine drain pool (`<15s`).
8. **Recommended Design (`ADR-006`):** Set `kill_signal = "SIGTERM"` and `kill_timeout = "300s"` in `fly.cell.toml`. On boot, `pg-cell-agent` calls `unix.Prctl(unix.PR_SET_CHILD_SUBREAPER, 1, 0, 0, 0)` and drains zombies via `SIGCHLD`/`wait4(-1, WNOHANG)`. To re-adopt across agent crashes: scan `/vol/tenants/*/pgdata/postmaster.pid`, validate matching live PID in `/proc/<pid>/comm` and `agent.lock` state, and only purge `postmaster.pid`/`.s.PGSQL.5432` when `flock(LOCK_EX|LOCK_NB)` succeeds and PID is confirmed dead. During VM shutdown (`SIGTERM`), run a 16-goroutine worker pool checkpointing and calling `pg_ctl stop -m smart` across all active clusters cleanly well inside the 300s window. Track per-tenant startup timeout (base 10s, extended to 30s if post-crash WAL recovery is detected) with exponential crash-loop backoff.
9. **Architecture Changes:** Build `internal/cell/supervisor` (`PR_SET_CHILD_SUBREAPER`, `flock` lock manager, `/proc` re-adoption scanner, startup/shutdown FSM, crash-recovery timeout detector); update `deploy/fly/fly.cell.toml`.
10. **Dependencies:** Fly `/init` runtime configuration (`RISK-29`), unique cluster directories (`RISK-01`), Gateway drain protocol (`RISK-07`).
11. **Trade-Offs:** Parallel 16-goroutine `pg_ctl stop` during deploys creates a transient I/O/checkpoint spike bounded inside 15s (requiring `300s` safety timeout margin).
12. **Security Implications:** `PGDATA/agent.lock` stored outside tenant `CLONE_NEWNS` visibility (`0600` owned by root) so tenant SQL/C code cannot unlink or forge lock state.
13. **Failure Recovery Strategy:** If `pg-cell-agent` suffers `SIGKILL`, tenant `postgres` instances stay alive serving queries (`postmaster` unaffected); restarted `pg-cell-agent` re-adopts all running PIDs cleanly within `<500ms`. If `postgres` itself crashes repeatedly (>3 crashes in 60s), quarantine tenant into `CRASH_LOOP` state, alert operations, and inspect R2 PITR integrity.
14. **Validation Method:** `EXP-A3` (`SIGKILL` agent re-adoption), `EXP-B1`/`EXP-B3` (Shutdown races), `EXP-C5` (500 concurrent wake/stop stress + zero zombie/dual-primary assertion).
15. **Acceptance Criteria:** `0` dual-primary starts across 1,000 forced race/crash iterations; `100%` live query survival across `pg-cell-agent` `SIGKILL` restarts; `0` zombie processes (`Z` state) left behind after 1,000 start/stop cycles; clean full-Cell VM drain `<15s` on `SIGTERM`.
16. **Remaining Uncertainty:** Real PostgreSQL startup durations across 5,000-table catalogs, `pgvector` index loads, and post-crash dirty WAL replay on Fly NVMe (`EXP-B1` / `UQR-08`).

### RISK-07: Scale-to-Zero & Cooperative Drain
1. **Risk ID & Title:** `RISK-07` — Scale-to-Zero & Cooperative Drain
2. **Severity:** `P1`
3. **Root Cause:** Determining shutdown safety from a single local agent SQL probe (such as `SELECT count(*) FROM pg_listening_channels()`, which per PostgreSQL docs inspects *only the calling session's* channels!) misses idle clients holding temp tables, `LISTEN` subscriptions, session GUCs, advisory locks, prepared transactions (`2PC`), and allows new connections to race in between the idle check and `pg_ctl stop`.
4. **Failure Scenario:** App opens a persistent `LISTEN/NOTIFY` connection or holds a `CREATE TEMP TABLE` inside an idle-pooled connection. Agent sees zero running queries, invokes `pg_ctl stop -m fast`, killing the backend and silently losing notifications or dropping temp tables—or Client B establishes a TCP connection 3ms after the SQL check and gets `ECONNRESET` mid-handshake as `postgres` exits.
5. **Technical Explanation:** PostgreSQL session state is stateful per backend (`LISTEN` hash table `pendingActions`, `pg_temp_*` schemas, `pg_advisory_lock()`, non-default session `SET` GUCs, open cursors) and cannot be safely inspected or migrated out-of-band by a sidecar agent. Furthermore, `pg_ctl stop -m smart` blocks waiting for all clients to disconnect unless connections are actively closed by the upstream gateway/pooler, whereas `-m fast` rolls back active transactions (`FATAL: terminating connection due to administrator command`). Therefore, safe scale-to-zero requires Gateway orchestration: the Gateway owns connection admission and session-pinning state.
6. **Industry-Standard Solutions:**
   - **Proxy/Compute Coordinated Drain** (`Neon` Compute/Proxy autosuspend coordinator, `Cloud Run`/`Fly` concurrency-based proxy hold queue + `SIGTERM` drain).
   - **Opt-Out / Dedicated Always-On** for stateful workloads holding persistent listeners or advisory locks.
7. **Solution Comparison:**
   - *Option A — Agent-only `pg_stat_activity` polling + `pg_ctl stop -m fast`:* Simple, **broken**—breaks `LISTEN`, temp tables, advisory locks, and races new client arrivals.
   - *Option B — Recommended: Gateway-Controlled Drain Protocol:* Gateway gates new transactions (`DRAINING` hold queue), waits for active transactions and pinned sessions (`0 pinned, 0 active`), signals `pg-cell-agent` to verify zero `pg_prepared_xacts`, zero background/replication/COPY workers, flush WAL, execute `pg_ctl stop -m smart`, and assert `pg_controldata` `"shut down"`.
8. **Recommended Design (`ADR-007`):** Note: Scale-to-zero sits cleanly in **Stage 3** (after Stage 1–2 core stability). When idle threshold expires and Gateway confirms `0 active transactions` and `0 pinned sessions` (`LISTEN`, `TEMP TABLE`, `SET`, advisory lock, active `COPY`), `pg-cell-agent` initiates drain -> Gateway transitions tenant route state to `DRAINING` and buffers newly arriving requests in its wake hold queue -> Gateway closes idle pooled backend sockets -> `pg-cell-agent` checks `pg_prepared_xacts == 0` and zero active workers -> forces WAL switch/flush (`CHECKPOINT` + archive sync) -> calls `pg_ctl stop -m smart` (escalating to `-m fast` only past 25s safety deadline) -> verifies `pg_controldata` reports `Database cluster state: shut down` -> marks `STOPPED`. If Gateway accumulated held requests during drain, it immediately dispatches `Wake()`.
9. **Architecture Changes:** Add Gateway-Agent `Drain` / `AbortDrain` RPC over `6PN` mTLS; track session-pinning flags in `pg-gateway` (`internal/wire`) / PgBouncer session state; keep `maintenance_lock` veto hook (`RISK-08`).
10. **Dependencies:** Gateway protocol observer (`RISK-11`), process lock/lifecycle (`RISK-06`), maintenance scheduler (`RISK-08`), wake-up coalescing (`RISK-36`).
11. **Trade-Offs:** Tenants keeping idle `LISTEN` or session-pinned clients open cannot sleep until client disconnect or idle-pin timeout expiration (explicitly billed as active RAM/seat time or documented in Developer Docs).
12. **Security Implications:** Clean socket close prevents half-open session state carry-over across wake cycles and ensures clean audit logging of sleep/wake epochs.
13. **Failure Recovery Strategy:** If a client arrives mid-`DRAINING`, Gateway pauses it transparently in memory until either drain aborts (if `postgres` still alive pre-`pg_ctl`) or `STOPPED` completes and immediately triggers `Wake()`, returning zero `ECONNRESET`. If shutdown deadline expires due to stuck backend/IO, escalate `-m fast`, archive WAL, and log alert.
14. **Validation Method:** `EXP-B1`..`EXP-B5` (1,000 randomized drain races with concurrent `LISTEN`, `PREPARE TRANSACTION`, `COPY`, advisory locks, and +/-5ms late arrivals).
15. **Acceptance Criteria:** `0` unexpected `ECONNRESET` errors; `0` shutdowns permitted while `LISTEN`, `2PC`, or advisory locks are active; `100%` of clean sleeps confirm `pg_controldata` `"shut down"` and archived final WAL before `STOPPED`.
16. **Remaining Uncertainty:** Real p50/p95/p99 drain duration under active Page Cache dirty writeback and wake-after-drain turn-around time (`EXP-B1`, `UQR-08`).

### RISK-08: Autovacuum & Transaction ID Wraparound
1. **Risk ID & Title:** `RISK-08` — Autovacuum & Transaction ID Wraparound
2. **Severity:** `P1`
3. **Root Cause:** Relying solely on a brief `VACUUM` immediately before sleep leaves high-churn databases (that burst heavily for 20s and sleep for 25s, or never sleep while running heavy updates, or sit dormant in R2 for months with elevated `datfrozenxid`) vulnerable to XID/Multixact exhaustion before `autovacuum_naptime` (default 60s) wakes workers cleanly.
4. **Failure Scenario:** A serverless webhook processor runs 100k short `UPDATE`/`DELETE` transactions in 15-second bursts every few minutes, sleeping cleanly before autovacuum completes, or holds a long-lived `BEGIN` cursor/prepared transaction/orphaned replication slot preventing `xmin` advancement. Eventually `age(datfrozenxid)` hits ~2 billion (`xidStopLimit`), and PostgreSQL locks out all writes globally: `ERROR: database is not accepting commands to avoid wraparound data loss`.
5. **Technical Explanation:** PostgreSQL uses modulo-$2^{32}$ transaction IDs (`XID`) and `MultiXactId` (`MXID`), allowing ~2 billion live XIDs ahead of `datfrozenxid` before forced shutdown protects tuple visibility (`src/backend/access/transam/varsup.c`). Scale-to-zero interacts dangerously with autovacuum because stopped clusters advance zero vacuum progress while sleeping, yet if woken repeatedly for sub-minute intervals with `autovacuum_naptime = 60s`, autovacuum workers rarely complete a pass—and an active `idle in transaction` session, unconsumed replication slot, or `2PC` transaction blocks `RecentGlobalXmin` globally inside that tenant cluster.
6. **Industry-Standard Solutions:**
   - Dedicated background monitoring of `age(datfrozenxid)`, `mxid_age(datminmxid)`, `pg_stat_user_tables` dead tuples, slot lag, and prepared xact age (`RDS`, `Neon`, `Crunchy`/`Patroni`).
   - Proactive `maintenance_lock` blocking suspend until `VACUUM (FREEZE)` completes.
   - Aggressive idle-in-transaction & slot retention timeouts.
8. **Recommended Design (`ADR-007`):** Implement `internal/cell/maintenance` scheduler on every Cell: (1) Set defaults `autovacuum_naptime = '15s'`, `autovacuum_vacuum_cost_limit = 400`, `idle_in_transaction_session_timeout = '5min'`, `max_slot_wal_keep_size = '256MB'`; (2) Poll `age(datfrozenxid)`, `mxid_age(datminmxid)`, dead tuple ratios, `pg_prepared_xacts` age, and slot lag every 5m while active and immediately upon every wake-up; (3) If `age(datfrozenxid) > 100_000_000` (5% of wraparound limit) or `mxid_age > 100_000_000` or dead tuples > 25%, assert `maintenance_lock = true` (vetoing scale-to-zero drain), execute throttled `VACUUM (FREEZE, INDEX_CLEANUP AUTO)`, and clear lock only once thresholds drop below watermark; (4) Always execute `VACUUM (FREEZE)` before Stage 3 Deep Freeze archival to R2 so cold backups start cleanly near XID age 0.
9. **Architecture Changes:** Add `internal/cell/maintenance` goroutine inside `pg-cell-agent`; integrate `maintenance_lock` veto into `RISK-07` drain check; export XID/MXID age metrics (`RISK-39`).
10. **Dependencies:** Cooperative drain (`RISK-07`), Cell disk/IO limits (`RISK-17`, `RISK-37`), monitoring/alerts (`RISK-39`, `RISK-40`).
11. **Trade-Offs:** `VACUUM (FREEZE)` adds write amplification (extra full-page WAL writes when freezing old blocks) and holds tenants awake during maintenance windows, slightly reducing scale-to-zero sleep ratios for write-heavy Free/Standard DBs.
12. **Security Implications:** Maintenance role executes internally via local agent Unix connection, isolated from customer credentials; `idle_in_transaction_session_timeout` also defends against deliberate lock/bloat DoS.
13. **Failure Recovery Strategy:** If `age(datfrozenxid)` exceeds critical alert (`>120M` / `RISK-40`) due to a long-running query or orphaned slot, alert operations and inspect blockers in `pg_stat_activity` / `pg_replication_slots` (dropping stale dead slots only per explicit DR policy).
14. **Validation Method:** `EXP-B2` & `EXP-C4` (Continuous 10M high-churn `UPDATE`/`DELETE` txns inside 25s wake/sleep loops while measuring `age(datfrozenxid)`, table bloat, and WAL amplification).
15. **Acceptance Criteria:** `age(datfrozenxid)` never exceeds `150M` across 10M churn transactions under forced rapid wake/sleep cycles; `maintenance_lock` demonstrably vetoes sleep until `VACUUM (FREEZE)` completes.
16. **Remaining Uncertainty:** Optimal `vacuum_cost_delay` and `maintenance_work_mem` values to avoid hurting OLTP neighbors while completing freeze quickly on Fly NVMe (`UQR-07`).

### RISK-09: PostgreSQL Memory Configuration & OOM Risk
1. **Risk ID & Title:** `RISK-09` — PostgreSQL Memory Configuration
2. **Severity:** `P1`
3. **Root Cause:** Assuming an idle/light PG17 cluster consumes 35–50 MB RSS ignores dynamic worst-case allocations: `work_mem` applies *per sort/hash/CTE node* *per parallel worker* *per backend connection*; `maintenance_work_mem`, extension heaps (`pgvector` HNSW indexes), mmap'd files, Linux Page Cache pressure, and shared `/dev/shm` POSIX DSM leaks quickly blow past static 50 MB estimates and trigger host-wide OOM kills.
4. **Failure Scenario:** Five concurrent queries run 4-way hash joins with `max_parallel_workers_per_gather = 2` and `work_mem = 4MB`, allocating `5 × 3 processes × 4 nodes × 4 MB = 240 MB` anonymous RAM + 64 MB `/dev/shm` segments inside a tenant expecting 50 MB -> triggers Cell memory exhaustion, killing `pg-cell-agent` or healthy sibling tenants via Linux host OOM killer.
5. **Technical Explanation:** PostgreSQL memory breaks into shared memory (`shared_buffers`, WAL buffers, lock tables, proc arrays—allocated at boot + DSM segments in `/dev/shm` under `dynamic_shared_memory_type = posix`) and private per-backend heap (`work_mem` *per executor node*, catalog/relcache `CacheMemoryContext` scaling with table/column count, PL/pgSQL context, extension caches). On Fly.io Firecracker microVMs, `/dev/shm` defaults to 50% of VM RAM globally; an OOM kill inside a shared `/dev/shm` fails to call `shm_unlink()`, silently leaking shared memory segments until reboot. Additionally, `shared_buffers = 16MB` relies heavily on the shared Linux Page Cache (trading extra `pread`/`write` kernel copies for dense tenant packing), meaning heavy active tables compete directly in the VM's shared page cache.
6. **Industry-Standard Solutions:**
   - Explicit cgroup memory limits (`memory.max`, `memory.oom.group = 1`) + OOM priority shielding (`oom_score_adj = -900` on supervisor, `+500` on tenant processes).
   - Tiered `shared_buffers` sizing + strict `max_connections` & parallel-worker caps (`max_parallel_workers_per_gather = 0`) on multi-tenant shared nodes.
   - Dedicated swap shock absorber (`swap_size_mb = 2048` on Fly) preventing instant hard OOM on micro-spikes.
7. **Solution Comparison:**
   - *Option A — Fixed static "50 MB per tenant" oversubscription:* High apparent density, **causes Cell OOM crashes** under analytical/join spikes.
   - *Option B — Reserve worst-case `15 × 4MB × 4` (240 MB) for every dormant/idle tenant:* Prevents overcommit completely, **cripples density** (~30 tenants per 8 GB VM).
   - *Option C — Recommended: Tight Cgroup Caps (`memory.max`), Private `/dev/shm` `tmpfs`, Zero Parallel Workers on Shared Cells & Dynamic Admission Math:* Caps per-tenant burst inside `cgroups v2` (`memory.oom.group = 1`), reserves **25% VM RAM** for OS/agent/Page Cache + `swap_size_mb = 2048`, keeps `work_mem = 4MB` + `max_parallel_workers_per_gather = 0`, mounts private `64m` `/dev/shm` per tenant, and admits active tenants by summing baseline RSS + active burst budget (`<=75%` VM RAM).
8. **Recommended Design (`ADR-008`):** Configure shared Cells with PG17 defaults: `shared_buffers = '16MB'` (to be empirically benchmarked vs `32MB`/`64MB` in Stage 0–1), `max_connections = 15`, `work_mem = '4MB'`, `maintenance_work_mem = '32MB'`, `max_parallel_workers_per_gather = 0`, `huge_pages = off`. In `fly.cell.toml`, set `swap_size_mb = 2048`. Inside each tenant's `CLONE_NEWNS`, mount a private `tmpfs` `/dev/shm` (`size=64m,mode=1777,nosuid,nodev,noexec`). Set `cgroups v2` per-tenant `memory.high` (80% tier cap) and `memory.max` (100% tier cap, e.g., 128 MB–512 MB), `memory.oom.group = 1`, `oom_score_adj = -900` on `pg-cell-agent` / `+500` on tenants, plus 1s `/proc/<pid>/statm` watchdog fallback. Tiered Paid/Dedicated Cells scale `shared_buffers` (`64MB`–`256MB`) proportionally.
9. **Architecture Changes:** Add per-tenant `tmpfs` `/dev/shm` mount to `internal/cell/isolation`; implement admission math (`Sum(active_baseline + burst_headroom) <= 0.75 * VM_RAM`) in `pg-cell-agent` & Control Plane scheduler; configure `swap_size_mb = 2048` in `deploy/fly/fly.cell.toml`.
10. **Dependencies:** Cgroup/namespace isolation (`RISK-05`), Cell capacity policy (`RISK-31`), large-tenant promotion (`RISK-38`), Fly VM SKUs (`RISK-29`).
11. **Trade-Offs:** `max_parallel_workers_per_gather = 0` and `shared_buffers = 16MB` trade parallel scan speed and double-buffer hit latency on large shared queries in exchange for predictable density and zero OOM cascades; `swap_size_mb = 2048` trades latency on spike paging over sudden process termination.
12. **Security Implications:** `memory.oom.group = 1` + private `/dev/shm` stops single-tenant OOM bombs from either killing `pg-cell-agent`/siblings or leaving unlinked shared memory segments exhausting VM `/dev/shm`.
13. **Failure Recovery Strategy:** If a tenant query exceeds `memory.max`, the Linux cgroup OOM killer cleanly kills the entire offending tenant `cgroup` -> `pg-cell-agent` clears IPC/sockets (private `tmpfs` `/dev/shm` frees automatically on namespace exit), emits alert/event, and lets next client request restart cleanly via `PGDATA` WAL crash recovery while siblings keep running uninterrupted.
14. **Validation Method:** `EXP-C2` (50 concurrent active tenants + multi-join `work_mem`/PL/pgSQL memory bombs vs `pgbench` Tenant B), plus Stage 1 `16MB` vs `32MB` vs `64MB` `shared_buffers` RSS/p99 benchmark.
15. **Acceptance Criteria:** `0` `pg-cell-agent` or sibling OOM kills across 100 injected memory-bomb cycles; private `/dev/shm` utilization returns strictly to `0` within 1s of killed tenant exit; empirical `shared_buffers` benchmark recorded before Stage 2.
16. **Remaining Uncertainty:** Exact resident RSS profile of PG17 with `1,000+` tables (Catalog/RelCache growth) and `pgvector` HNSW indexes under `shared_buffers = 16MB` vs `32MB` on Fly NVMe (`UQR-07`).

### RISK-10: PostgreSQL Configuration & Extension Isolation
1. **Risk ID & Title:** `RISK-10` — PostgreSQL Configuration Isolation
2. **Severity:** `P1`
3. **Root Cause:** Granting `SUPERUSER` or trusting `supautils` alone to secure extensions and GUCs fails if untrusted procedural languages (`plpython3u`, `plperlu`, `c`), `COPY ... FROM PROGRAM`, `LOAD '/path/to/evil.so'`, `ALTER SYSTEM`, or host filesystem paths (`pg_read_server_files`, `file_fdw`) remain reachable, or if tenants can mutate `postgresql.conf`/`pg_hba.conf`.
4. **Failure Scenario:** A malicious tenant invokes `CREATE EXTENSION plpython3u;` or compiles/drops a `.so` file or executes `COPY t FROM PROGRAM 'cat /proc/1/environ'` or exploits a vulnerable third-party C extension hook to escalate to the Linux UID running `postgres`, reading host secrets or sibling files.
5. **Technical Explanation:** In PostgreSQL's privilege architecture, `SUPERUSER` intentionally bypasses all internal SQL permission checks and grants OS user execution via `COPY ... PROGRAM` and `LOAD`. While Supabase's `supautils` intercepts `ALTER SYSTEM`, reserved roles, and extension hooks (`ProcessUtility_hook`), C-level hooks run *inside* the postmaster address space after dynamic extension code loads—meaning any buggy or untrusted C extension can subvert hooks via raw pointer memory writes if arbitrary extensions or untrusted `.so` uploads are permitted. Therefore, **PostgreSQL engine restrictions must be reinforced by OS namespace containment (`RISK-05`, `RISK-21`) and a strict vetted Extension Allowlist**.
6. **Industry-Standard Solutions:**
   - **No Tenant `SUPERUSER` + Vetted Extension Allowlist (`RDS`, `Supabase`, `Neon`)** exposing only audited extensions compiled safely into read-only system dirs.
   - **Dedicated VM Tier** for untrusted languages (`plpythonu`) or custom extensions (`PostGIS`, third-party `.so`).
   - **OS `noexec` + `pivot_root` + `seccomp-bpf` backstop** ensuring even an exploited C extension cannot read host secrets or dial out over `6PN`.
7. **Solution Comparison:**
   - *Option A — `supautils` + arbitrary shared extensions on Shared Cells:* Unacceptable C-level exploit blast radius (`P0` escalation).
   - *Option B — Zero extensions enabled:* Breaks mainstream Postgres apps needing `uuid-ossp`, `pgcrypto`, `pg_trgm`, `vector`.
   - *Option C — Recommended: Strict Version-Locked Extension Allowlist + `app_owner` Role + `supautils` + OS Jail:* Permits audited safe extensions safely via `supautils` privilege delegation while stripping `SUPERUSER`, blocking `LOAD`/`COPY PROGRAM`/untrusted PLs, locking down configs (`0600` root-owned), and isolating inside `CLONE_NEWNS` + `noexec`.
8. **Recommended Design (`ADR-005`):** Provision tenants strictly as non-superuser `app_owner` (`NOSUPERUSER NOCREATEDB NOCREATEROLE` or tightly scoped via `supautils`). Lock `supautils.extensions_parameter_overrides` & extension allowlist strictly to: `uuid-ossp`, `pgcrypto`, `pg_trgm`, `citext`, `btree_gin`, `btree_gist`, `hstore`, `vector` (`pgvector`), and `pg_stat_statements`. Strip/do not ship untrusted PLs (`plpython*`, `plperl*`, `pltcl*`) or `adminpack`/`file_fdw` packages on shared Cell images. Enforce `dynamic_library_path = '$libdir'` locked by root (`0600` `postgresql.conf`/`pg_hba.conf` + immutable GUC guard), `REVOKE EXECUTE` / missing memberships on `pg_execute_server_program`, `pg_read_server_files`, `pg_write_server_files`. Require Dedicated Firecracker Cells for custom/untrusted extensions.
9. **Architecture Changes:** Configure `deploy/Dockerfile.cell` compiling only the vetted PG17 extension set + `supautils`; enforce root-owned `0600` immutable config injection in `pg-cell-agent` before `pivot_root`; update product docs explicitly scoping shared-Cell extension compatibility.
10. **Dependencies:** OS isolation & loopback `CLONE_NEWNET` (`RISK-05`, `RISK-21`), PostgreSQL secret/auth protection (`RISK-22`).
11. **Trade-Offs:** Tenants requiring `PostGIS`, `pg_cron`, `timescaledb`, or custom C extensions must deploy on Dedicated VM Cells (`higher $/mo SKU`), sacrificing zero-cost shared packing for safety.
12. **Security Implications:** Closes every standard PostgreSQL SQL-to-shell escalation vector (`COPY PROGRAM`, `LOAD`, `pg_read_server_files`, `file_fdw`), backed up by `noexec` + `CLONE_NEWNS` + `seccomp-bpf` if a zero-day C bug hits an allowlisted extension.
13. **Failure Recovery Strategy:** If an extension vulnerability (`CVE`) is discovered in an allowlisted extension, update `Dockerfile.cell` and roll-deploy Cells cleanly using 16-goroutine `SIGTERM` drain, or temporarily revoke `CREATE EXTENSION <ext>` via `supautils` config push.
14. **Validation Method:** `EXP-C1` (Automated SQL privilege escalation suite inside tenant role attempting `COPY PROGRAM`, `LOAD`, `CREATE FUNCTION ... LANGUAGE C/plpython3u`, `ALTER SYSTEM`, `pg_ls_dir('/vol')`).
15. **Acceptance Criteria:** `100%` of escalation vectors blocked cleanly by PostgreSQL (`insufficient privilege`) and verified additionally blocked at OS/chroot/netns level if simulated from local C hook.
16. **Remaining Uncertainty:** Exact `supautils` compatibility and behavior against PostgreSQL 17's new utility hooks & role GUC changes (`UQR-06`, needs Stage 0 build/test).

### RISK-11: Prepared Statement Virtualization & Protocol Compatibility
1. **Risk ID & Title:** `RISK-11` — Prepared Statement Virtualization
2. **Severity:** `P1`
3. **Root Cause:** Attempting to multiplex multiple PostgreSQL clients onto a smaller backend pool inside a custom Go transaction-mode proxy by naively maintaining a `stmtName -> sqlHash` map fails catastrophically across the full Extended Query Protocol state machine (`Parse`, `Bind`, `Describe`, `Execute`, `Close`, `Sync`, `Flush`, unnamed `""` statements/portals, pipeline mode, error-skip-to-`Sync`, DDL plan invalidation, `DEALLOCATE`, `DISCARD ALL`, and session-bound side effects like `TEMP TABLE` / `SET` / `LISTEN` / `advisory_lock`).
4. **Failure Scenario:** Prisma or `pgx` sends a pipelined batch: `Parse("") -> Bind("") -> Execute -> Parse("") -> Sync`. A naive transaction proxy collides statement `""`, loses `ParseComplete`/`BindComplete` ordering, fails to swallow post-error messages until `Sync`, or swaps backend connections between `CREATE TEMP TABLE` and `SELECT * FROM temp_t`, crashing production apps with `ERROR: prepared statement "s1" does not exist` or silent wrong results.
5. **Technical Explanation:** According to PostgreSQL Frontend/Backend Protocol docs (`protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY`), prepared statements (`Parse`) are **connection-local state** inside a `postgres` backend (`PreparedStatement` hash table). Unnamed statement `""` has lifetime rules tied to subsequent `Parse("")`, while named statements persist across transactions until `Close('S')` or `DEALLOCATE`, and **portals** bind parameters with partial fetch `max_rows` (suspended portals across `Execute`/`Flush` cannot move backends!). When any message errors in Extended Query, Postgres discards all subsequent pipelined messages until the next `Sync` (`'S'`) clears the error state. Worse, transaction pooling is fundamentally incompatible with session-stateful constructs unless the proxy dynamically tracks and **pins** that client to its dedicated backend (`TEMP TABLE`, `DECLARE CURSOR`, `SET` vs `SET LOCAL`, `pg_advisory_lock`, `LISTEN`, `PREPARE TRANSACTION`).
6. **Industry-Standard Solutions:**
   - **Proven Session / Transaction Pooler (`PgBouncer 1.21+`)**: Added full protocol-level prepared-statement rewriting in transaction mode (`max_prepared_statements`), battle-tested across Prisma/pgx/JDBC.
   - **Two-Endpoint Separation (`Supabase` / `Neon`):** Dedicated Transaction Pooler endpoint (via `PgBouncer` or custom proxy) + Direct Session endpoint for stateful migrations/`pg_dump`/`LISTEN`.
   - **Custom Protocol-Aware Multiplexer** built after extensive driver compatibility testing (`pgpool-II`, `Odyssey`, `Supavisor`).
7. **Solution Comparison:**
   - *Option A — Build custom Go Extended-Query virtualizer for Stage 1 MVP:* High probability of subtle ORM bugs (Prisma/Drizzle/JDBC/pipeline), delays core reliability work by months—**rejected for Stages 1–2**.
   - *Option B — Pure Session Pooling only (`max_connections=15` cap):* 100% SQL/protocol compatible, **limits concurrent serverless lambda fan-in** unless paired with `PgBouncer`.
   - *Option C — Recommended (`ADR-009`):* **Stages 1–2:** Terminate TLS/SNI/Auth/Metering cleanly in Go `pg-gateway`, delegating pooling behind `pg-gateway` to **Session Pooling or proven `PgBouncer 1.21+` (`pool_mode = transaction` with `max_prepared_statements > 0` + Direct session endpoint)**. **Stage 3:** Introduce optional custom Go `pgproto3` transaction multiplexer & session pinning *only* after passing 100% of Benchmark Group E across all 7 drivers/ORMs.
8. **Recommended Design (`ADR-009`):** Separate TLS/SNI/SCRAM/Wakeup/RU-Metering in `pg-gateway` from transaction-mode SQL pooling in Stages 1–2 by pairing `pg-gateway` with per-Cell `PgBouncer 1.21+` (or dedicated session mode). Document explicit transaction-pooling incompatibilities cleanly (session `SET`, `LISTEN`, `TEMP TABLE` require the Direct/Session endpoint or automatic pinning). When building Stage 3 native Go transaction multiplexing (`internal/wire`), implement the complete state machine: per-client virtual statement/portal tables, rewriting client names to backend canonical hash IDs, replaying missing `Parse` frames transparently on backend rebind, swallowing errors strictly until `Sync`, invalidating on DDL/rollback/`DEALLOCATE ALL`/`DISCARD ALL`, forwarding `CancelRequest` via CSPRNG key mapping, and auto-pinning sessions cleanly upon `TEMP`/`LISTEN`/`SET`/advisory locks/`BEGIN` (`Sync` boundary).
9. **Architecture Changes:** Deploy `PgBouncer 1.21+` inside `Dockerfile.cell` (or Session Pooling default) for Stages 1–2; keep `internal/wire` in Stage 1–2 focused cleanly on `SSLRequest`, DirectTLS, SNI/SCRAM auth binding, packet bounds, `pgproto3` frame inspection for RU counting, and transparent byte pass-through once backend bound.
10. **Dependencies:** Gateway security & packet caps (`RISK-23`), connection queue/backpressure (`RISK-12`), scale-to-zero drain protocol (`RISK-07`).
11. **Trade-Offs:** Passing through `PgBouncer 1.21+` adds one ultra-fast local Unix-socket hop (~50–100µs) inside the Cell VM in Stages 1–2, in exchange for eliminating months of subtle protocol virtualizer bugs before production launch.
12. **Security Implications:** Clean `DISCARD ALL` / `RESET ALL` between unpinned transactions (and isolated per-tenant PgBouncer pools/sockets) guarantees zero session variable or prepared-plan bleed between connections.
13. **Failure Recovery Strategy:** If a backend drops mid-extended-query batch in unpinned mode before `ReadyForQuery` (`'Z'`), fail cleanly with `08006` (never silently replay unknown side-effect SQL on another backend!). DDL invalidation errors automatically clear cached backend statement mappings cleanly.
14. **Validation Method:** `EXP-E1`..`EXP-E4` (Full real integration test suites for **Prisma, Drizzle, `pgx` pipeline mode, `sqlx`, JDBC `useServerPrepStmts`, `node-postgres`, and `psql`** across migrations, `COPY`, prepared statements, rollbacks, `CancelRequest`, `LISTEN/NOTIFY`).
15. **Acceptance Criteria:** `100%` pass rate across all 7 real ORM/driver test suites in Group E; `0` protocol desyncs, `prepared statement does not exist` errors, or wrong-backend temp-table reads under concurrent load.
16. **Remaining Uncertainty:** Exact `PgBouncer 1.21+` prepared-statement memory overhead per tenant when hosting 80–100 active tenants on one Cell, and subtle Prisma/pgx pipeline edge cases under scale-to-zero drain (`UQR-09`).

### RISK-12: PostgreSQL Connection Pooling & Storms
1. **Risk ID & Title:** `RISK-12` — PostgreSQL Connection Pooling
2. **Severity:** `P1`
3. **Root Cause:** Serverless compute functions (Vercel, AWS Lambda, Cloudflare Workers) frequently open hundreds to thousands of concurrent short-lived TCP connections simultaneously, quickly saturating per-tenant `max_connections = 15`, exhausting Cell file descriptors/backend RAM, and creating unbounded queue head-of-line blocking if connection limits, wait timeouts, cancellation, and pinned-session leaks are unmanaged.
4. **Failure Scenario:** A serverless webhook spike spawns 600 concurrent Edge requests hitting Tenant A (holding 50ms queries). Without bounded queues at Gateway and global Cell backend limits, 600 sockets hit Postgres (`FATAL: sorry, too many clients already`), or 20 active tenants all spawn 50 backends each (`1,000 backends × 8 MB` = `8 GB RAM`), OOM-crashing the entire Compute Cell.
5. **Technical Explanation:** Every PostgreSQL backend process spawns a heavyweight OS process (`~5–10 MB` private/Pg shared maps + kernel stack + file descriptors). Shared Cells cannot admit unbounded backends without blowing VM RAM (`RISK-09`) or `pids.max = 64` (`RISK-05`). Additionally, when queued or active queries stall, PostgreSQL `CancelRequest` (a separate out-of-band connection carrying `(ProcessID, SecretKey)`) must be rewritten and routed to the **exact backend socket** currently executing that client's query—trivial in session mode, subtle in multiplexed transaction mode!
6. **Industry-Standard Solutions:**
   - Two-level bounded semaphore queues (Per-tenant client cap + Per-tenant backend cap + Global Cell backend cap + Wait timeout -> `53300`).
   - Idle-in-transaction & idle-pinned-session reclamation timeouts (`idle_in_transaction_session_timeout`, `client_idle_timeout`).
7. **Solution Comparison:**
   - *Option A — Unlimited client queueing inside `pg-gateway`:* Buffers bursts silently until Go heap fills or clients time out past 60s—**causes memory exhaustion & retry storms**.
   - *Option B — Fast-fail immediately at `max_connections = 15` with zero queue:* Drops brief 20ms concurrent micro-bursts unnecessarily.
   - *Option C — Recommended (`ADR-009`): Bounded Waiting Queues + Global Cell Backend Ceiling + `CancelRequest` Registry:* Permits controlled burst absorption (e.g., 200 concurrent clients waiting max 5s for 15 backend slots per tenant), caps total active backends per 8 GB Cell (`<=1,200`), and routes `CancelRequest` accurately.
8. **Recommended Design (`ADR-009`):** Enforce strict numerical bounds: (1) Per-tenant active backend cap `10–15` (tiered by SKU, default 15 in PG); (2) Per-tenant Gateway waiting client cap `200` (pooled mode) with **5-second pool acquisition deadline** returning SQLSTATE `53300` (`too_many_connections: pool queue timeout`) cleanly rather than silently hanging; (3) Global Cell backend limit (`<=1,200` total active PG backends across an 8 GB Cell enforced by `pg-cell-agent` + Gateway); (4) Pinned session timeout (`idle_session_timeout = '10min'`, `idle_in_transaction_session_timeout = '5min'`) reclaiming leaked pinned slots; (5) Cryptographically generated CSPRNG 32-bit `CancelKey` table in `pg-gateway` mapping client `(PID, Secret)` to live backend `(PID, Secret)` over `6PN` to cancel hung queries cleanly even in transaction mode.
9. **Architecture Changes:** Implement `CancelKey` registry, per-tenant wait semaphores, and bounded queues in `pg-gateway` (`internal/wire`) paired with PgBouncer/Session pools on Cells; expose queue wait time and rejections to Prometheus (`RISK-39`).
10. **Dependencies:** Protocol virtualization (`RISK-11`), Memory math (`RISK-09`), Gateway DoS caps (`RISK-23`), Wake-up storm coalescing (`RISK-36`).
11. **Trade-Offs:** Bursts exceeding `200` concurrent queued clients per tenant fail fast with `53300`, protecting neighboring tenants and Gateway memory at the cost of requiring standard client retry-with-backoff above plan concurrency.
12. **Security Implications:** Per-tenant queue limits isolate connection-flood DoS attacks cleanly inside Tenant A without exhausting global Cell FDs or delaying Tenant B connections.
13. **Failure Recovery Strategy:** Client disconnects while waiting in queue cancel `context.Context` immediately, releasing queue slot cleanly; crashed backend connections automatically clear from backend semaphore and fail pending query once with `08006` (never double-executing).
14. **Validation Method:** `EXP-B5` (500/1,000 concurrent connections across Tenant A while Tenant B executes `pgbench`) and `EXP-E2` (`CancelRequest` + pool timeout verification).
15. **Acceptance Criteria:** `0` `FATAL: sorry, too many clients already` backend errors during 1,000-client connection storms; Tenant B latency variance `<10%` during Tenant A connection flood; `100%` `CancelRequest` propagation accuracy.
16. **Remaining Uncertainty:** Real Gateway memory/FD behavior under 10,000 simultaneous half-active pooled TLS sockets on Fly `performance-2x`/`4x` Gateways (`EXP-E2`, `UQR-09`).

### RISK-13: XFS and Fly Volume Compatibility
1. **Risk ID & Title:** `RISK-13` — XFS and Fly Volume Compatibility
2. **Severity:** `P1`
3. **Root Cause:** Early designs assumed Fly.io Volumes provide **XFS with reflink/CoW (`FICLONE`)** and multi-Cell attachment, and treated a fixed 80 GB volume size as universal. In reality, Fly Volumes are local NVMe **`ext4`** filesystems attached 1:1 to a single physical host Machine, cannot shrink once expanded, do not expose XFS `FICLONE` out of the box, and pack container root filesystems (`/`) onto small ephemeral storage separate from `/vol`.
4. **Failure Scenario:** Deploying code calling `FICLONE` fails immediately with `EOPNOTSUPP`; or writing `pg_basebackup`/`pg_combinebackup` staging to `/tmp` fills the small ephemeral `/` rootfs causing `ENOSPC`; or provisioning an oversized 500 GB volume leaves 450 GB idle permanently billed at `$0.15/GB-month` (`$67.50/mo` wasted) because volumes cannot shrink. Additionally, physical host failure temporarily renders that single-attached Fly Volume unreachable until Fly migrates/replaces or standby/R2 recovers elsewhere.
5. **Technical Explanation:** According to official [Fly.io Volumes documentation](https://fly.io/docs/volumes/overview/): Fly Volumes are encrypted NVMe block slices attached to a single physical Fly worker host formatted as `ext4` by default. They **cannot** be shared across multiple active Machines simultaneously (ruling out shared-disk active-active multi-Cell mounts), **cannot** shrink once extended via `fly volumes extend`, cost `$0.15/GB-month` provisioned (even when attached to a stopped Machine), and retain snapshot backups (`$0.08/GB-month` stored, first 10 GB/mo free). Crucially, inside Fly Firecracker microVMs, the guest kernel (`fly-kernel`) may omit optional kernel features such as `CONFIG_QUOTA` (`prjquota`) or `CONFIG_BLK_DEV_LOOP` (`/dev/loop*`), making runtime boot probing mandatory before relying on kernel quota enforcement.
6. **Industry-Standard Solutions:**
   - Treat single-attached Fly NVMe `ext4` as fast local persistent Primary Cell cache/storage, paired strictly with **Cross-Zone R2 backups or Physical Standbys** (`RISK-03`) for durability beyond single-host loss.
   - Strict rootfs `/` vs `/vol` path isolation + workload-tiered volume sizing (`20 GB` -> `80 GB` -> `200 GB`) grown dynamically as utilization approaches 70%.
3. **Solution Comparison:**
   - *Option A — Attempt raw block volume or nested XFS-on-loopback file inside Fly `ext4`:* Requires `CONFIG_BLK_DEV_LOOP` / privileged mount support inside Firecracker (often absent or adds 5–10% double-filesystem `fsync`/metadata penalty)—**risky/unproven** until Stage 0 check.
   - *Option B — Recommended (`ADR-002`, `ADR-010`): Native Fly `ext4` + Strict `/vol` Separation + Stage 0 Empirical Probing:* Uses Fly's native `ext4` directly with zero double-filesystem write penalty, tests kernel flags (`prjquota`, `/dev/loop`) in Stage 0 via `envprobe`, and scales volume sizes upward incrementally (`20 -> 80 -> 200 GB`) because shrinking is impossible.
8. **Recommended Design (`ADR-010`):** Standardize strictly on native Fly **`ext4`**. Isolate paths: configure `TMPDIR=/vol/tmp` globally; store `/vol/pool`, `/vol/staging`, `/vol/tenants`, and `/vol/.cell_ballast` exclusively on `/vol`; place Unix domain sockets on a small `16m` `tmpfs` (`/run/pg`). In **Stage 0.1**, execute `internal/cell/envprobe` on live Fly Firecracker hardware to measure and document empirically: exact `findmnt` flags (`prjquota` support), `/dev/loop*` availability, `pg_test_fsync` p50/p99 latency, `fio` random/seq IOPS, Machine replacement volume retention, snapshot restore time, and online `fly volumes extend` behavior. Use stepped SKU volumes rather than one arbitrary 80 GB constant.
9. **Architecture Changes:** Implement `internal/cell/envprobe`; remove all XFS assumptions and multi-Cell shared-volume access assumptions; enforce `TMPDIR=/vol/tmp` in `Dockerfile.cell` and `fly.cell.toml`.
10. **Dependencies:** Stage 0 live Fly PoC (`EXP-A1`), backup staging sizing (`RISK-02`), quotas (`RISK-17`).
11. **Trade-Offs:** Sacrifices instant cross-tenant CoW cloning (`FICLONE`) and shrinks cannot happen in place (requiring tenant live migration to a new smaller-volume Cell if a Cell drains down significantly).
12. **Security Implications:** Fly encrypts volumes at rest at the infrastructure/host layer; per-tenant `0700` UID isolation + envelope-encrypted R2 backups protect tenant data confidentiality above the block layer.
13. **Failure Recovery Strategy:** If a Fly worker host dies completely (making local `ext4` volume offline beyond `12s` safety window / Pro failover), Control Plane declares Cell failed (`RISK-19`) and recovers Pro tenants via unique-zone Standby (`RPO=0` scoped) and Standard tenants via Cross-Cell R2 restore (`RPO<=5s`), cleaning up orphaned old volumes once Fly recovers host.
14. **Validation Method:** **Stage 0.1 Live Hardware Benchmark (`EXP-A1`, `EXP-D4`)** (`envprobe`, `pg_test_fsync`, `fio`, `fly machine replace`, snapshot restore, `fly volumes extend`).
15. **Acceptance Criteria:** Verified empirical Stage 0 report on real Fly hardware documenting `ext4` mount options, `fsync` p99 (`<5ms` target check), volume persistence across Machine replacement, and verified `prjquota` vs zero-module fallback path.
16. **Remaining Uncertainty:** Fly's exact guest `fly-kernel` configuration (`CONFIG_QUOTA`, `CONFIG_BLK_DEV_LOOP`, `cgroup v2` controllers) and live NVMe `pg_test_fsync` tail latency under shared Fly worker noise (`UQR-01`, `UQR-03`).

### RISK-14: Storage Accounting & CoW Space Tracking
1. **Risk ID & Title:** `RISK-14` — Reflink / Volume Storage Accounting
2. **Severity:** `P1`
3. **Root Cause:** Measuring database size via SQL (`pg_database_size()`) misses `pg_wal/`, `pg_wal/summaries/`, `base/pgsql_tmp/`, backup staging dirs, and **open-unlinked files** (deleted files still held open by an active query or crashed backend); meanwhile, naive `filepath.Walk` scans `O(N)` files slowly and double-counts shared extents if CoW/reflinks are ever introduced post-Stage-3.
4. **Failure Scenario:** A tenant executes a runaway sort creating a 4 GB temporary file in `base/pgsql_tmp/` and unlinks or crashes mid-query while holding the file descriptor, or accumulates 2 GB of `pg_wal` behind a stalled slot. `pg_database_size()` reports 80 MB while `df /vol` approaches 100%, tripping global Cell `ENOSPC` without billing or attributing the offender.
5. **Technical Explanation:** In POSIX filesystems (`ext4` and `XFS`), unlinking an open file removes its directory entry (making `du` and `filepath.Walk` blind to it) while its allocated blocks remain pinned until the final FD closes. Only filesystem-level accounting—specifically Linux **`ext4` Project Quotas (`PRJQUOTA` queried via `quotactl(Q_GETQUOTA)`)** or tracking open `/proc/<pid>/fd` + `/proc/<pid>/io` `write_bytes` deltas—sees physical block consumption including `pg_wal`, `pgsql_tmp`, and open-unlinked files in `O(1)` time. Should CoW reflinks ever be revisited in Stage 3+ on custom hosts, physical tracking must additionally parse shared (`FIEMAP_EXTENT_SHARED`) vs exclusive extent ownership rules to avoid billing N tenants 100% each for shared base blocks.
6. **Industry-Standard Solutions:**
   - Kernel Project Quota accounting (`quotactl`) per tenant directory (`chgrp` / `chattr +P -p <projid>`).
   - Dual accounting (logical `pg_database_size()` for customer SQL metrics + physical block quota `quotactl` reconciled continuously against `df`).
8. **Recommended Design (`ADR-010`):** Eliminate CoW reflink accounting complexity from Stages 0–2 (`ext4` non-shared independent clusters). Track **two metrics**: (1) Logical DB size via `pg_database_size()` (for developer UX dashboards), and (2) Physical allocated blocks covering the entire `/vol/tenants/{id}` tree (including `pg_wal`, `summaries`, `pgsql_tmp`) via `O(1)` **`quotactl` `PRJQUOTA`** queries (when `envprobe` confirms kernel support) or periodic `statfs` + directory block walk + `/proc/<pid>/io` `write_bytes` delta checks (when `prjquota` is absent). Run a 60-second Cell reconciler comparing `sum(tenant_physical_bytes) + pool_bytes + staging_bytes` against `df /vol` (`statvfs`); flag any drift `>2%` as leaked open-unlinked descriptors or orphaned staging directories. Defer Stage 3+ CoW shared-extent accounting strictly to future R&D.
9. **Architecture Changes:** Add `PRJQUOTA` `quotactl` reader + 60s `df`-vs-sum reconciler inside `pg-cell-agent`; explicitly remove Stage 0–2 XFS CoW accounting code.
10. **Dependencies:** Fly `ext4` `envprobe` verification (`RISK-13`), hard quota enforcement (`RISK-17`), monitoring metrics (`RISK-39`).
11. **Trade-Offs:** Billing/enforcing quotas on physical `PGDATA` + `pg_wal` + temp files rather than just `pg_database_size()` prevents hidden storage abuse (`pg_wal`/`pgsql_tmp`) at the cost of counting transient WAL/VACUUM bloat temporarily against tenant limits (buffered by soft-warn vs hard-block headroom).
12. **Security Implications:** Closes storage exhaustion bypasses where a malicious tenant intentionally creates huge unlinked temp files or dead tuples to hide physical disk use from logical SQL monitors.
13. **Failure Recovery Strategy:** If 60s `df` reconciler discovers `>2%` unaccounted physical block growth traced to open unlinked files inside a runaway/crashed process, terminate the offending query/backend (`pg_terminate_backend`) and alert operations; purge orphaned `/vol/staging/*` entries.
14. **Validation Method:** `EXP-C3` (Open-unlinked file write test, huge temp spill + transaction abort, WAL accumulation test comparing `quotactl` + 60s reconciler vs `df`).
15. **Acceptance Criteria:** `O(1)` physical disk usage accounting matches real `df` consumed blocks within **`<2%`** across temp spills, WAL bursts, and open-unlinked file tests.
16. **Remaining Uncertainty:** Availability of `CONFIG_QUOTA` / `prjquota` on Fly.io's stock guest kernel (`UQR-01`); if unavailable, loop-device vs `/proc/<pid>/io` delta precision verification needed (`EXP-C3`).

### RISK-15: Cloudflare R2 Reliability, Atomicity & Backup Validation
1. **Risk ID & Title:** `RISK-15` — Cloudflare R2 Reliability & Backup Validation
2. **Severity:** `P1`
3. **Root Cause:** Treating an HTTP `200 OK` upload response from Cloudflare R2 as proof of a recoverable PostgreSQL backup ignores broken parent-incremental chains, missing WAL/history segments, unverified file checksums, lost encryption keys, leaked uncompleted multipart parts, concurrent `manifest.json` races, and subtle S3-API conditional-header semantics on multipart completions.
4. **Failure Scenario:** A Cell loses connectivity midway through a 5 GB multipart base backup upload (leaking orphan parts billed forever). Simultaneously, two failover Cells update `tenants/{id}/manifest.json` with out-of-order `If-Match` expectations or omit a conditional check, overwriting newer valid backup references with an old chain whose parent WAL was GC'd—only discovered months later when a restore attempt fails fatally.
5. **Technical Explanation:** According to official [Cloudflare R2 documentation](https://developers.cloudflare.com/r2/): (1) R2 guarantees **strong read-after-write consistency** globally for `PutObject`, `DeleteObject`, and `ListObjects`. (2) Conditional headers (`If-None-Match: "*"`, `If-Match`) are evaluated **atomically** on `PutObject` and `CompleteMultipartUpload`, returning `412 PreconditionFailed` to losing concurrent writers (and automatically aborting the losing `CompleteMultipartUpload` upload ID, whose parts are reclaimed); *crucially*, conditional headers placed on `CreateMultipartUpload` are **not** re-evaluated at completion, and every `412` failure plus all uploaded parts **still count as billable Class A operations**! (3) Furthermore, object checksums (`SHA-256` / `MD5`) prove transport integrity of *one object*, not PostgreSQL cross-file consistency, which requires verifying the entire backup directory via **`pg_verifybackup`**, confirming parent-base/WAL continuity (`RISK-16`), and confirming envelope DEK decryption unwrapping.
6. **Industry-Standard Solutions:**
   - R2/S3 Bucket Lifecycle rule auto-aborting incomplete multipart uploads (`AbortIncompleteMultipartUpload` at `1 day`), paired with Control Plane metadata tracking + object immutability.
   - Multi-gate Two-Phase Backup Publish (checksum + `pg_verifybackup` + DEK unwrap + WAL continuity -> atomic CAS `manifest.json` backed by Control Plane PostgreSQL catalog).
   - Automated scheduled **clean-room restore drills** verifying recoverability continuously with `pg_amcheck`.
7. **Solution Comparison:**
   - *Option A — Rely solely on S3/R2 `PutObject` `200 OK` + ETag verification:* Leaves silent broken incremental chains, missing `.history` files, unrecoverable DEKs, and leaked multipart parts—**rejected**.
   - *Option B — Recommended (`ADR-002`): Two-Phase Verified Publish + Control Plane Catalog Authoritative Index + Automated Restore Drills:* Verifies `pg_verifybackup` + DEK unwrap + WAL continuity locally prior to R2 manifest publication (`If-Match` CAS + Control DB transaction), auto-aborts failed multiparts after 24h, and runs weekly clean-room restores.
8. **Recommended Design (`ADR-002`):** Configure R2 Bucket Lifecycle to abort incomplete multipart uploads after `24 hours`. Before marking any backup `VERIFIED` in `manifest.json` and Control Plane Postgres `backups` table: (1) Run `pg_verifybackup` on the staged backup directory/stream against its SHA-256 `backup_manifest`; (2) Test unwrapping/decrypting the header with the tenant's KMS-wrapped DEK; (3) Verify continuous parent backup linkage (`base -> incr_1..N`) and unbroken WAL segment continuity (`min_wal_seg .. end_lsn`) + `.history` files; (4) Publish immutable backup objects first (`If-None-Match: "*"`), then CAS-update `manifest.json` using **`If-Match: "<etag>"`** (mirroring authoritatively in Control Plane HA Postgres `backups` table so R2 CAS never stands alone). Run a weekly clean-room automated drill restoring sampled backups to isolated verifier Cells and executing `pg_amcheck`. Empirically validate R2 `CompleteMultipartUpload` conditional headers across target Fly regions in Stage 0.2.
9. **Architecture Changes:** Build `internal/storage/r2` implementing envelope crypto, explicit `If-Match`/`If-None-Match` conditional checks, multipart error abort cleanup (`AbortMultipartUpload` immediately on error rather than waiting 24h), and weekly clean-room restore job in `lifecycle-freeze-queue`.
10. **Dependencies:** PG17 `pg_verifybackup` (`RISK-02`), envelope KMS/DEK (`RISK-24`), PITR WAL tracking (`RISK-16`), Control DB (`RISK-32`).
11. **Trade-Offs:** Waiting for local `pg_verifybackup` + WAL continuity check + weekly clean-room restore Cells adds modest CPU/compute cost in exchange for mathematical confidence that published backups actually restore; failed conditional CAS ops still pay Class A op costs if two writers race (minimized by epoch fencing + Control DB locks).
12. **Security Implications:** Envelope AES-256-GCM DEK encryption protects backups at rest even against raw bucket credential leaks; strict prefix scoping (`tenants/{id}/`) prevents cross-tenant key reads.
13. **Failure Recovery Strategy:** On mid-multipart upload network failure, client calls `AbortMultipartUpload` immediately and schedules retry with exponential backoff (with R2 24h lifecycle rule as safety net). If `pg_verifybackup` fails, discard staging artifact cleanly, trigger full backup retry, and alert operations.
14. **Validation Method:** `EXP-D4` (Stage 0.2 R2 conditional race test + byte-flip corruption test + mid-upload abort test) and `EXP-D5` (Clean-room empty-Cell restore + `pg_amcheck`).
15. **Acceptance Criteria:** `100%` deterministic `412 PreconditionFailed` enforcement validated in Stage 0.2 on both single-PUT and `CompleteMultipartUpload`; `100%` rejection of tampered/incomplete chains before `VERIFIED` status; `0` orphan multipart uploads >24h; `100%` pass rate on weekly `pg_amcheck` restore drills.
16. **Remaining Uncertainty:** Real R2 `CompleteMultipartUpload` throughput/tail-latency variance across Fly regions (`iad`, `ewr`, `lhr`, `sin`) under concurrent multi-GB backup bursts (`EXP-D4`, `UQR-03`).

### RISK-16: Point-in-Time Recovery (PITR)
1. **Risk ID & Title:** `RISK-16` — Point-in-Time Recovery (PITR)
2. **Severity:** `P1`
3. **Root Cause:** PITR fails silently whenever WAL archiving omits `.history` timeline files created during failovers/promotions, deletes old WAL segments or base backups needed by downstream incremental chains during retention GC, or fails to record exact `min_required_wal_seg` (`START WAL LOCATION` -> `STOP WAL LOCATION`) boundaries per backup.
4. **Failure Scenario:** Tenant Pro fails over on Tuesday (`Timeline 1 -> Timeline 2`). On Wednesday an engineer runs `DROP TABLE orders;`. Recovery is requested for `Wednesday 14:05 UTC`, restoring Tuesday morning's base backup (`Timeline 1`). Because `00000002.history` was skipped by the WAL uploader or expired prematurely by naive age-based GC (`delete WAL older than 7d`), PostgreSQL refuses to switch to Timeline 2 (`requested timeline 2 is not a child of this server's history`) -> unrecoverable PITR failure.
5. **Technical Explanation:** According to [PostgreSQL Continuous Archiving docs](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-TIMELINES): Every archive recovery / `pg_promote()` increments PostgreSQL's `TimeLineID` and creates `<tli>.history` recording exact parent-timeline switch-point LSNs. Without `.history` files in `restore_command` (`%f`), PG cannot traverse timeline forks. Additionally, restoring a PG17 incremental backup requires the complete root `base` plus *every* sequential `incr` up to the chosen restore point, *plus* every WAL segment from the chosen backup's `start_lsn` (`CHECKPOINT LOCATION` / `backup_label`) cleanly across all timeline switches up to `recovery_target_time` / `recovery_target_lsn`. Age-based deletion of base backups or old WAL breaks later dependent chains unless GC performs a full dependency-graph reference count.
6. **Industry-Standard Solutions:**
   - Graph/dependency-aware backup retention catalogs (`pgBackRest`, `WAL-G`, `Barman`) pinning every base backup, incremental child, `.history`, and WAL range until the entire chain's recovery window expires.
   - Isolated clone-into-new-directory PITR (`recovery_target_action = 'promote'`) avoiding destructive overwrite of production `PGDATA`.
7. **Solution Comparison:**
   - *Option A — Naive time-based TTL deletion (`7-day bucket lifecycle rule`):* **Fatal flaw**—expires the 8-day-old full base backup while day-2 incremental backups or active WAL tails still depend on it!
   - *Option B — Recommended (`ADR-002`): Dependency-Graph Catalog Retention GC + `.history`-Complete Archival + Clean-Room Target Clone Restore:* Stores every timeline history file (`{tli}.history`) alongside WAL segments in R2, tracks exact LSN/timeline dependency intervals in Control Plane HA Postgres + `manifest.json`, never applies raw R2 blind time-TTL expiry directly on active chains, and always restores PITR into a new isolated Cell slot.
8. **Recommended Design (`ADR-002`):** Record `(backup_id, parent_id, type[FULL|INCR], timeline_id, start_lsn, end_lsn, start_time, end_time, min_wal_seg, max_wal_seg, status)` in Control DB + `manifest.json`. Archive `.history` files synchronously alongside WAL segments immediately upon creation/promotion (`pg_receivewal` + archive hook). Retention GC (`lifecycle-freeze-queue`) walks the dependency DAG backwards from the retention horizon, marking objects `EXPIRED` only when *zero* live incremental chains or PITR windows cover them. PITR restores into a fresh `/vol/tenants/{clone_id}` staging dir (`>=2.2x` target size): download + extract full/incr chain -> `pg_combinebackup` -> `pg_verifybackup` -> configure `recovery.signal`, `restore_command` (fetching `.wal.zst` and `.history` from R2), `recovery_target_time`/`lsn`, `recovery_target_timeline = 'latest'`, `recovery_target_action = 'promote'` -> start isolated PG17, verify `SELECT pg_is_in_recovery() == false`, then cut over or expose cloned endpoint cleanly.
9. **Architecture Changes:** Add PITR dependency DAG metadata schema in Control Plane HA DB; ensure `pg_receivewal` archives `.history` files immediately; remove blind R2 age-based object expiration policies in favor of DAG-aware GC worker.
10. **Dependencies:** PG17 incremental/verify/combine workflow (`RISK-02`), R2 conditional & integrity gates (`RISK-15`), cross-Cell epoch fencing (`RISK-18`).
11. **Trade-Offs:** Retaining a parent base backup + WAL until the *newest* dependent incremental chain ages past the retention window increases effective R2 storage duration slightly (~1 base period extra, e.g., 8–14 days for a 7-day PITR window), which is trivial at `$0.015/GB-month`.
12. **Security Implications:** PITR clones preserve full tenant UID/namespace isolation (`RISK-05`) and rotate client DB credentials automatically upon clone activation; recovery SQL parameters are generated internally cleanly without SQL injection.
13. **Failure Recovery Strategy:** If a requested target timestamp hits a corrupted/missing WAL segment, recovery halts cleanly on the staging clone without touching the live corrupted source cluster, alerting operators and allowing safe recovery up to the last valid prior LSN/backup point.
14. **Validation Method:** `EXP-D5` & `EXP-D6` (`CREATE TABLE` -> insert T1 -> failover `TLI 1->2` -> insert T2 -> `DROP TABLE` -> PITR to T1.5 & T2.5 across `.history` boundary on an empty Cell).
15. **Acceptance Criteria:** `100%` exact row recovery before `DROP TABLE` across >=2 simulated timeline switches (`TLI 1 -> 2 -> 3`); `0` broken dependencies permitted during 30-day synthetic retention GC stress simulation.
16. **Remaining Uncertainty:** Exact restore RTO curve across 1 GB, 5 GB, and 20 GB datasets on Fly `ext4` + R2 parallel multipart download + `pg_combinebackup` (`EXP-D5`, `UQR-03`).

### RISK-17: Storage Quotas & Disk Exhaustion
1. **Risk ID & Title:** `RISK-17` — Storage Quotas and Disk Exhaustion
2. **Severity:** `P1`
3. **Root Cause:** Asynchronous directory polling every 30 seconds cannot stop a tenant executing a bulk `INSERT`/`CREATE INDEX`/unbounded temp spill from consuming 20–50 GB of WAL and heap files in under 10 seconds, filling the shared Cell NVMe volume to `100%` (`ENOSPC`) and freezing every co-located neighbor—and setting `default_transaction_read_only = on` alone does not halt autovacuum WAL, superuser maintenance, or in-flight temp files mid-execution.
4. **Failure Scenario:** Tenant A triggers `INSERT INTO t SELECT repeat('x', 4096) FROM generate_series(1, 10000000)` with a paused replication slot. Within 8 seconds, Tenant A writes 18 GB of heap + `pg_wal` segments before the 30s poller fires. Shared `/vol` hits `100%`; every neighbor Tenant B–Z hangs waiting on `CHECKPOINT` / WAL segment `open()` (`PANIC: could not write to log file: No space left on device`), crashing the entire Cell.
5. **Technical Explanation:** Synchronous write-path enforcement requires interception inside the kernel VFS allocation path or deterministic resource limits: Linux **`ext4` `PRJQUOTA`** (`chattr +P -p <project_id>` + `quotactl(Q_SETQUOTA)`) fails over-quota `write()`/`fallocate()` calls instantaneously inside kernel space with `EDQUOT` without affecting sibling projects. However, if Fly's guest kernel (`fly-kernel`) omits `CONFIG_QUOTA` (`UQR-01`) or `/dev/loop` (`CONFIG_BLK_DEV_LOOP`), a **zero-module kernel-adaptive defense** is essential: combining POSIX `setrlimit(RLIMIT_FSIZE)` (per-file cap preventing single huge relation/temp runaway), PostgreSQL hard query/WAL GUCs (`temp_file_limit`, `max_wal_size`, `max_slot_wal_keep_size`, `statement_timeout`), and a tight **1-second `/proc/<pid>/io` `write_bytes` poller** that trips read-only + `pg_terminate_backend()` within 1s, strictly paired with pre-allocated emergency ballast space on `/vol` so checkpoints never deadlock at 100%.
6. **Industry-Standard Solutions:**
   - **Kernel Project Quotas (`ext4 PRJQUOTA` / `XFS pquota`)** enforcing hard synchronous `EDQUOT` boundaries.
   - **Dedicated Per-Tenant Block Device / Loopback File (`dm-thin` / loop-ext4)** when directory project quotas aren't available.
   - **PostgreSQL Guardrails + Pre-allocated Emergency Ballast File** (`Supabase`/`RDS` emergency space reserve preventing 100% WAL deadlock).
7. **Solution Comparison:**
   - *Option A — 30s userspace `filepath.Walk` + SQL `read_only`:* Leaves huge 10s–30s `ENOSPC` runaway window and misses unlinked files—**rejected**.
   - *Option B — Always force per-tenant loopback ext4 image files:* Hard cap, **higher I/O amplification & double filesystem overhead** + requires `CONFIG_BLK_DEV_LOOP`.
   - *Option C — Recommended (`ADR-010`): Multi-Layer Defense — Kernel `ext4 PRJQUOTA` (`EDQUOT`) Primary + Zero-Module Fallbacks (`RLIMIT_FSIZE` + PG Bounds + 1s `/proc/<pid>/io`) + `2 GB` `.cell_ballast` + Cell Watermarks:* Enforces synchronous `EDQUOT` whenever Fly kernel permits (`envprobe`), falls back deterministically `<25 MB` overshoot if `prjquota` is absent, and reserves 2 GB emergency `/vol/.cell_ballast`.
8. **Recommended Design (`ADR-010`):** Layer 4 independent boundaries:
   1. **Kernel Write Boundary (`envprobe` adaptive):** When `prjquota` is available on `/vol`, assign unique `project_id` (`chattr +P -p <proj_id>`) per `/vol/tenants/{id}` and enforce hard block/inode limits via `quotactl` (`EDQUOT`). If Stage 0 `envprobe` shows Fly's `fly-kernel` omits both `CONFIG_QUOTA` and `/dev/loop`, enforce: `setrlimit(RLIMIT_FSIZE, 1GB)` via `SysProcAttr` + **1-second `/proc/<pid>/io` `write_bytes` watcher** setting `default_transaction_read_only = on` and running `pg_terminate_backend()` within 1s of breaching quota (bounding overshoot `<25 MB`, verified experimentally in `EXP-C3`).
   2. **PostgreSQL Native Limits:** `temp_file_limit = '256MB'`, `max_wal_size = '256MB'`, `wal_keep_size = '64MB'`, `max_slot_wal_keep_size = '256MB'` (critical: caps orphaned replication slot WAL buildup!), `statement_timeout = '10s'` (shared tier).
   3. **Cell-Level Reserve & Watermarks:** Pre-allocate a **`2 GB` `/vol/.cell_ballast`** file (`fallocate`). Admission control freezes new tenant placement at **`75%`** `/vol` usage; at **`85%`** triggers urgent scale-to-zero / Deep Freeze evictions or migrations; at **`92%`** sets top-growth unpinned tenants read-only and unlinks `.cell_ballast` strictly to guarantee space for clean `CHECKPOINT` / `DROP` / slot cleanup without global `ENOSPC`.
   4. **Quota Reset UX:** Even at hard quota, allow `DELETE`/`TRUNCATE`/`VACUUM FULL`/`DROP` via admin/maintenance endpoint so tenants aren't permanently wedged.
9. **Architecture Changes:** Add `PRJQUOTA`/`envprobe` fallback watchdog (`internal/cell/isolation`), mandatory PG GUCs in `postgresql.conf` generator, `.cell_ballast` initializer, and 75%/85%/92% watermarks in scheduler (`RISK-31`).
10. **Dependencies:** Stage 0 Fly kernel `envprobe` (`RISK-13`), storage accounting (`RISK-14`), Cell capacity placement (`RISK-31`), large-tenant promotion (`RISK-38`).
11. **Trade-Offs:** Reserving `25%` Cell volume headroom + `2 GB` `.cell_ballast` lowers usable billable GB per Fly Volume (~73% usable vs 100%)—explicitly modeled in Unit Economics (`Section 8`); tight `max_wal_size=256MB` trades slightly higher checkpoint frequency for deterministic WAL caps.
12. **Security Implications:** Stops malicious single-tenant disk exhaustion DoS from triggering global Cell outages across sibling tenants.
13. **Failure Recovery Strategy:** If Tenant A hits `EDQUOT` (or `53100`), Gateway translates cleanly to SQLSTATE `53100` (`disk full / quota exceeded`) with guidance to prune data or upgrade (`RISK-34`); Cell siblings remain 100% writable. Should Cell volume reach `92%`, freeing `.cell_ballast` buys immediate ~2 GB checkpoint runway while high-growth offender is throttled/migrated.
14. **Validation Method:** `EXP-C3` (Bulk `generate_series` insert flood + paused replication slot + runaway `CREATE INDEX` in Tenant A while Tenant B executes continuous `pgbench` transactions).
15. **Acceptance Criteria:** Tenant A halts cleanly at its exact quota (`EDQUOT` or `<25 MB` 1s fallback bound); Tenant B suffers `0` `ENOSPC` errors and `<5%` TPS dip; Cell volume never hits `100%`.
16. **Remaining Uncertainty:** Exact `CONFIG_QUOTA`/`prjquota` and `CONFIG_BLK_DEV_LOOP` kernel config status inside live Fly Firecracker microVMs (`EXP-A1` / `UQR-01`).

### RISK-18: Split-Brain and Epoch Fencing
1. **Risk ID & Title:** `RISK-18` — Split-Brain and Epoch Fencing
2. **Severity:** `P1`
3. **Root Cause:** Changing routing tables in `pg-gateway` within 500ms or checking lease tokens only in Control Plane APIs fails during asymmetric network partitions: an isolated old Primary Cell can still possess open TCP sockets from pre-partition Gateways, queued background HTTP workers, or delayed replication/backup jobs, allowing **two active primaries to commit writes simultaneously** (`split-brain`).
4. **Failure Scenario:** Network partition isolates Primary Cell #1 from Control Plane (while Gateway #2 still holds an established `6PN` socket to Cell #1 for 10 seconds, or an async HTTP `/v1/sql` request reaches Cell #1). Control Plane declares Cell #1 dead after 5s and promotes Standby Cell #2 at `epoch = 2`. For 5 seconds, both Cell #1 (`epoch = 1`) and Cell #2 (`epoch = 2`) commit conflicting `UPDATE balances` transactions locally. When connectivity returns, two diverged transaction histories exist—irreconcilable silent data corruption!
5. **Technical Explanation:** True distributed systems fencing (Kleppmann / Stonith principles) requires enforcement **at the actual storage/commit boundary**, not merely at the outer router: (a) On **Pro Sync Tier**, because every commit requires `SyncRepWaitForLSN` from the synchronous standby, atomically advancing the fencing epoch and **reconfiguring/promoting the standby first** ensures the partitioned old primary *mathematically cannot satisfy `synchronous_standby_names` and stalls inside `COMMIT`* even if its CPU keeps running! (b) On **Standard Async Tier** (no standby quorum), preventing overlap during total partition requires a **strictly disjoint bounded lease timeout invariant**: `T_old_primary_self_fence < T_control_plane_promote` using monotonic local hardware/kernel clocks (`CLOCK_MONOTONIC` + Linux `softdog` watchdog, immune to NTP jumps). Specifically, if local agent forces `SIGKILL` cleanly at `8.0s` without Control Plane lease renewal while Control Plane forbids promotion until `12.0s` (`4.0s` clock-drift & scheduling safety margin), two writable primaries can never overlap in time—while backup/WAL uploaders independently attach monotonic `epoch` tags into `If-Match` manifest updates and R2 paths so stale epochs cannot overwrite newer R2 history.
6. **Industry-Standard Solutions:**
   - **Shared Storage SCSI-3 PR / NVMe Reservations / Consensus Quorum Fencing (`Patroni` + `etcd` + `watchdog`)**: Old primary self-fences via Linux `/dev/watchdog` hardware/softdog reset before `etcd` TTL expires.
   - **Quorum Witness Pre-Fencing (`Synchronous Standby` Promotion Order)**: Standby rejects old `walsender` / increments epoch *before* accepting read-write traffic.
8. **Recommended Design (`ADR-011`):** Implement dual write-boundary fencing tailored cleanly per tier:
   1. **Pro Sync Tier (`Pre-Promotion Standby Fencing`):** Control Plane HA Postgres increments `epoch` (`E -> E+1`) inside a serializable promotion lock -> sends `FenceAndPromote(epoch=E+1)` to Standby first (Standby closes/rejects old primary's replication connection and executes `pg_promote()`) -> even if old primary retains stale Gateway TCP connections, its PostgreSQL `COMMIT` path hangs forever on `SyncRepWaitForLSN` because zero sync standbys confirm `E`!
   2. **Standard Async Tier (`Monotonic Disjoint Lease + Watchdog Fencing`):** Primary Cell leases renew every `2.0s` over `6PN` against `CLOCK_MONOTONIC`. If `pg-cell-agent` fails to renew a lease for **`8.0s`**, `pg-cell-agent` locally flips Gateway socket refusal and executes **`SIGKILL`** on the tenant `postgres` postmaster (`+ Linux softdog` daemon safety watchdog rebooting VM if agent itself hangs past `8.5s`). Control Plane enforces a strict **`12.0s` minimum promotion delay** from last confirmed ACKed lease before promoting `E+1` on another Cell (`4.0s` safety buffer absorbs kernel scheduler jitter & GC pauses).
   3. **Storage/R2 Fencing:** Every R2 `manifest.json` CAS write (`If-Match`) and Control Plane status check carries monotonic `epoch`; any delayed upload from `epoch < current_epoch` is rejected/ignored (`EXP-D6`).
9. **Architecture Changes:** Add monotonic lease & `/dev/watchdog` / `softdog` fencing daemon in `internal/cell/supervisor`; add strict `12.0s` async promotion barrier and Pro pre-fence orchestration in `internal/control/epoch` and `failover`; isolate backup R2 prefixes cleanly by `epoch_{000001}`.
10. **Dependencies:** Control Plane HA Postgres CAS authority (`RISK-32`), Pro sync standby (`RISK-03`), failover hysteresis (`RISK-19`), R2 conditional checks (`RISK-15`).
11. **Trade-Offs:** Guarantees zero split-brain overlap by intentionally accepting a **minimum `12.0s` promotion wait** when a Standard Async primary disappears abruptly without an external witness—a mandatory safety trade-off unless upgraded to Pro Sync standby. Also assumes guest kernel scheduler stalls do not exceed `4.0s` simultaneously with Control Plane failure (`softdog` backstop).
12. **Security Implications:** Prevents partitioned/compromised stale Cells from silently overwriting authoritative R2 `manifest.json` or serving spoofed historical data to roaming clients.
13. **Failure Recovery Strategy:** When a partitioned/restarted old primary reconnects to Control Plane reporting stale `epoch < current_epoch`, Control Plane marks it **`FENCED_QUARANTINE`** immediately; all local tenant processes stay killed, un-archived dirty tails (if any) are quarantined for forensic inspection rather than blindly replayed onto `epoch E+1`, and the cluster is cleanly purged/resynced as a fresh standby.
14. **Validation Method:** `EXP-D6` (Asymmetric `iptables` network partition leaving old Primary accessible to test client while cutting Control Plane link during active `COMMIT` writes on both Pro and Standard tiers).
15. **Acceptance Criteria:** `0` divergent acknowledged transactions across 50 injected asymmetric network partitions (`Pro`: old primary blocks commit cleanly at `SyncRepWaitForLSN`; `Standard`: old primary terminates strictly `<8.1s` before new primary promotes at `>=12.0s`); `0` stale `manifest.json` overwrites.
16. **Remaining Uncertainty:** Exact behavior of Linux `softdog` watchdog inside Fly Firecracker guest kernels (availability of `/dev/watchdog` vs `CLONE_NEWUSER`/container privileges) and actual Firecracker hypervisor pause jitter tails under heavy host contention (`UQR-01`, `UQR-04`).

### RISK-19: Cross-Cell Failover & Partition Recovery
1. **Risk ID & Title:** `RISK-19` — Cross-Cell Failover
2. **Severity:** `P1`
3. **Root Cause:** Triggering failover from a single Gateway health probe causes false-positive failovers during transient CPU spikes, garbage collection pauses, or `6PN` jitter; promoting without distributed promotion locks risks concurrent failovers; and failing to handle incomplete WAL tails, R2 unavailability, or returning old primaries corrupts tenant continuity.
4. **Failure Scenario:** Gateway #1 experiences a brief 2s `6PN` micro-drop to Cell #1 while Control Plane can still reach Cell #1 cleanly. If Gateway triggers immediate failover while Gateway #2 simultaneously triggers another promotion on Cell #3, or R2 experiences a 503 during promotion, recovery leaves partial timeline branches, broken client retry duplicates, and inaccurate `1.2s failover` marketing claims.
5. **Technical Explanation:** Reliable distributed failover separates **detection**, **decision**, **fencing**, **promotion**, and **reconciliation**: (1) Multiple independent vantages (Control Plane prober + Gateway health signals) using **`3 consecutive 1s failures`** hysteresis distinguish transient GC/packet blips from genuine node/process death. (2) A single transactional **`SELECT ... FOR UPDATE` promotion lock** inside Control Plane's 3-node HA Postgres (`epochs` table) ensures at most one coordinator wins promotion for `(tenant_id, epoch)`. (3) Pro Sync promotion promotes the already-caught-up warm standby (`pg_promote()` + archive `.history`), whereas Standard Async recovery restores the latest verified R2 base/incr chain + latest archived `.wal.zst` onto a target Cell (explicitly bounding and documenting `RTO` empirically rather than guessing `1.2s`).
6. **Industry-Standard Solutions:**
   - Consensus leader-election + hysteresis quorum probing (`Patroni` TTL/retry loops, `RDS` multi-AZ witness).
   - Scoped, empirically benchmarked RTO SLOs categorized cleanly per recovery mode (Warm Pro Standby vs Cold Async R2 Restore).
7. **Solution Comparison:**
   - *Option A — Instant single-probe (<2s) automated failover:* High risk of flapping false positives during GC/network jitter and unverified `1.2s` RTO claims—**rejected**.
   - *Option B — Recommended (`ADR-011`): Multi-Vantage `3×1s` Hysteresis + Transactional Promotion Lock + Mode-Specific Recovery Targets:* Balances fast detection (3s confirmation) against zero false flips, uses fencing (`RISK-18`), handles degraded dependency matrices cleanly, and measures real RTO honestly.
8. **Recommended Design (`ADR-011`):**
   1. **Detection & Hysteresis:** Require `3 consecutive 1s` health failures across both Control Plane prober and reporting Gateways before marking Cell `SUSPECT`. Probe internal `PG` health vs `pg-cell-agent` liveness to distinguish slow SQL from dead VM.
   2. **Promotion Lock & Execution:** Control Plane worker acquires transactional `FOR UPDATE` row lock on `tenant_epochs` -> enforces Fencing (`RISK-18`) -> executes mode-specific failover:
      - **Pro Sync:** Confirm standby `flush_lsn >= last_known` -> execute `pg_promote()` -> publish Timeline `tli+1` `.history` -> update Gateways `epoch = E+1` -> provision replacement standby.
      - **Standard Async:** Wait mandatory `12.0s` safety window -> schedule healthy Cell -> restore verified R2 base/incremental chain + available WAL -> start PG (`epoch = E+1`).
   3. **Client Retry Idempotency Clarification:** Document explicitly that PostgreSQL failover cannot silently deduplicate **in-flight unknown-outcome commits** (`08006` connection dropped mid-`COMMIT`); applications using non-idempotent mutations must apply idempotency keys (`XID` or business key check) rather than blind driver auto-retry!
   4. **Dependency Degraded Matrix:** If R2 is unavailable during Pro failover, standby promotes cleanly directly from local NVMe (`pg_stat_replication`) buffering new `.history`/WAL locally until R2 recovers (`RISK-41`). If both standby AND R2 are completely dead/unreachable, hold tenant safely `UNAVAILABLE` (fail closed—never silently boot an empty DB!).
9. **Architecture Changes:** Build `internal/control/failover` state machine (`HEALTHY -> SUSPECT -> FENCING -> PROMOTING -> COMPLETED/ABORTED`), promotion lock schema, and multi-vantage health aggregator.
10. **Dependencies:** Epoch fencing (`RISK-18`), Sync standby/R2 durability (`RISK-03`, `RISK-15`), `6PN` network prober (`RISK-30`), Control Plane HA DB (`RISK-32`).
11. **Trade-Offs:** `3×1s` hysteresis + `12s` Async fencing puts realistic Async RTO into the `15s + R2 restore time` range (`~15–45s+` depending on DB size) and Pro warm-standby RTO in the `~4–8s` range—rejecting unverified `1.2s` claims in favor of real fail-safe correctness.
12. **Security Implications:** Returning old primaries are strictly blocked from re-attaching or serving stale data via Gateway mTLS `epoch` check (`epoch_mismatch -> terminate`); promotion actions generate immutable audit records.
13. **Failure Recovery Strategy:** If standby promotion fails mid-way (before `epoch = E+1` commits in Control DB), rollback promotion lock cleanly, probe whether old primary recovered health or select second standby/R2 path; if simultaneous regional outage hits all Cells in one region, hold read-only/unavailable cleanly until manual/automated cross-region Geo-DR playbook (`RISK-41`) executes.
14. **Validation Method:** `EXP-D2` (Standby failover & rollback under load), `EXP-D3` (Pro Sync vs Async full Cell `kill -9`, R2 temporary outage during failover, returning stale primary rejoin test).
15. **Acceptance Criteria:** `0` false-positive failovers under 2s synthetic `6PN` packet loss (`tc netem`); `0` concurrent dual promotions across 20 injected simultaneous trigger races; empirically measured p50/p95/p99 Pro and Async RTO documented.
16. **Remaining Uncertainty:** Real end-to-end Pro `pg_promote()` + Gateway route propagation latency (`4–8s` target hypothesis) and cross-Cell cold R2 download + PG recovery speed under multi-GB databases on live Fly hardware (`UQR-03`, `UQR-04`).

### RISK-20: Live Tenant Migration
1. **Risk ID & Title:** `RISK-20` — Live Tenant Migration
2. **Severity:** `P1`
3. **Root Cause:** Migrating a live tenant across Cells via naive directory copy (`rsync`/`tar`) misses concurrent dirty writes/LSNs; logical replication fails on DDL (`ALTER TABLE`, `CREATE INDEX`), sequences, unlogged tables, and extensions; and naive cutovers leave long-running transactions, `prepared_xacts`, or active slots behind causing brief dual-writer windows.
4. **Failure Scenario:** Tenant grows past shared-Cell limits (`RISK-38`) and is scheduled for live promotion to a Dedicated Cell. Using `pg_dump` or logical replication drops DDL `ALTER TABLE` added mid-sync or misses `nextval()` sequences, causing duplicate primary key failures after DNS/Gateway switchover—or source stays briefly writable while slow clients finish transactions, losing post-cutover inserts.
5. **Technical Explanation:** PostgreSQL Physical Streaming Replication transmits byte-identical WAL blocks covering all DDL, sequences, views, extensions, roles, and heap/index updates sequentially with exact LSN determinism (`replay_lsn`). Therefore, migrating across identical PostgreSQL major versions (`PG 17 -> PG 17`) via `pg_basebackup` + physical replication slot + coordinated Gateway `DRAINING` cutover + `pg_promote()` preserves 100% binary schema/sequence fidelity—provided replication lag converges `<64 KB`, `max_slot_wal_keep_size` prevents orphaned migration slots from filling source disk (`RISK-17`), and source is fenced *before* target executes `pg_promote()`. (Note: Major version upgrades like `PG 17 -> PG 18` cannot use physical streaming and instead require planned logical-replication cutover windows.)
6. **Industry-Standard Solutions:**
   - **Physical Streaming Replication + Coordinated Proxy Pause + `pg_promote()`** (`RDS` Blue/Green / Instance Resize, `CloudNativePG` Switchover).
   - **Cold Quiesce + R2/Snapshot Restore** (for small/sleeping tenants where a few seconds of downtime is invisible).
7. **Solution Comparison:**
   - *Option A — Logical Replication (`pgoutput`) live migration:* Supports major version jumps, **breaks seamlessly on DDL, unlogged tables, and sequence skew** without fragile event triggers—**rejected for intra-version Cell balancing/promotion**.
   - *Option B — Recommended (`ADR-011`): Physical Streaming Replication Cutover (`PG17 -> PG17`) + Cold Fallback for Sleeping DBs:* 100% DDL/sequence/extension faithful, clean instant rollback pre-cutover, zero dual-primary window via Gateway `DRAINING` + Epoch fence.
8. **Recommended Design (`ADR-011`):** Keep source and target Cells on matched PG17 major binaries: (1) If tenant is `STOPPED` (sleeping), fast cold R2 or direct Cell-to-Cell copy safely migrates offline cleanly; (2) If tenant is `ACTIVE`: target Cell streams `pg_basebackup` over `6PN` mTLS into `/vol/tenants/{id}` and starts as a physical standby consuming a bounded source slot (`max_slot_wal_keep_size = '256MB'`). (3) Control Plane waits for `pg_wal_lsn_diff(flush_lsn, replay_lsn) < 64 KB`, zero active long transactions >5s, and `pg_prepared_xacts == 0`. (4) Gateway places tenant into brief `DRAINING` admission pause (holding new incoming queries cleanly in memory). (5) Source executes `CHECKPOINT` / final WAL flush -> target verifies `replay_lsn == source_flush_lsn` -> Control DB atomically advances `epoch++` & updates owner Cell -> source drops/stops (`agent.lock` released & frozen read-only/stopped) -> target calls `pg_promote()` & archives timeline `.history` -> Gateway switches route & releases buffered clients -> source slot & stale dir purge after 24h verification grace.
9. **Architecture Changes:** Build `internal/control/scheduler` live migrator state machine (`SYNCING -> CONVERGED -> DRAIN_PAUSE -> PROMOTED -> CLEANUP/ABORTED`); add bounded replication slot guard inside source `pg-cell-agent`.
10. **Dependencies:** Physical replication over `6PN` (`RISK-03`, `RISK-30`), Gateway pause/drain barrier (`RISK-07`), Epoch fencing (`RISK-18`), large-tenant detector (`RISK-38`).
11. **Trade-Offs:** Requires matched PostgreSQL major versions across Cells (cross-major-version upgrades need a distinct logical upgrade pipeline); bulk initial `pg_basebackup` consumes source NVMe read bandwidth throttled via `--max-rate`.
12. **Security Implications:** Replication credentials generated ephemerally per migration over mutually authenticated `6PN` TLS (`hostssl replication`), revoked immediately on cutover/abort.
13. **Failure Recovery Strategy:** If target fails before `epoch++` commits: Control DB aborts migration, source drops temporary replication slot immediately cleanly freeing WAL retention, and traffic never pauses. If source fails mid-sync before cutover: abort migration and run standard failover (`RISK-19`).
14. **Validation Method:** `EXP-E1` / Migration Stress Test (Active `pgbench` client running concurrent `CREATE INDEX CONCURRENTLY`, `ALTER TABLE ADD COLUMN`, `nextval()`, plus injected pre-cutover target crash and source crash).
15. **Acceptance Criteria:** `0` lost committed rows or sequence duplicates across concurrent DDL migrations; cutover read/write pause `<500ms` measured at client (hypothesis to validate in Stage 2); `100%` clean slot cleanup on injected mid-sync aborts.
16. **Remaining Uncertainty:** Real pause duration `<500ms` under heavy dirty-page flush (`CHECKPOINT`) prior to final LSN sync on loaded Fly `ext4` volumes (`UQR-08`).

### RISK-21: Process and Operating System Isolation
1. **Risk ID & Title:** `RISK-21` — Process and Operating System Isolation
2. **Severity:** `P1`
3. **Root Cause:** Multi-tenant OS processes running on a shared VM without isolated UIDs, mount roots (`pivot_root`), PID visibility separation, network egress blocks, capability stripping, and syscall filtering allow compromised SQL/extension processes to inspect `/proc`, traverse `/vol/tenants/*`, read `/sys/fs/cgroup`, tamper with `/run/pg` sockets, or attack host management interfaces.
4. **Failure Scenario:** A tenant runs a malicious dynamic exploit or reads `/proc/1/environ` / `/vol/tenants/{victim_id}/pgdata/base/...` via symlink traversal, or sends HTTP requests over `6PN` to internal Cell metrics endpoints or another tenant's Unix socket if permissions permit.
5. **Technical Explanation:** Linux namespaces isolate kernel resource views per process tree: `CLONE_NEWPID` confines `/proc` purely to the tenant's own `postmaster` + children (`PID 1..N` inside jail); `CLONE_NEWNS` + `pivot_root` binds only `/usr/lib/postgresql/17` (`ro`), `/vol/tenants/{id}/pgdata` (`nosuid,nodev,noexec`), a private `/dev/shm` (`tmpfs`), and minimal `/dev`/`/etc` stubs—making sibling `/vol/tenants/*`, `/sys/fs/cgroup`, and agent binaries non-existent in that VFS namespace; `CLONE_NEWNET` leaves only `127.0.0.1`/`::1` loopback (`socket(AF_INET)` to external/6PN hosts returns `ENETUNREACH`); `PR_SET_NO_NEW_PRIVS = 1` + `CapBnd = 0` strips all root privileges; `seccomp-bpf` drops dangerous syscalls (`ptrace`, `bpf`, `mount`, `unshare`, `clone(NEWUSER)`, `kexec_load`). Bind-mounting `/run/pg/{id}/.s.PGSQL.5432` exposes **only** that tenant's Unix socket outside into Gateway bridge ACLs (`0700` owned per tenant/bridge GID). Note: AppArmor/SELinux profiles may not be compiled/loaded inside stock Fly Firecracker kernels (`envprobe` checks on boot—never rely on unverified LSM assumptions alone).
6. **Industry-Standard Solutions:**
   - OCI/runC-grade Linux namespace containment + `seccomp-bpf` + non-root UID + `pivot_root` (`Docker`/`containerd` isolation primitives applied deterministically per PG process without daemon overhead).
   - Dedicated Firecracker microVMs per tenant for high-compliance workloads.
7. **Solution Comparison:**
   - *Option A — Run full Docker/containerd containers inside Fly VM:* Nested container daemon overhead (`containerd` + overlayfs on top of Firecracker `ext4`), potential systemd/cgroup conflicts under Fly `/init`—**avoided**.
   - *Option B — Recommended (`ADR-005`): Direct Go `syscall.SysProcAttr` + `pivot_root` + `seccomp-bpf` Per-Tenant Jail:* Zero container-daemon overhead (<3ms setup), works cleanly under Fly `/init`, directly configures `CLONE_NEWNS/PID/IPC/NET`, UID `10000+slot`, `no_new_privs`, `CapBnd=0`, and `seccomp-bpf`.
8. **Recommended Design (`ADR-005`):** Isolate every tenant `postgres` process via `internal/cell/isolation`: unique non-root UID `10000+slot`, `0700` `PGDATA`; private `CLONE_NEWNS` + `pivot_root` exposing solely read-only PG17 libs/bins + private `/tmp` (`nosuid,nodev,noexec`) + private `64m` `/dev/shm` `tmpfs` + own `PGDATA`; `CLONE_NEWPID` hiding host processes; `CLONE_NEWIPC` isolating SysV/POSIX memory; loopback-only `CLONE_NEWNET`; `CapBnd=0` + `PR_SET_NO_NEW_PRIVS=1`; strict `seccomp-bpf` allowlist. Run `envprobe` at boot to check namespace/`seccomp`/AppArmor availability inside Fly guest kernel and refuse startup (fail closed!) if core namespaces or `seccomp` fail initialization. Validate all inputs passed from Control Plane into `pg-cell-agent` cleanly via strict regex/path sanitization (`filepath.Rel` traversal guard) so tenant IDs or GUCs cannot inject paths/flags into `pg-cell-agent`.
9. **Architecture Changes:** Build `internal/cell/isolation` pre-exec Go re-exec wrapper setting namespaces, `pivot_root`, `seccomp-bpf`, UIDs, and socket bind-mounts cleanly prior to `execve("/usr/lib/postgresql/17/bin/postgres")`.
10. **Dependencies:** Failure-domain & security boundaries (`RISK-05`), `envprobe` boot check (`RISK-13`), PG role isolation (`RISK-10`, `RISK-22`).
11. **Trade-Offs:** Maintaining custom Go `pivot_root` chroot layouts and `seccomp-bpf` syscall allowlists adds careful testing effort whenever PostgreSQL minor releases or allowlisted extensions update (`Dockerfile.cell` integration test required every release).
12. **Security Implications:** Blocks arbitrary socket egress (`6PN` SSRF), sibling filesystem traversal, `/proc` secret leakage, `ptrace` inspection, and container-escape syscalls (`unshare`, `bpf`, `mount`).
13. **Failure Recovery Strategy:** If namespace or `seccomp` initialization fails on an incompatible kernel/node, fail closed cleanly (do NOT fall back to running un-isolated `postgres`), mark Cell `UNHEALTHY`, and evacuate tenants (`RISK-19`).
14. **Validation Method:** `EXP-C1` (Adversarial exploit harness run inside spawned tenant context inspecting `/proc`, `/sys`, `/vol`, UIDs, `CapEff`, `seccomp` blocked calls, and `connect()` to `fdaa::3` / `127.0.0.1` ports).
15. **Acceptance Criteria:** `CapEff == 0000000000000000`; `/proc` inside tenant jail lists strictly `<=1` root postmaster + own workers; sibling `/vol/tenants/*` invisible (`ENOENT`); all non-loopback `connect()` fails (`ENETUNREACH`); all restricted syscalls fail (`EPERM`).
16. **Remaining Uncertainty:** Whether Fly's unprivileged Firecracker container wrapper/kernel restricts `CLONE_NEWNS` + `pivot_root` or `seccomp-bpf` without extra VM capabilities (`EXP-A1`, `EXP-C1`, `UQR-01`).

### RISK-22: PostgreSQL Security
1. **Risk ID & Title:** `RISK-22` — PostgreSQL Security
2. **Severity:** `P1`
3. **Root Cause:** Exposing passwords via CLI arguments or environment variables (`/proc/<pid>/cmdline`, `/proc/<pid>/environ`), retaining superuser roles, permitting shared catalog/database views across tenants, leaving management SQL vulnerable to string interpolation, or failing to protect replication credentials and support rotation creates critical credential and privilege-escalation exposure.
4. **Failure Scenario:** A bug exposes `/proc/<pid>/environ` containing `POSTGRES_PASSWORD=...`, or an unparameterized `pg-cell-agent` management helper runs `fmt.Sprintf("CREATE USER %s ...", input)` exposing SQL injection inside internal `SUPERUSER` bootstrap connections—or a compromised app credential rotates slowly while old active sessions remain logged in indefinitely.
5. **Technical Explanation:** Within each isolated tenant cluster (`postgres` process-per-tenant), sibling customer databases do not coexist inside the same cluster anyway (`RISK-01`), automatically eliminating cross-tenant `pg_database`/`pg_roles` SQL catalog snooping! Remaining internal security boundaries center on: (a) keeping tenant `app_owner` strictly non-superuser; (b) delivering `SCRAM-SHA-256` verifiers and replication passwords strictly through root-owned `0600` ephemeral files/pipes during `initdb`/boot rather than CLI flags or environment variables; (c) isolating Gateway-to-Postgres internal authentication so clients never see internal superuser/pooler passwords; (d) parameterizing 100% of management SQL using `pgx.Identifier.Sanitize()` / `$1` bind arguments; and (e) invalidating active Gateway pools cleanly upon credential rotation/revocation.
6. **Industry-Standard Solutions:**
   - Per-tenant `SCRAM-SHA-256` verifier storage at Control Plane / Gateway, ephemeral root-only secret injection, zero `SUPERUSER` grant, strict SQL identifier quoting/parameterization, and fast credential revocation broadcasts.
   - Internal client-certificate / peer-UID auth over Unix domain sockets (`local all postgres peer`) avoiding static admin passwords altogether for `pg-cell-agent`!
7. **Solution Comparison:**
   - *Option A — Store shared admin password in env vars for `pg-cell-agent`:* Risks `/proc` visibility and static shared password compromise across Cells—**rejected**.
   - *Option B — Recommended (`ADR-005`): Linux `peer` Socket Auth for Local `pg-cell-agent` + `SCRAM-SHA-256` Zero-Secret-Env Client Auth + Immediate Revocation Broadcast:* Eliminates local superuser password files cleanly using kernel `SO_PEERCRED` (`peer` UID match over Unix socket), injects tenant credentials strictly via root-owned files/SQL binds, and enforces rotation via Gateway epoch/version bumps.
8. **Recommended Design (`ADR-005`):** (1) `pg_hba.conf` allows internal `pg-cell-agent` administration strictly over root-owned local Unix socket via PostgreSQL `peer` auth (kernel `SO_PEERCRED` verification—zero static admin passwords on disk or env!). (2) Client connections authenticate using `SCRAM-SHA-256` against Gateway/PgBouncer (`user_secret_version`), rejecting MD5/trust cleanly; secrets never enter `argv` or `environ`. (3) Tenant role (`app_owner`) has zero `SUPERUSER`, zero `pg_read_server_files` / `pg_execute_server_program`, and restricted `PUBLIC` defaults (`REVOKE CREATE ON SCHEMA public FROM PUBLIC` if configured or schema-owned by `app_owner`). (4) Password rotation or revocation executes `ALTER ROLE ... WITH PASSWORD ...` in Postgres, updates verifier in Control DB, increments `auth_epoch`, and triggers immediate Gateway session termination (`pg_terminate_backend`) for revoked tokens (`<2s` propagation). (5) `pg-cell-agent` management queries forbid raw SQL string concatenation (`pgx.Identifier{name}.Sanitize()` for DDL + strict regex `[a-z0-9_]{1,63}`).
9. **Architecture Changes:** Add `peer` local socket config + `auth_epoch` invalidation hook between Control Plane, Gateway, and Cell Agent; ban `exec.Command` secret env vars in Go linter/design.
10. **Dependencies:** Extension/GUC lockdown (`RISK-10`), OS namespace/socket boundaries (`RISK-21`), Gateway TLS/SCRAM binding (`RISK-23`).
11. **Trade-Offs:** Revoking a credential terminates active client sessions tied to the old `auth_epoch`, requiring apps to reconnect with rotated secrets cleanly.
12. **Security Implications:** Eliminates `/proc` password scraping, removes internal static superuser passwords (`peer` auth), stops management SQL injection, and enforces cryptographic `SCRAM-SHA-256` end-to-end.
13. **Failure Recovery Strategy:** If a replication or tenant credential is suspected compromised (`RISK-41`), trigger bulk rotation API which generates new 256-bit secrets, pushes updated verifiers via Control Plane, bumps `auth_epoch` killing active Gateway sessions, and records immutable audit trail.
14. **Validation Method:** `EXP-C1` & `EXP-E2` (Verify `/proc/<pid>/cmdline` and `/proc/<pid>/environ` contain zero secrets; run fuzz SQLi payloads on management API; test <2s active-session kick on credential revocation).
15. **Acceptance Criteria:** `0` secrets found in `/proc/*/environ` or `/proc/*/cmdline`; `0` management API SQL injection findings; `100%` revoked sessions disconnected within `<2s` of revocation commit.
16. **Remaining Uncertainty:** Exact synchronization latency between Control Plane credential rotation API and multi-region Gateways before active pooled idle connections expire cleanly (`UQR-09`).

### RISK-23: Gateway Security
1. **Risk ID & Title:** `RISK-23` — Gateway Security
2. **Severity:** `P1`
3. **Root Cause:** Exposing `pg-gateway` directly on public TCP Port `5432` invites PostgreSQL TLS downgrade stripping, massive pre-auth memory bombs (`StartupMessage` claiming `len = 2 GB`), unauthenticated Slowloris socket holds, TLS-SNI vs PostgreSQL startup tenant spoofing, `SCRAM` brute-force floods, forged `CancelRequest` attacks, and accidental customer secret/SQL literal logging.
4. **Failure Scenario:** An attacker connects to `gateway:5432`, skips `SSLRequest` or specifies SNI `victim.db.domain.com` while passing `user=attacker_db.owner` to confuse rate limits or route into sibling state; or opens 10,000 connections sending 1 byte/sec exhausting all Gateway file descriptors; or sends an int32 length prefix `0x7FFFFFFF` forcing a 2 GB `make([]byte, length)` heap OOM crash across all tenants on that Gateway instance.
5. **Technical Explanation:** PostgreSQL's wire startup sequence begins cleanly with an unencrypted 8-byte int32 length + code frame (`SSLRequest` `80877103` or `StartupMessage` `196608` or `CancelRequest` `80877102`), OR direct TLS ClientHello (`sslnegotiation=direct` in PG17). Fly's built-in `pg_tls` handler terminates TLS outside our Go binary before SNI inspection is reliable/flexible for our custom routing—requiring **`handlers = []` Raw TCP Passthrough** (`plan.md Section 2.D`) directly into Go `crypto/tls`. Without defensive `io.LimitReader` bounds *before* allocating packet slices, pre-TLS/pre-auth `Deadline` timers, and cryptographic verification linking `tls.ConnectionState.ServerName` (SNI) to the authenticated `tenant_id` in Control Plane DB, the public gateway becomes a single-point memory DoS & spoofing target.
6. **Industry-Standard Solutions:**
   - Wildcard TLS (`*.db.domain.com`, TLS 1.2/1.3) terminated in hardened edge proxy (`Fly Raw TCP` `handlers = []`) + cryptographic SNI-to-Tenant binding.
   - Strict wire framing limits (`MaxStartupBytes = 8 KB`, `MaxWireMessageBytes = 64 MB`), pre-auth deadlines (`5s`), token-bucket per-IP rate limiting, exponential backoff on SCRAM auth failures, and zero-PII structured logs.
7. **Solution Comparison:**
   - *Option A — Use Fly's built-in `pg_tls` edge handler:* Simplifies ACME certs, **terminates TLS at Fly Proxy** hindering flexible SNI + DirectTLS + custom client auth policies.
   - *Option B — Recommended (`ADR-009`): Go Raw TCP Passthrough (`handlers = []`) on Fly Dedicated IPv4 + Anycast IPv6:* Gives 100% control over `SSLRequest`, PG17 `DirectTLS`, DNS-01 ACME wildcard certs (`crypto/tls`), packet length bounds, Slowloris deadlines, and exact SNI-to-SCRAM tenant validation.
8. **Recommended Design (`ADR-009`):** Enforce at `pg-gateway` (`cmd/pg-gateway`, `internal/wire`):
   1. **TLS Enforcement:** Support both 8-byte `SSLRequest` upgrade and PG17 `DirectTLS` (`sslmode=require` minimum; plaintext non-TLS `StartupMessage` rejected immediately with `28000: TLS connection required`). Wildcard TLS 1.2/1.3 via automated DNS-01 ACME (`certmagic` / Control Plane cert store).
   2. **Frame & Time Bounds:** Read 4-byte length prefix first; reject `StartupMessage > 8,192 bytes`, `CancelRequest != 16 bytes`, and any post-auth `pgproto3` message `> 64 MB` *before allocation* (`08P01` protocol violation + disconnect). Enforce `5s` total pre-auth deadline defeating Slowloris completely.
   3. **Cryptographic SNI Binding:** Extract `tenant_id` from TLS SNI (`{tenant_id}.db.domain.com`) or fallback `user={tenant_id}.{role}` / `options=-c endpoint={tenant_id}`. If TLS SNI specifies a tenant ID, require it to **strictly equal** the authenticated `tenant_id` from `StartupMessage` + `SCRAM` lookup (mismatch -> immediate disconnect + security log).
   4. **Rate Limits & Anti-Brute-Force:** Per-IP token-bucket connection rate limit + progressive per-`(IP, tenant_id)` failure backoff after 5 bad SCRAM attempts (`42501` delay/block). Generate 32-bit `CancelRequest` backend secret keys strictly via `crypto/rand`.
   5. **Zero-Secret Logging:** Never log `StartupMessage` passwords, `SCRAM` proofs, or SQL `Parse`/`Query`/`DataRow` payloads; log strictly redacted connection metadata `(conn_id, src_ip_hash, tenant_id, sqlstate, duration_ms)`.
9. **Architecture Changes:** Configure `deploy/fly/fly.gateway.toml` with Dedicated IPv4 + Anycast IPv6 + `handlers = []`; implement hardened framing reader, `crypto/tls` SNI matcher, and rate limiters in `internal/wire` and `cmd/pg-gateway`.
10. **Dependencies:** Wire protocol compatibility (`RISK-11`), Gateway memory/buffer streaming (`RISK-35`), Fly Dedicated IPv4 pricing (`RISK-29`, Section 8).
11. **Trade-Offs:** Terminating wildcard TLS inside Fly Machines (`pg-gateway`) consumes ~1–2 ms CPU per fresh TLS handshake and adds `$2/mo` Dedicated IPv4 cost cleanly justified in Unit Economics (`Section 8`), while requiring DNS-01 wildcard ACME automation.
12. **Security Implications:** Neutralizes pre-auth memory bombs, Slowloris socket starvation, TLS downgrade stripping, cross-tenant SNI routing confusion, brute-force password guessing, and secret exposure in log aggregators.
13. **Failure Recovery Strategy:** ACME cert renewal runs 30 days ahead of expiry across 3+ redundant Gateways sharing encrypted R2/Control Plane cert state; malformed protocol floods trip per-IP rate-limiter / Fly edge drop without degrading healthy authenticated pooled connections.
14. **Validation Method:** `EXP-E2` (Gateway security fuzz suite: 2 GB length headers, 5,000 Slowloris sockets, plaintext `StartupMessage`, SNI-vs-user spoofing, SCRAM brute-force flood, and log scrubber audit).
15. **Acceptance Criteria:** `0` Go panics or heap spikes (`<10 MB` delta) under 5,000 malformed/Slowloris attacks; `100%` SNI mismatch rejection; `0` plaintext non-TLS logins permitted; `0` password/SQL literal matches in logs.
16. **Remaining Uncertainty:** Real TLS handshake CPS capacity (`connections/sec`) on `performance-2x` vs `performance-4x` Fly Gateway VMs under cold thundering herds (`UQR-09`).

### RISK-24: Tenant Data Security
1. **Risk ID & Title:** `RISK-24` — Tenant Data Security
2. **Severity:** `P1`
3. **Root Cause:** Relying purely on shared bucket-level encryption (`SSE-S3`), skipping per-tenant key separation, leaving stale orphaned snapshots/WAL in R2 after account deletion, missing audit logs, or logging SQL query payloads violates customer isolation, key rotation, data residency, and GDPR/right-to-erasure mandates.
4. **Failure Scenario:** A customer executes `DELETE DATABASE` (exercising GDPR erasure) or an operator rotates compromised keys. Months later, a misconfigured bucket prefix or old base backup still decrypts with the shared bucket key (`SSE-S3`), or support logs retain raw `INSERT INTO users (ssn) VALUES (...)` literals—exposing customer PII long after deletion.
5. **Technical Explanation:** Object-store server-side encryption (`R2 SSE`) protects against physical disk theft at Cloudflare, **not** logical tenant isolation or instantaneous cryptographic erasure across millions of immutable WAL segments (`RISK-02`, `RISK-16`). True cryptographic multi-tenant erasure requires **Envelope Encryption**: every tenant owns a unique 256-bit Data Encryption Key (`DEK`) stored wrapped by a rotating KMS Key Encryption Key (`KEK`) inside the Control Plane KMS store; `pg-cell-agent` encrypts every R2 base/incremental backup and WAL `.zst` object client-side using AES-256-GCM (or ChaCha20-Poly1305) bound via AAD (`tenant_id + epoch + object_key`) before HTTPS upload to R2. Deleting a tenant enters a 7-day `SOFT_DELETED` grace window (blocking all logins immediately), after which hard-delete destroys the `DEK` (**crypto-shredding**—making every remaining R2 fragment mathematically indistinguishable from random noise instantly) and enqueues async R2 prefix deletion.
6. **Industry-Standard Solutions:**
   - Envelope encryption (`DEK` per tenant wrapped by rotating `KEK` in KMS/HSM) + Authenticated Encryption with Associated Data (`AES-256-GCM` binding tenant AAD).
   - 7-day soft-delete safety grace -> instant `DEK` destruction (**crypto-shredding**) + asynchronous prefix purge (`GDPR` compliance).
   - Strict regional cell/R2 bucket pinning (`EU`/`US`) + immutable audit trails + zero-PII telemetry.
7. **Solution Comparison:**
   - *Option A — Cloudflare R2 `SSE` only:* Zero client crypto code, **no per-tenant key rotation or instant crypto-shredding**, and a single R2 bucket token compromises all tenants cleanly—**rejected**.
   - *Option B — Recommended (`ADR-002`, `ADR-005`): Client-Side Envelope Encryption (`DEK` per tenant / rotating `KEK`) + 7-Day Soft-Delete -> Crypto-Shredding + Prefix-Scoped R2 GC:* Instant cryptographic erasure, prevents cross-tenant ciphertext substitution via AAD, enforces regional R2 buckets cleanly, and costs `<0.5%` CPU with Go AES-NI (`>2 GB/s`).
8. **Recommended Design (`ADR-002`, `ADR-005`):** Generate unique 256-bit AES-GCM `DEK` per tenant wrapped by Control Plane KMS `KEK` (scheduled `KEK` rotation every 90 days re-wrapping DEKs cleanly without re-uploading TBs of backups, and on-demand `DEK` rotation on new full backups). Encrypt all R2 objects client-side with AAD `(tenant_id | epoch | key)`. Enforce regional Cell + R2 bucket placement matching tenant data residency setting (`US` vs `EU`). Deletion workflow (`Flow 12`): mark `SOFT_DELETED` (revoke auth immediately, preserve 7 days against accidental `DELETE`) -> after 7 days (or explicit immediate-purge flag), **crypto-shred DEK** inside Control Plane HA DB, record immutable `TENANT_PURGED` audit row, and dispatch async `lifecycle-freeze-queue` R2 prefix sweep. Strip all SQL parameters/literals/PII from Gateway/Agent/Control logs permanently.
9. **Architecture Changes:** Implement envelope AES-256-GCM + AAD crypto wrapper in `internal/storage/r2` and `internal/control` KMS service; add `SOFT_DELETED` -> `PURGED` deletion state machine and immutable `audit_events` table.
10. **Dependencies:** R2 backup validation (`RISK-15`), Control Plane HA DB (`RISK-32`), PG/Gateway log scrubbing (`RISK-22`, `RISK-23`).
11. **Trade-Offs:** Adds KMS `KEK` availability dependency (mitigated by short-TTL wrapped DEK caching during active streaming + HA KMS quorum); losing all KMS KEK copies permanently destroys recoverability of every encrypted R2 backup (`UQR-12` strict KEK backup ceremony required).
12. **Security Implications:** Protects backup confidentiality against bucket-wide compromises, defeats ciphertext swap attacks via AAD binding, satisfies GDPR immediate-erasure SLAs via crypto-shredding, and prevents PII leaks in observability stacks.
13. **Failure Recovery Strategy:** If accidental deletion occurs within the 7-day grace window, Control Plane restores access cleanly via PITR clone (`RISK-41`). If R2 prefix sweep encounters transient network errors post-crypto-shred, queue retries idempotently until bucket prefix is empty while data is already cryptographically unreadable.

### RISK-25: Request Unit (RU) Accuracy & Wire Semantics
1. **Risk ID & Title:** `RISK-25` — Request Unit Accuracy
2. **Severity:** `P1`
3. **Root Cause:** Naive Gateway byte/packet counting treats each client message as 1 query and equates `CommandComplete` + bytes + wall time to true execution cost. In PostgreSQL, one query fires multiple protocol frames (`Parse`, `Bind`, `Describe`, `Execute`, `DataRow` x N, `CommandComplete`, `ReadyForQuery`), pipelined simple queries bundle dozens of statements into one `'Q'` frame, failed/rolled-back/timed-out queries still burn up to 10s of heavy backend CPU/IO, parallel workers multiply actual work, and Gateway internal retries duplicate protocol messages.
4. **Failure Scenario:** A tenant repeatedly sends a `SELECT count(*) FROM huge_table` that scans 10 GB for `9.9s` before hitting `statement_timeout = '10s'` (`ErrorResponse`), paying $0 if errors weren't billed—or sends `SELECT 1; SELECT 2; ... SELECT 50;` inside one Simple Query `'Q'` message paying only `1 RU`—or Gateway transparently wakes/retries a connection causing a single customer query to count `2×` inside billing.
5. **Technical Explanation:** PostgreSQL's backend always emits exactly **one `CommandComplete` (`'C'`) or `ErrorResponse` (`'E'`) per executed SQL statement** inside either Simple Query (multi-statement `'Q'` emits multiple `'C'`s cleanly!) or Extended Query (`Execute` emits `'C'`/`'E'`/`'PortalSuspended'`), and emits **`EmptyQueryResponse` (`'I'`)** on whitespace queries. Crucially, `ErrorResponse` occurring *after* backend query dispatch (e.g., constraint violation, deadlock `40P01`, `statement_timeout` `57014`) consumed real Postgres compute—unlike pre-dispatch Gateway syntax/auth/quota rejections (`57P03`, `28P01`, `53300`). Additionally, internal **Gateway wake-up or seamless retry loops** never represent customer-initiated duplicate work and must be suppressed from billing counters via Gateway request sequence context (`is_internal_retry = false`), whereas genuine **client-initiated** TCP retries did consume independent execution cycles and must be metered honestly per published policy.
6. **Industry-Standard Solutions:**
   - Explicit published **4-Way Separation**: (1) Deterministic Protocol Event Metering, (2) Internal FinOps Resource Cost Accounting (`RISK-26`), (3) Calibrated Customer Pricing Heuristic (`RISK-27`), and (4) Resource/Concurrency Limits.
   - Zero double-billing on proxy-internal wakeups or seamless failover retries.
7. **Solution Comparison:**
   - *Option A — Bill purely per incoming TCP packet or `'Q'`/`'Execute'` frame:* Easily gamed via multi-statement `'Q'` strings or double-bills Gateway internal retries—**rejected**.
   - *Option B — Bill raw hardware `cgroup` nanoseconds directly per query:* Chaotic bills due to background autovacuum/checkpoint noise (`RISK-26`)—**rejected**.
   - *Option C — Recommended (`ADR-012`): Deterministic Protocol-Result Metering + Explicit Published Error/Abort/Retry Rules:* Counts authoritative backend execution responses (`'C'`, post-dispatch `'E'`, `CopyData` bytes, execution wall-clock duration) scoped strictly outside Gateway internal wake retries.
8. **Recommended Design (`ADR-012`):** Instrument `pg-gateway` (`internal/metering`) strictly on backend responses coupled with dispatch state: (1) Meter exact per-statement counters `(commands_completed, post_dispatch_errors, rows_affected_or_returned, wire_bytes_out, copy_bytes_in, backend_exec_wall_ms)` emitted cleanly for every `'C'`, post-dispatch `'E'`, and `CopyData` chunk (automatically billing every statement inside multi-statement `'Q'` cleanly!). (2) Pre-dispatch Gateway rejections (failed auth `28P01`, sleeping timeout `57P03`, pool queue timeout `53300`, SNI mismatch) emit `0` billable RU. (3) Transparent Gateway wake-up holds or aborted internal drain retries do NOT duplicate RU counters because counters increment only after backend dispatch/execution proceeds. (4) Publish crystal-clear billing rules documenting that queries cancelled by `statement_timeout`, client `CancelRequest`, or explicit `ROLLBACK` after executing on the backend count strictly according to backend wall time + bytes consumed prior to abort.
9. **Architecture Changes:** Build deterministic protocol observer state machine inside `internal/metering` wired to `internal/wire` dispatch flags (`dispatched_to_backend`); write explicit Billing Semantics documentation page (`RISK-34`).
10. **Dependencies:** Wire protocol parser (`RISK-11`), CPU/IO COGS accounting (`RISK-26`), durable billing ledger (`RISK-28`).
11. **Trade-Offs:** Customer-visible RU metrics remain cleanly deterministic and reproducible (predictable bills!) rather than tracking microsecond Linux kernel variance, while shifting true CPU/IO discrepancy tracking into internal FinOps (`RISK-26`).
12. **Security Implications:** Multi-statement `'Q'` batching and `statement_timeout` loops cannot bypass compute metering (`statement_timeout` burn still consumes metered wall-ms/RUs + triggers abuse throttling `RISK-26`).
13. **Failure Recovery Strategy:** If a backend crashes (`08006`) mid-execution cleanly after executing `N` ms without sending `'C'`/`'E'`, close-connection hook records pre-drop partial elapsed execution time cleanly (or writes `0` on un-dispatched wake drop), audited asynchronously against `pg_stat_statements`.
14. **Validation Method:** `EXP-E2` / Metering Test Harness (Send multi-statement `'Q'`, `Parse`/`Execute`/`Describe` pipelines, `COPY IN/OUT`, deliberate `ROLLBACK`, `statement_timeout`, bad-password login, and Gateway drain-wake retries).
15. **Acceptance Criteria:** `100%` deterministic correspondence between issued backend SQL operations and metered records; `0` billable units logged for failed auth or Gateway pre-dispatch wakes; `0` missed statements inside batched `'Q'` strings.
16. **Remaining Uncertainty:** Edge cases with `PortalSuspended` (cursor partial fetches transmitting multiple `Execute` calls per single `Parse`) weighting balance vs single-execute statements (`UQR-10`).

### RISK-26: CPU and Disk Metering Attribution
1. **Risk ID & Title:** `RISK-26` — CPU and Disk Metering Attribution
2. **Severity:** `P1`
3. **Root Cause:** Attempting to bill individual tenant SQL queries using raw Linux `cgroups v2` `cpu.stat` and `io.stat` deltas attributes shared PostgreSQL background maintenance (`autovacuum`, `checkpointer`, `walwriter`, `summarize_wal`), page-cache misses driven by neighboring tenants flushing the shared Cell page cache, delayed dirty-buffer checkpoint writes, and shared filesystem metadata operations onto whichever innocent tenant query happens to run simultaneously.
4. **Failure Scenario:** Tenant B fires a simple `1ms` PK lookup (`SELECT * FROM users WHERE id = 5`) during the exact second `checkpointer` flushes dirty buffers or `autovacuum` freezes old tuples inside Tenant B's cgroup—or after heavy neighbor Tenant A thrashing evicted Tenant B's hot index blocks from the shared VM Linux Page Cache. Billing raw `io.stat` bytes/CPU charges Tenant B `100x` unpredictably for identical 1ms PK lookups!
5. **Technical Explanation:** Per PostgreSQL internals and Linux `cgroups v2`: (a) `checkpointer` and `bgwriter` run asynchronously inside the tenant `postmaster` cgroup writing dirty shared buffers long after the originating `INSERT` committed; (b) `autovacuum` and `wal_summarizer` consume `cgroup` CPU/IO autonomously; (c) **`io.stat` tracks physical NVMe reads/writes only**, completely omitting Linux Page Cache hits (`blks_hit`), while charging cache *misses* heavily when VM memory pressure evicts cold pages; (d) shared `ext4` journal commits (`jbd2`) serialize metadata updates globally across all cgroups on one volume. Therefore, **`cgroups v2` telemetry measures true Cell-level tenant infrastructure consumption (FinOps COGS + abuse protection), NOT clean per-query customer billing!**
6. **Industry-Standard Solutions:**
   - Separate **Customer Billing Metric** (deterministic SQL/wire work units or explicit provisioned tier CU/RAM hours) from **Internal FinOps COGS Telemetry** (`cgroups v2` + `pg_stat_database` + `pg_stat_bgwriter`) and **Resource Enforcement** (`io.max` / `cpu.max` / Dedicated promotion).
   - Periodic `pg_stat_statements` reconciliation checking `shared_blks_hit` vs `shared_blks_read` + `temp_blks_written` over 5-minute windows.
7. **Solution Comparison:**
   - *Option A — Direct cgroup `cpu.stat`/`io.stat` per-query billing:* Financially chaotic, punishes tenants for VM cache eviction and background maintenance—**rejected**.
   - *Option B — Recommended (`ADR-012`): Strict Separation of Per-Query Customer Metering vs 5-Minute Internal Cgroup/PG FinOps Telemetry & Throttling:* Keeps customer invoices clean and predictable while accurately tracking 100% of background/WAL/temp/cache-miss infrastructure cost internally per tenant.
8. **Recommended Design (`ADR-012`):** Enforce strict architectural separation: (1) **Customer Billing (`billing-usage-queue`)** uses strictly deterministic protocol events (`RISK-25`) + physical/logical storage bytes (`RISK-14`); (2) **Internal COGS Accounting (FinOps)** scrapes every tenant's `cgroups v2` `cpu.stat`, `io.stat`, `memory.current`, plus PostgreSQL `pg_stat_database` (`blks_hit`, `blks_read`, `temp_bytes`), `pg_stat_bgwriter`, and WAL generation rate every 5 minutes—explicitly tracking `autovacuum`, WAL, checkpoint, and parallel-worker overhead against real Fly/R2 invoices; (3) **Abuse Enforcement** uses `cgroups v2` `cpu.max`/`io.max` ceilings and promotes tenants whose sustained background CPU/IO COGS diverges far above plan tier into Dedicated Cells (`RISK-38`).
9. **Architecture Changes:** Add 5-minute FinOps collector inside `pg-cell-agent` publishing internal `cogs_telemetry` metrics cleanly separated from customer `billing-usage-queue`; configure `pg_stat_statements` per cluster.
10. **Dependencies:** Cgroup/OS instrumentation (`RISK-05`), autovacuum (`RISK-08`), protocol metering (`RISK-25`), pricing calibration (`RISK-27`), large-tenant promotion (`RISK-38`).
11. **Trade-Offs:** Customer billing does not micro-adjust instantly when `autovacuum` spikes—requiring carefully calibrated margins (`RISK-27`) and sustained-usage promotion tiers (`RISK-38`) so heavy hidden background churn is eventually upgraded fairly.
12. **Security Implications:** Separates internal FinOps/kernel telemetry from customer-facing invoice streams, preventing subtle side-channel inference about neighbor page-cache pressure from appearing on customer bills.
13. **Failure Recovery Strategy:** If FinOps COGS telemetry collector detects a tenant's background CPU/WAL (`autovacuum` or temp churn) continuously exceeding `>2x` its RU revenue for >24 hours, raise automated FinOps alert + trigger tier review/promotion (`RISK-38`).
14. **Validation Method:** `EXP-C4` (Execute steady 1ms PK lookups in Tenant B while simultaneously injecting forced `CHECKPOINT`, `VACUUM (FREEZE)`, and heavy Neighbor A page-cache thrashing).
15. **Acceptance Criteria:** `0%` variance in Tenant B customer per-query RU count during simultaneous background `VACUUM`/`CHECKPOINT` and Neighbor A thrash; internal FinOps COGS collector reconciles total VM CPU/IO against `cgroups v2` within `<5%`.
16. **Remaining Uncertainty:** Real `pg_stat_statements` memory cost + miss ratio when dynamic un-parameterized SQL overflows `pg_stat_statements.max` (default 5,000) across 100 active tenants (`UQR-10`).

### RISK-27: RU Pricing Model
1. **Risk ID & Title:** `RISK-27` — RU Pricing Model Viability
2. **Severity:** `P1`
3. **Root Cause:** Inventing arbitrary per-million Request Unit (`RU`) dollar rates or claiming "10x–250x cheaper" unit economics prior to benchmarking true COGS across idle-long-tail tenants, dense OLTP tenants, and adversarial analytical scan workloads leads directly to unprofitable pricing tiers and gross-margin inversion.
4. **Failure Scenario:** Publishing "$0.50 per 1M RUs + $0.00/mo Free Tier with 100k RUs" without workload caps causes: (a) 10,000 abandoned idle free databases consuming 45 MB each (`450 GB` Fly NVMe = `$67.50/mo` + R2/control overhead with `$0` revenue); or (b) one heavy analytical tenant executing continuous `9.9s` scans within the free/low-RU cap, saturating a `$90–$132/mo` Compute Cell while paying `$3/mo`.
5. **Technical Explanation:** Serverless PostgreSQL unit economics break into **fixed/floor costs** (always-on Fly Compute Cell VMs + attached NVMe `@ $0.15/GB-month` + Fly Dedicated IPv4 `@ $2/mo` per Gateway region + Pro Standby VMs + Control Plane 3-node HA) vs **marginal variable costs** (active CPU time, NVMe IOPS saturation requiring extra Cell scaling, R2 storage `@ $0.015/GB-month` + Class A/B ops, Deep Freeze wake latency). A pure per-request fee works cleanly *only* when paired with separate per-GB storage pricing, free-tier automated R2 Deep Freeze (zero Fly NVMe cost after grace period), concurrency/timeout ceilings (`statement_timeout`, `io.max`), minimum billable compute floors on active/dedicated tiers, and empirical COGS weight calibration against real Stage 1–2 load tests.
6. **Industry-Standard Solutions:**
   - **Multi-Dimensional Serverless Pricing (`Neon` / `PlanetScale` / `Turso` / `Cloudflare D1`):** Separate **Compute / RU consumption** + **Active/Idle Storage GB-month** + **Free-tier aggressive Deep Freeze / low storage cap** + **Dedicated Tier graduation**.
   - **Empirical Unit-Economics Model (`Section 8`)**: Explicitly parameterized with verified vendor SKUs (`$0.15/GB-mo` Fly NVMe, `$0.015/GB-mo` R2, `$66–$132/mo` Cells) rather than speculative multipliers.
7. **Solution Comparison:**
   - *Option A — Pure flat per-million-RU billing with unlimited storage/scan duration:* Margin-negative against idle storage hoarding and heavy full-table scans—**rejected**.
   - *Option B — Pure active CU-second billing (like Neon):* Accurately mirrors VM time, sacrifices simple "pay-per-request" API predictability for low-traffic REST/webhook devs.
   - *Option C — Recommended (`ADR-012`): Dual-Meter Hybrid Heuristic (RU Tiers + Explicit Storage/Backup GB + Deep Freeze Eviction + Dedicated Compute Graduation):* Preserves intuitive RU billing for OLTP apps while capping scan CPU (`statement_timeout`, `io.max`), charging exact R2/NVMe storage above tiny free caps, and auto-promoting sustained heavy users (`RISK-38`).
8. **Recommended Design (`ADR-012`):** (1) Separate Storage (`$/GB-month`) and Backup/PITR retention billing cleanly from Compute RU charges; (2) Establish strict Free Tier bounds (e.g., max 250 MB storage, `statement_timeout=5s`, max 5 concurrent backends, automatic R2 Deep Freeze after 7 days inactivity eliminating `$0.15/GB` Fly NVMe bleed); (3) Calibrate final RU weights `(w_stmt, w_wall_ms, w_bytes_out, min_ru_per_exec)` only after Stage 1–2 empirical COGS runs across three benchmark archetypes (`Section 8`); (4) Enforce concurrency caps, `cgroups v2` throttling (`RISK-26`), and automatic Dedicated Cell promotion (`RISK-38`) so one analytical tenant cannot burn shared Cell margin; (5) Remove all unsupported "10x–250x cheaper" claims until calibrated.
9. **Architecture Changes:** Parameterize RU formula constants dynamically in `pg-control-plane` pricing engine; build Stage 3 Deep Freeze R2 auto-archiver for dormant Free Tier databases; enforce plan limits in Gateway & Cell admission controller.
10. **Dependencies:** Protocol metering (`RISK-25`), FinOps COGS accounting (`RISK-26`), Fly/R2 pricing baseline (`RISK-29`), Deep Freeze / large-tenant promotion (`RISK-38`).
11. **Trade-Offs:** Adding concurrency bounds, `statement_timeout`, and Free-tier Deep Freeze archival slightly increases cold-start wait on rarely accessed Free databases (multi-second R2 rehydrate) in exchange for positive platform gross margins at massive free-tier scale.
12. **Security Implications:** Hard Free-tier concurrency/RU/timeout caps defeat free-account crypto-mining and resource-exhaustion signup abuse (`Sybil` billing abuse).
13. **Failure Recovery Strategy:** When any tenant hits Free/Tier soft/hard monthly budget limits, Gateway transitions smoothly to `QUOTA_PAUSED` returning clean SQLSTATE `53100`/`53400` without deleting data, letting developers upgrade or reset next cycle cleanly.
14. **Validation Method:** Stage 1–2 COGS Financial Simulation & Live Load Benchmark (`EXP-C4`, `EXP-D5`, `Section 8` Unit Economics Model validation comparing simulated RU bills vs real Fly + R2 cost curves across all 4 workload archetypes).
15. **Acceptance Criteria:** Calibrated financial model demonstrates documented positive gross margin (`>=50%` target margin under configured tier limits) across: (a) 10,000 idle/low-volume Free DBs, (b) heavy indexed OLTP, (c) heavy analytical abuse attempt, and (d) Pro Sync HA tiers.
16. **Remaining Uncertainty:** Real achievable tenant density per Fly Cell (`80` active / `500` dormant target), real Cloudflare Queue & R2 Class A/B op volume under burst workloads, and customer cold-wake elasticity (`UQR-07`, `UQR-10`).

### RISK-28: Usage Event Reliability
1. **Risk ID & Title:** `RISK-28` — Usage Event Reliability
2. **Severity:** `P1`
3. **Root Cause:** Buffering aggregated usage metrics solely in `pg-gateway` heap RAM loses revenue on unexpected Gateway OOM/`SIGKILL` crashes, while Cloudflare Queues' at-least-once HTTP Pull Consumer delivery semantics cause duplicated invoice charges on lease-expiry redelivery or network retries without durable client-side WAL persistence and database-level idempotency.
4. **Failure Scenario:** Gateway accumulates 14 seconds of usage batches in memory and receives abrupt `SIGKILL` during VM host eviction -> billing events permanently lost. Conversely, Control Plane Pull Consumer consumes a batch from Cloudflare Queues, writes to `usage_ledger`, and times out before calling `/ack`; 30s later Queue redelivers the batch -> without `ON CONFLICT (idempotency_key) DO NOTHING`, customer gets double-billed!
5. **Technical Explanation:** Reliable distributed usage ingestion requires an **End-to-End Outbox-to-Idempotent-Sink Pipeline**: (1) Gateway periodically (every 15s—or 1s micro-flush for minimal loss window—and synchronously during `SIGTERM` shutdown) commits serialized usage batch records into a local disk-backed B+tree store (`go.etcd.io/bbolt` WAL file) *before* asynchronously calling Cloudflare Queues `sendBatch`. Local `bbolt` records delete only after receiving Queue HTTP `200 OK`. (2) Each batch carries a globally unique deterministic **`idempotency_key = sha256(gateway_id | tenant_id | window_start_unix | seq_no)`**. (3) Control Plane HTTP Pull Consumer (`cloudflare-go/v7`) inserts rows into HA Postgres `usage_ledger` inside an ACID transaction protected by `UNIQUE (idempotency_key)` using `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` **before** posting `/queues/{id}/messages/ack` with `lease_id`!
6. **Industry-Standard Solutions:**
   - Client/Edge disk-backed WAL (`bbolt`/`SQLite`/disk spool) -> At-least-once Queue -> Transactional Idempotent Ledger (`ON CONFLICT DO NOTHING`) + Asynchronous Reconciliation Job.
8. **Recommended Design (`ADR-004`, `ADR-012`):** Implement a 3-stage pipeline:
   1. **Gateway `bbolt` WAL (`internal/metering`):** Flush usage windows every 15s (plus synchronous checkpoint flush on `SIGTERM`) to local `/data/gateway_usage.bbolt` prior to network send; erase from `bbolt` strictly after Queue ACK `200`. Unsent `bbolt` batches replay cleanly on Gateway restart.
   2. **Cloudflare Queues Transport (`billing-usage-queue`):** Batched JSON/Protobuf payloads keyed with `sha256(gateway_id + tenant_id + window_start + seq_no)`.
   3. **Control Plane HTTP Pull Consumer (`internal/queue`):** Polls `/messages/pull` (`lease_id` = 60s), executes `BEGIN; INSERT INTO usage_ledger (...) VALUES (...) ON CONFLICT (idempotency_key) DO NOTHING; COMMIT;` cleanly, and issues `/messages/ack` only post-`COMMIT`.
   4. **Nightly Reconciliation Auditor:** Compares aggregated `usage_ledger` statement/time totals against Gateway exported Prometheus counters (`RISK-39`) and tenant `pg_stat_statements` totals (`5%` anomaly threshold triggers billing dispute/audit alert).
9. **Architecture Changes:** Add `bbolt` WAL writer/replayer inside `cmd/pg-gateway`; add Cloudflare Queues HTTP Pull/Ack consumer (`cloudflare-go/v7`) + `usage_ledger (idempotency_key TEXT PRIMARY KEY, ...)` schema in `pg-control-plane`.
10. **Dependencies:** Cloudflare Queues HTTP Pull API availability (`ADR-004`), Control Plane HA Postgres (`RISK-32`), protocol metering counters (`RISK-25`), monitoring alerts (`RISK-39`, `RISK-40`).
11. **Trade-Offs:** Gateway VMs require a small persistent/scratch local volume (`1 GB`) or fast local disk for `bbolt` (`<1ms` per 64 KB batch fsync every 15s); abrupt total Gateway VM disk loss can still drop <=15s (tunable to <=1s) of unshipped local counters unless replicated remotely (acceptable residual edge risk for metering, avoiding slow synchronous RPC on every SQL query!).
12. **Security Implications:** Immutable append-only `usage_ledger` prevents silent tampering; internal Gateway-to-Queue/Control APIs authenticate via scoped Cloudflare tokens and mTLS; no raw SQL strings appear in billing batches.
13. **Failure Recovery Strategy:** If Cloudflare Queues is temporarily unreachable (5xx outage), Gateway pauses deletion in `bbolt` (bounded up to local disk cap, alerting at `RISK-40` backlog threshold) and replays cleanly in chronological order once Queue API recovers. Out-of-order late deliveries merge cleanly by timestamp window into `usage_ledger`.
14. **Validation Method:** `EXP-E2` & `EXP-D1` (Crash Gateway via `SIGKILL` mid-window and verify `bbolt` replay; replay identical batch messages 5x through Cloudflare Queue consumer and assert exact row invariance).
15. **Acceptance Criteria:** `0%` duplicate rows across `5x` forced Queue redelivery tests; `0` dropped records across graceful `SIGTERM` Gateway redeploys; bounded `<=15s` (or `<=1s` if configured) worst-case un-persisted loss window under abrupt Gateway hardware destruction; nightly reconciliation audit functional.
16. **Remaining Uncertainty:** Real Fly Gateway local disk latency/throughput impact of `bbolt` `fsync` at 1s vs 15s intervals and Cloudflare Queue HTTP Pull batch latency/rate limits under sustained burst load (`UQR-10`).

### RISK-29: Fly.io Machine Constraints
1. **Risk ID & Title:** `RISK-29` — Fly.io Machine Constraints
2. **Severity:** `P2`
3. **Root Cause:** Fly.io imposes concrete infrastructure boundaries on Firecracker microVMs and Machines API control loops: (a) API write rate limits (~10 intensive write actions/min or per-app mutation throttling returning `HTTP 429` with `Retry-After`) and initial org fleet caps; (b) injected `/init` PID 1 with `kill_signal = "SIGINT"` and 5s `kill_timeout` defaults; (c) small ephemeral rootfs `/` separate from mounted `/vol`; (d) regional hardware SKU capacity variation; and (e) non-zero baseline compute cost (`$66/mo` `performance-2x` 4 GB, `$132.01/mo` `performance-4x` 8 GB) + `$0.15/GB-month` persistent NVMe/stopped rootfs floor.
4. **Failure Scenario:** A viral burst spawns 50 new tenants triggering 50 parallel `CreateMachine` API calls -> Fly API throttles with `HTTP 429 Too Many Requests`, breaking provisioning; or a Cell deploy sends default `SIGINT` and hard-kills Firecracker 5s later mid-checkpoint across 60 active PostgreSQL clusters; or placing Pro primary + standby without `--volume-requires-unique-zone` lands both Machines on one physical worker rack/power zone.
5. **Technical Explanation:** According to official [Fly.io Pricing & Machines Docs](https://fly.io/docs/about/pricing/): Compute bills per second while running (`performance-2x` = 2 dedicated vCPU / 4 GB RAM ~$66/mo; extra RAM = `$6/GB/mo` so 8 GB on `2x` = `$90/mo`; `performance-4x` = 4 dedicated vCPU / 8 GB RAM ~$132.01/mo); attached Volumes and stopped rootfs cost `$0.15/GB-month` (`snapshots` = `$0.08/GB-month` stored after 10 GB free/mo). Crucially, tenant scale-to-zero operates purely at the **OS process level inside already-running Cells**, reducing Fly API calls during steady-state wakes to **0**. Remaining Fly API calls occur only during macro Cell fleet scaling, Pro standby replacement, and rollouts—where token-bucket rate limiting and headroom Cell buffers prevent hitting Fly API throttles.
6. **Industry-Standard Solutions:**
   - Process-level multi-tenancy inside pre-warmed Compute Cell pools (`0` VM boots on tenant wake).
   - Rate-limited infrastructure reconciler honoring `HTTP 429` + `Retry-After` + standby warm headroom buffer (`75%` admission cap).
   - Zone-diverse volume placement (`--volume-requires-unique-zone`) and explicit `SIGTERM` / `300s` drain lifecycle overrides.
7. **Solution Comparison:**
   - *Option A — 1 Fly Machine VM per Tenant:* Direct Firecracker isolation per tenant, **fails at scale** due to Fly API write throttling on wake bursts and prohibitive `$0.15/GB` stopped rootfs/volume economics (`ADR-005`).
   - *Option B — Recommended (`ADR-006`, `ADR-010`): Warm Multi-Tenant Cell Pools (`0` API calls/wake) + Rate-Limited Fleet Scaler + Dedicated Zone-Separated Pro Standbys:* Absorbs tenant concurrency bursts instantaneously inside Linux VMs while safely wrapping macro fleet scaling in `Retry-After`-aware rate limiters.
8. **Recommended Design (`ADR-006`, `ADR-010`):** (1) Isolate tenant wake/sleep strictly inside Cell VMs (`0` Fly API calls). (2) Wrap `fly-machines` client in Control Plane with a per-app token-bucket rate limiter obeying `HTTP 429` `Retry-After` headers cleanly. (3) Override `/init` defaults in `deploy/fly/fly.cell.toml`: `kill_signal = "SIGTERM"`, `kill_timeout = "300s"`, `swap_size_mb = 2048`; implement `PR_SET_CHILD_SUBREAPER` in `pg-cell-agent` (`RISK-06`). (4) Confine all temp/pool/PGDATA files to `/vol` (`TMPDIR=/vol/tmp`), keeping ephemeral `/` untouched (`RISK-13`). (5) Maintain warm pre-provisioned headroom Cells before active utilization reaches `75%`, and enforce `--volume-requires-unique-zone` between Pro Primary and Standby Machines (`RISK-03`). (6) Measure always-on Cell economics against empirical Stage 1 load (`Section 8`).
9. **Architecture Changes:** Add `fly.cell.toml`, `fly.gateway.toml` (`handlers=[]` + Dedicated IPv4), `fly.standby.toml`, `fly.control.toml`; wrap Fly Machines REST client with token-bucket + `Retry-After` backoff; add warm Cell headroom autoscaler in `internal/control/scheduler`.
10. **Dependencies:** Stage 0 Fly runtime/volume proof (`RISK-13`), process lifecycle (`RISK-06`), Cell capacity policy (`RISK-31`), regional network (`RISK-30`).
11. **Trade-Offs:** Keeping warm headroom Cells running raises fixed monthly baseline cost compared to pure pay-as-you-go Lambda (`Section 8`), mitigated by bin-packing 80–500 tenants per Cell SKU and raising org fleet limits with Fly support prior to GA.
12. **Security Implications:** Least-privilege Fly deploy tokens scoped separately per app (`cell-app` vs `gateway-app` vs `control-app`); immutable Control Plane audit log of every Machine lifecycle call.
13. **Failure Recovery Strategy:** If Fly reports capacity exhaustion (`507`/`insufficient capacity`) for `performance-4x` in one zone/region during scale-out, Control Plane scheduler falls back cleanly to secondary SKU (`performance-2x + extra RAM`) or cross-zone placement (`iad` -> `ewr` backup region for new tenant placements).
14. **Validation Method:** `EXP-A1` & Stage 0 Fly Test Suite (Create/start/stop/replace Machine across zones, verify `Retry-After` handling on synthetic `429`, verify `--volume-requires-unique-zone` distinct host/zone placement, verify `SIGTERM` `300s` clean checkpoint).
15. **Acceptance Criteria:** `0` unhandled `HTTP 429` provisioning errors under synthetic scaling bursts; verified separate failure-zone placement on Pro Primary/Standby pairs; `100%` clean `SIGTERM` Cell drains within `<15s` (well inside `300s`).

### RISK-30: Regional Network Risks (`6PN`)
1. **Risk ID & Title:** `RISK-30` — Regional Network Risks (`6PN`)
2. **Severity:** `P2`
3. **Root Cause:** Routing over Fly `.internal` round-robin DNS caches stale/stopped Machine IPv6 addresses during rollouts/failures, and unbuffered transient WireGuard (`6PN`) packet loss or cross-AZ latency jitter stalls Gateway-to-Cell connection pools into unbounded goroutine and memory growth.
4. **Failure Scenario:** A Gateway opens backend tunnels using cached `<app>.internal` DNS; Cell #2 crashes and is replaced -> DNS TTL lingers for 60s routing new traffic into dead IPv6 blackholes, or 3% `6PN` packet loss spikes cross-region RTT causing 2,000 Gateway goroutines to pile up waiting indefinitely on TCP `connect()`/`write()`, OOMing the Gateway!
5. **Technical Explanation:** According to [Fly Private Networking (`6PN`) documentation](https://fly.io/docs/reference/private-networking/): Every Machine receives a unique immutable private IPv6 address (`FLY_PRIVATE_IP`) reachable deterministically via `<machine_id>.vm.<app-name>.internal`, avoiding round-robin `<app>.internal` DNS ambiguity cleanly, and intra-org `6PN` WireGuard traffic is encrypted & unmetered. However, encrypted WireGuard tunnels still run over underlying physical datacenter switches and cross-AZ/cross-region WAN links: packet drops, MTU fragmentation, silent half-open TCP drops on sudden host reboots, and WAN latency variation (`1–3ms` intra-region vs `10–80ms` cross-region) can hang blocking `net.Dial` or `conn.Write` syscalls unless strict TCP keepalives, connect/write timeouts, bounded hold queues, and fast-fail backpressure (`08006` / `503`) are enforced.
6. **Industry-Standard Solutions:**
   - Direct machine-ID addressing (`<machine_id>.vm.<app>.internal` or `FLY_PRIVATE_IP` registered in Control DB) bypassing round-robin DNS.
   - Internal mTLS (`<30d` auto-rotated certs) + aggressive TCP keepalives (`10s` idle, `3s` interval, `3` probes) + strict dial/write deadlines + bounded queue backpressure.
7. **Solution Comparison:**
   - *Option A — Use `<cell-app>.internal` DNS or Flycast HTTP balancing for Gateway-to-Cell:* Breaks stateful tenant pinning (Gateway must reach the *exact* Cell Machine hosting that tenant's `PGDATA`) and risks stale DNS resolution—**rejected**.
   - *Option B — Recommended (`ADR-009`, `ADR-011`): Direct `<machine_id>.vm.<app-name>.internal` IPv6 Routing + mTLS + Bounded Timeouts + `6PN` Synthetic Prober:* Deterministic routing straight to owning Cell Machine with instant failover invalidation and bounded memory under blackholes.
8. **Recommended Design (`ADR-009`, `ADR-011`):** (1) Gateways dial exact target Cell VMs via `<machine_id>.vm.<cell-app>.internal:7432` pushed dynamically in Control Plane route tables (invalidated via instant epoch-bump push—zero DNS round-robin staleness). (2) Authenticate every Gateway-Cell and Primary-Standby channel over `6PN` with mutual TLS (internal CA rotating short-lived 7–30d certs seamlessly before expiry). (3) Enforce `2s` TCP dial timeout, TCP keepalives (`10s`/`3s`/`3`), `30s` socket write deadline, bounded per-tenant wait queues (`RISK-12`), and fast-fail (`08006`) if queues saturate. (4) Run a continuous `6PN` synthetic RTT + loss prober between Gateways, Cells, and Standby zones feeding hysteresis failover (`RISK-19`) and Prometheus metrics (`RISK-39`).
9. **Architecture Changes:** Build internal mTLS cert issuer/rotator in `pg-control-plane`; enforce immutable `<machine_id>.vm...internal` target endpoints in Gateway route cache and `pg-cell-agent`; configure `tc`/`netem` chaos tests in CI.
10. **Dependencies:** Failover hysteresis (`RISK-19`), Gateway pool bounds (`RISK-12`, `RISK-35`), Pro sync replication latency (`RISK-03`), Fly `6PN` (`RISK-29`).
11. **Trade-Offs:** Aggressive TCP keepalives (`10s`) and `2s` dial timeouts speed blackhole detection cleanly at negligible packet cost while requiring slightly careful tuning if extreme legitimate WAN congestion occurs across distant regions.
12. **Security Implications:** Encrypts and mutually authenticates internal `6PN` control, SQL proxy, and replication streams on top of Fly's WireGuard mesh (defense-in-depth against shared-proxy or misrouted org access); automated `<30d` cert rotation limits stolen cert lifetime.
13. **Failure Recovery Strategy:** When Gateway detects TCP blackhole/reset to Cell #1 (`dial` timeout or `ECONNRESET`), it invalidates cached idle backend sockets to Cell #1 immediately, reports suspect signal to Control Plane hysteresis engine (`RISK-19`), rejects un-dispatched requests cleanly (`53300`/`08006`), and switches cleanly once Control Plane promotes `epoch E+1`.
14. **Validation Method:** `EXP-D2` & Network Chaos (`tc qdisc netem` injecting `5%` packet loss, `200ms` jitter, and blackhole drop between Gateway/Primary/Standby).
15. **Acceptance Criteria:** `0` Gateway OOM crashes or unbounded goroutine leaks under 5% loss / 100% blackhole simulation; `100%` pool recovery within `<5s` of network restoration; `0` expired mTLS certs under 30d simulated rotation drill.
16. **Remaining Uncertainty:** Real baseline p50/p95/p99 `6PN` intra-region inter-zone RTT (`iad` zone A <-> zone B) and cross-region jitter under multi-Gbps load on live Fly hardware (`UQR-04`).

### RISK-31: Cell Capacity Management
1. **Risk ID & Title:** `RISK-31` — Cell Capacity Management
2. **Severity:** `P2`
3. **Root Cause:** Without multi-dimensional placement scoring and explicit hard caps across active PG processes, dormant cluster counts, RAM/Page Cache footprints, CPU oversubscription, backend connection counts, and `ext4` disk space, Control Plane scheduling accidentally co-locates multiple heavy workloads on one VM, causing global page-cache thrashing, NVMe saturation, and cascading latency spikes.
4. **Failure Scenario:** Five tenants start empty (0 MB), all grow simultaneously into 4 GB active OLTP workloads on the same `performance-4x` (8 GB) Cell #1. Combined working set (20 GB) exceeds Cell RAM (8 GB), evicting all Page Cache, saturating NVMe random read IOPS, pushing CPU utilization >95%, and hurting 75 innocent neighboring micro-tenants co-located on Cell #1.
5. **Technical Explanation:** PostgreSQL relies heavily on the shared Linux Page Cache (`RISK-09`) to serve hot indexes without physical disk reads when `shared_buffers = 16MB`. Multi-tenant Cell capacity is therefore bounded simultaneously by **5 orthogonal resources**: (1) Physical RAM (`Active PG processes × worst-case RSS + 25% OS/Page Cache reserve`); (2) Active CPU headroom (`cgroups v2 cpu.max` + oversubscription factor); (3) Physical NVMe space (`<=75%` volume cap accounting for WAL, staging, and `.cell_ballast`); (4) Kernel file descriptors & total PG backends (`<=1,200` backends per 8 GB Cell); and (5) Total dormant directories (`<=500` per Cell to cap `initdb`/re-adoption scans and disk metadata).
6. **Industry-Standard Solutions:**
   - Multi-dimensional bin-packing scheduler + live telemetry rebalancing (`Kubernetes`/`Nomad` weighted resource bin-packing paired with database workload promotion).
   - Proactive Cell evacuation / live physical migration (`RISK-20`) whenever utilization exceeds `75%` admission / `80%` rebalance watermark.
7. **Solution Comparison:**
   - *Option A — Static round-robin tenant-to-Cell assignment:* Simple, **inevitably creates hot-shard noisy Cells** as tenant workloads diverge asymmetrically over weeks—**rejected**.
   - *Option B — Recommended (`ADR-008`, `ADR-011`): Multi-Dimensional Telemetry Bin-Packer + Hard Cell Ceilings + Auto-Evacuation/Promotion:* Continuously balances active RAM, disk `<=75%`, CPU, and connections across healthy Cells and migrates growing/hot tenants off automatically via `RISK-20`.
8. **Recommended Design (`ADR-008`, `ADR-011`):** Enforce explicit SKU capacity tables (example baseline for `performance-4x` 8 GB / 100 GB NVMe shared Cell, subject to Stage 1 empirical calibration):
   - Max active running PG processes: **80** (assuming dynamic RSS admission <=75% RAM)
   - Max dormant on-disk clusters: **500**
   - Max `ext4` physical disk utilization: **75%** admission freeze (`85%` urgent eviction `RISK-17`)
   - Max total PG backend connections: **1,200**
   - Page-cache safety guard: reserve `>=25%` Cell RAM untouched by PG heap/buffers (`~2 GB` on 8 GB Cell) solely for Linux Page Cache + OS + `pg-cell-agent`, alerting when global `major_faults` or `blks_read / (blks_hit + blks_read)` exceeds SLA.
   - Scheduler scores target Cells via `(FreeRAMWeight + FreeDiskWeight + LowCPULoadWeight + ZoneSpread)` and triggers automatic live migration (`RISK-20`) / Deep Freeze eviction whenever a Cell exceeds `80%` active utilization or a single tenant breaks shared-tier ceilings (`RISK-38`).
9. **Architecture Changes:** Build weighted bin-packing scheduler & automated hot-Cell evacuation loop in `internal/control/scheduler`; enforce hard local Cell admission refusal in `pg-cell-agent` if local free RAM/disk drops below safety floor.
10. **Dependencies:** Memory baseline & admission (`RISK-09`), disk quotas (`RISK-17`), noisy-neighbor & large-tenant promotion (`RISK-38`), monitoring telemetry (`RISK-39`).
11. **Trade-Offs:** Stopping admission at `75%` disk/RAM leaves ~25% headroom buffer on every active Cell (`higher $/active-tenant COGS` vs `100%` overpacking), intentionally trading raw density for stable neighbor p99 latency and recovery staging runway.
12. **Security Implications:** Prevents accidental/intentional "whale" tenants from starving security/audit daemons or inducing Cell-wide resource exhaustion DoS across neighboring customers.
13. **Failure Recovery Strategy:** If a Cell unexpectedly breaches 80% disk or RAM simultaneously due to synchronized tenant bursts, local `pg-cell-agent` suspends idle unpinned DBs first, throttles noisy `cgroups v2` `io.max`/`cpu.max`, rejects new tenant provisions on that Cell, and instructs Control Plane to evacuate top-growth DBs via live physical migration (`RISK-20`).
14. **Validation Method:** `EXP-C2`, `EXP-C3`, `EXP-C4` + Scheduler Growth Simulation (Simulate 5 Cells receiving skewed database/query growth; verify placement freezes past 75% and triggers automated live migration cleanly).
15. **Acceptance Criteria:** `0` Cells sustain `>85%` RAM or `>80%` disk without triggering automated admission block + live rebalance; Tenant B OLTP p99 latency remains within SLA during noisy Cell rebalance.
16. **Remaining Uncertainty:** Exact real-world maximum active tenant count per `performance-2x` (4 GB) vs `performance-4x` (8 GB) under realistic mixed ORM working sets before Linux Page Cache thrashing degrades p99 (`EXP-C4`, `UQR-07`).

## P2 — Control Plane & API Design

### RISK-32: Control Plane Reliability
1. **Risk ID & Title:** `RISK-32` — Control Plane Reliability
2. **Severity:** `P2`
3. **Root Cause:** Running a single-instance Control Plane API or single-node metadata PostgreSQL DB creates a global control-plane SPOF; lacking transactional outbox state machines, allocation locks, and background reconcilers causes permanent metadata-vs-Cell drift whenever API crashes occur mid-provision, mid-migration, or mid-delete.
4. **Failure Scenario:** Control Plane API receives `POST /databases`, claims a cluster on Cell #1, and suffers OOM or deploy restart *before* committing the `tenants` row to metadata DB -> Cell #1 leaks a running cluster forever. Conversely, deletion interrupts mid-migration leaving orphaned R2 prefixes and ghost Gateway routes.
5. **Technical Explanation:** Control Plane authority manages strictly strong-consistency metadata (`tenant -> owner_cell, epoch, unique system_identifier, lease_state, idempotency_keys, backup_catalog, usage_ledger`) where eventual consistency risks split-brain (`RISK-18`) or duplicate identities (`RISK-01`). Deploying stateless Go API servers behind Anycast/Flycast paired with a **3-node multi-zone HA PostgreSQL metadata cluster** (managed HA PG using Patroni/Fly multi-zone sync or managed Postgres) guarantees survivable single-node/zone loss. Every multi-step side effect (`Create`, `Migrate`, `Failover`, `Delete`) writes a state transition (`PROVISIONING -> ACTIVE -> MIGRATING -> SOFT_DELETED -> PURGED`) plus an outbox task inside one ACID DB transaction, driven forward idempotently by `control-reconcile-queue` and periodic inventory sweeps against live Cells. Meanwhile, Gateways hold short-TTL local routing caches (`epoch`-checked) so existing client SQL traffic stays live cleanly even across brief Control Plane API restarts!
6. **Industry-Standard Solutions:**
   - 3+ stateless API replicas + 3-node multi-zone HA PostgreSQL metadata DB with PITR backups -> R2.
   - Transactional Outbox + Explicit Entity State Machine + Periodic Reconciliation Loop (`Kubernetes controller` reconciliation pattern).
7. **Solution Comparison:**
   - *Option A — Embedded Raft metadata (`etcd` / `dqlite`) inside Go binary:* No separate Postgres process, **poor fit for rich relational joins across billing ledgers, backup DAGs, idempotency keys, and audit logs**.
   - *Option B — Recommended (`ADR-011`): 3+ Go Control API Replicas + 3-Node HA PostgreSQL Metadata DB + Reconciliation Sweeper:* Full ACID serializability (`SELECT ... FOR UPDATE`), relational ledger/backup queries, standard WAL-G/pgBackRest backups -> R2, and clean zone HA.
8. **Recommended Design (`ADR-011`):** Run >=3 Go `pg-control-plane` instances across zones backed by a 3-node synchronous HA PostgreSQL metadata cluster (separate from customer Cells) continuously archived to its own isolated R2 backup bucket. Enforce transactional resource allocation locks (`FOR UPDATE SKIP LOCKED` on Cell capacity slots), state machine enums, and outbox records on every API mutation. Drive rollback, orphan directory cleanup, and delete-during-migration convergence via **`control-reconcile-queue`** + a 5-minute full-cluster Cell inventory reconciler that compares live `/vol/tenants/*` on every Cell against Control DB truth. Record every state mutation into an append-only `audit_events` log.
9. **Architecture Changes:** Build `cmd/pg-control-plane` stateless HA services + HA PG schema (`clusters`, `epochs`, `backups`, `usage_ledger`, `outbox_tasks`, `audit_events`) + inventory reconciler loop.
10. **Dependencies:** Provisioning transactional claim (`RISK-01`, `RISK-33`), Epoch/failover locking (`RISK-18`, `RISK-19`), Cloudflare Queue pull workers (`RISK-28`), DR playbooks (`RISK-41`).
11. **Trade-Offs:** Adds infrastructure footprint/cost of a dedicated 3-node HA Metadata PG cluster + Control API instances (~`$200–$400/mo` baseline fixed platform overhead amortized across all tenants in `Section 8`).
12. **Security Implications:** Full tamper-evident `audit_events` trail of every tenant create/delete/failover/credential rotation; metadata DB encrypted at rest and backed up independently to isolated R2 bucket (`no shared creds with customer data plane`).
13. **Failure Recovery Strategy:** Single Control API node crash shifts instantly across sibling API replicas cleanly; single Metadata PG zone loss auto-promotes standby seamlessly. Should total Control Plane outage occur transiently (`RISK-41`), Gateways serve already-active sessions via cached routes cleanly within lease bounds (`RISK-18`) until Control Plane HA recovers (pausing *new* failovers/provisions safely fail-closed rather than splitting brains!).
14. **Validation Method:** `EXP-A3` & `EXP-D3` (Kill Control API instances randomly during concurrent provision/migrate/delete storms; stop Control DB primary during active Gateway SQL traffic and verify clean HA promotion + zero metadata drift post-reconciler).
15. **Acceptance Criteria:** `100%` metadata-vs-Cell directory convergence after injected crashes once reconciler finishes `<60s`; `0` dropped API requests on single Control API kill; active established customer queries unaffected during brief Control DB failover.
16. **Remaining Uncertainty:** Real Control Plane HA PG deployment choice (self-managed Fly PG 17 HA with Patroni/repmgr vs external managed HA metadata PG) and failover blackout duration under cross-zone Fly latency (`UQR-12`).

### RISK-33: Database Provisioning
1. **Risk ID & Title:** `RISK-33` — Database Provisioning
2. **Severity:** `P2`
3. **Root Cause:** Network timeouts during `POST /databases`, Cell disk-full errors mid-claim, `pg-cell-agent` disconnects, or skipping live readiness checks (`SELECT 1` + `SCRAM`) create duplicate databases, leaked half-configured directories, or "active" endpoints that fail authentication immediately on first connection.
4. **Failure Scenario:** Terraform/CLI sends `POST /databases`, timeout triggers retry 3s later without `Idempotency-Key` -> system bills and spawns 2 clusters; or `pg-cell-agent` disconnects mid-setup leaving an initialized `PGDATA` missing `app_owner` role or `SCRAM` password -> API returns `201 Created`, user connects and hits `FATAL: role "app_owner" does not exist`.
5. **Technical Explanation:** Reliable cloud resource provisioning follows an idempotent state-machine workflow: clients pass an `Idempotency-Key` header hashed alongside request parameters `(org_id, region, name, plan)` inside a unique DB index; duplicate retries return the original canonical record (`PROVISIONING` or `ACTIVE`) rather than creating a second tenant. All internal steps execute inside a sagalike state transition (`RESERVE_SLOT -> CLAIM_POOL_CLUSTER -> APPLY_ROLE_SECRET -> READINESS_CHECK -> ACTIVE`), compensating any failure automatically via rollback RPC + `control-reconcile-queue` purge.
6. **Industry-Standard Solutions:**
   - Stripe-style transactional `Idempotency-Key` table + unique constraints (`UNIQUE (tenant_id)`, `UNIQUE (system_identifier)`).
   - Readiness verification probe (`SCRAM-SHA-256` handshake + `SELECT 1` + version/extension check) before exposing `ACTIVE` status.
7. **Solution Comparison:**
   - *Option A — Fire-and-forget async create without idempotency or readiness probe:* Fast 202 response, **breaks client tooling expecting ready DBs or leaks ghost DBs on retries**—**rejected**.
   - *Option B — Recommended (`ADR-001`): Idempotent Transactional Provisioning + Two-Phase Claim + CSPRNG Secret Bootstrap + Verified `SELECT 1` Readiness Gate:* Guarantees exact-once provisioning, zero orphan leaks on failure, and 100% verified ready endpoints.
8. **Recommended Design (`ADR-001`):** Enforce: (1) `Idempotency-Key` support (mandatory or auto-scoped per request hash) persisted in Control DB `idempotency_records` (returning identical response on duplicate calls, returning `409 Conflict` on mismatched body). (2) Control DB constraints `UNIQUE (tenant_id)` and `UNIQUE (system_identifier)`. (3) On Cell claim: pop pool dir (`RISK-01`), inject CSPRNG 256-bit `SCRAM-SHA-256` role password cleanly without CLI/env exposure (`RISK-22`), create initial DB/allowlist config, verify live socket login (`SCRAM` + `SELECT 1`), register Gateway route `epoch = 1`, and mark `ACTIVE`. (4) Any disk-full, `os.Rename`, or agent-disconnect error rolls back capacity counters immediately and pushes cleanup to `control-reconcile-queue`.
9. **Architecture Changes:** Add `Idempotency-Key` middleware & `idempotency_records` table in `pg-control-plane`; add rollback RPC and `SCRAM` + `SELECT 1` readiness probe to `pg-cell-agent` claim flow (`Flow 1`).
10. **Dependencies:** Pre-warmed `initdb` pool (`RISK-01`), Control Plane HA DB (`RISK-32`), secret security (`RISK-22`), disk headroom admission (`RISK-17`).
11. **Trade-Offs:** Adding `SELECT 1` + `SCRAM` readiness check prior to returning `ACTIVE` adds ~30–100ms end-to-end provisioning latency (`Flow 1`) while guaranteeing zero "broken on first login" states.
12. **Security Implications:** Passwords generated strictly via `crypto/rand` (>=256-bit entropy) returned once at creation (Control DB stores only wrapped/hashed `SCRAM` verifier + encrypted secret only if explicitly dashboard-viewable per security tier, never logged in plaintext).
13. **Failure Recovery Strategy:** If agent crashes/disconnects mid-claim (`CLAIMING` state timed out past 15s), Control Plane marks attempt `FAILED`, releases slot reservation, and schedules `control-reconcile-queue` to purge any lingering `/vol/tenants/claiming/{tenant_id}` once agent reconnects; client retry safely gets clean state or new idempotent run.
14. **Validation Method:** `EXP-A2` & `EXP-A3` (Fire duplicate `POST /databases` storms with identical `Idempotency-Key`, disconnect agent mid-claim, fill target Cell disk during claim).
15. **Acceptance Criteria:** `100%` identical responses on retried `Idempotency-Key` calls (`1` cluster created); `0` broken DBs failing first login; `0` orphan directories remaining post-reconciliation across injected agent/disk faults.
16. **Remaining Uncertainty:** Steady-state p50/p99 end-to-end provisioning latency when the ready pool runs empty during a 1,000-DB simultaneous burst forcing on-demand `initdb` fallback (`EXP-A2`, `UQR-02`).

## P2 — Performance & Scalability Risks

### RISK-35: Gateway Bottlenecks
1. **Risk ID & Title:** `RISK-35` — Gateway Bottlenecks
2. **Severity:** `P2`
3. **Root Cause:** Buffering entire `pgproto3.DataRow` result sets or `COPY OUT`/`COPY IN` frames in Go heap per connection, spawning unbounded per-frame goroutines, or allocating fresh slice copies across 10,000 concurrent TLS sockets triggers Go GC pauses, excessive RSS growth, and tail-latency spikes across all tenants sharing a Gateway VM.
4. **Failure Scenario:** Fifty clients run `COPY table TO STDOUT` exporting 500 MB each while reading over slow residential links (`1 Mbps`), simultaneously with 8,000 idle TLS connections. If Gateway buffers `pgproto3` messages into unbounded Go channels or parses full `DataRow` columns into heap structs during pass-through, Gateway RSS explodes past 4 GB and OOM-crashes disconnecting all 8,050 users simultaneously.
5. **Technical Explanation:** In Go, high-throughput wire proxies achieve `<16 KB` per-connection RAM overhead only by avoiding per-message Go struct decoding (`pgproto3.Backend.Receive` struct allocations) on pure data-streaming loops and instead parsing only the lightweight 5-byte PostgreSQL header (`type byte + int32 length`) directly over pooled fixed buffers (`sync.Pool`), streaming payload bytes directly via bounded `io.CopyN` + `SetWriteDeadline` backpressure directly to/from TCP sockets! When a slow reader stalls reading `DataRow`/`COPY OUT`, socket TCP window closes -> `SetWriteDeadline` triggers backpressure back to PostgreSQL (`pg` stalls waiting to write cleanly instead of Gateway buffering 500 MB in Go heap!), or cleanly disconnects abusive slowloris sinks past `30s`.
6. **Industry-Standard Solutions:**
   - Streaming 5-byte frame router (`type + len`) using `sync.Pool` slab buffers, decoding full SQL payloads *only* when required for authentication/Extended Query parsing/metering headers (`CommandComplete` `'C'`, `ErrorResponse` `'E'`).
   - Bounded write deadlines (`SetWriteDeadline`), horizontal Fly Anycast scaling (`3+` Gateway Machines/region).
7. **Solution Comparison:**
   - *Option A — Full `pgproto3.Decode()` per `DataRow` on every proxied packet:* Clean Go types, **terrible allocation/GC pressure** on multi-million-row analytical queries (`10x` CPU/heap overhead)—**rejected**.
   - *Option B — Recommended (`ADR-009`): Zero-Allocation 5-Byte Frame Header Scanner + `sync.Pool` Streaming Pipe + Bounded `SetWriteDeadline`:* Inspects `type` (`'C'`, `'E'`, `'Q'`, `'P'`, `'X'`, `'d'`) cleanly for RU metering & routing state while copying `'D'` (`DataRow`) & `'d'` (`CopyData`) payloads straight across recycled pooled buffers with hard backpressure.
8. **Recommended Design (`ADR-009`):** Implement `internal/wire` as a lightweight 5-byte PG wire scanner + `sync.Pool` (32 KB slabs) streaming pump: pass `DataRow`/`CopyData` directly between client TLS socket and `6PN` mTLS socket without decoding columns; parse full messages strictly for `Startup`, `SCRAM`, `'C'`, `'E'`, and Stage-3 Extended Query headers (`'P'`/`'B'`/`'D'`/`'E'`/`'S'`). Enforce `30s` `SetWriteDeadline` backpressure, limit idle goroutines strictly to 2 lightweight reader/writer routines (or `netpoll`/epoll batching if `>10k` conns per Gateway VM), benchmark `1k -> 10k` TLS connections + `100 MB` `COPY` + pipeline throughput via `pprof` in Stage 1–2, and auto-scale horizontally across multiple Gateway VMs behind Fly Anycast.
9. **Architecture Changes:** Build zero-alloc streaming frame proxy in `internal/wire` (`cmd/pg-gateway`) + Go `pprof` / benchmark suite (`tests/benchmarks/gateway`).
10. **Dependencies:** Gateway security bounds (`RISK-23`), connection pooling queues (`RISK-12`), RU frame observation (`RISK-25`), `6PN` network (`RISK-30`).
11. **Trade-Offs:** Strict `SetWriteDeadline(30s)` intentionally kills clients that stop draining socket buffers for >30s while streaming huge `COPY OUT` results, protecting global Gateway stability at the expense of stalling pathological slow readers.
12. **Security Implications:** Bounds Gateway RAM strictly proportional to active stream buffers rather than unthrottled client payload sizes, neutralizing heap-exhaustion DoS vectors.
13. **Failure Recovery Strategy:** Multi-instance Gateway deployment via Fly Anycast (`2+` Gateways per region) absorbs single-Gateway crash/deploy seamlessly for new/reconnecting sessions; slow-client disconnects emit structured `08006` telemetry cleanly.
14. **Validation Method:** `EXP-E2` & `EXP-E3` (`10,000` concurrent TLS connections + simultaneous `100 MB` slow-reader `COPY OUT` + `pgx` pipeline throughput benchmark with Go `pprof` heap & goroutine profiling).
15. **Acceptance Criteria:** `<20 KB` average Go heap/stack footprint per idle TLS connection at `10,000` concurrent clients; `0` OOMs and `<50 MB` heap growth under `50` simultaneous throttled slow-reader `100 MB` `COPY OUT` streams.
16. **Remaining Uncertainty:** Real TLS handshake CPU saturation point and epoll/goroutine scheduling overhead on `performance-2x` vs `performance-4x` Fly Gateway VMs (`UQR-09`).

### RISK-36: Database Wake-Up Bottlenecks
1. **Risk ID & Title:** `RISK-36` — Database Wake-Up Bottlenecks
2. **Severity:** `P2`
3. **Root Cause:** Concurrent serverless traffic landing simultaneously on a stopped tenant creates wake-up thundering herds (`500` redundant spawn attempts); meanwhile, wake latency varies dramatically across clean shutdown (`pg_ctl stop`), post-crash dirty WAL replay, huge catalogs (`1,000+` tables), extensions (`pgvector`), and cold R2 restoration—making unbenchmarked `35ms` / `80ms` guarantees dangerously false.
4. **Failure Scenario:** One popular serverless API endpoint scales from 0 to 500 Lambda workers simultaneously targeting a stopped database. Without request coalescing (`singleflight`) and Cell boot semaphores, all 500 wake calls race or spawn duplicate recovery probes, or 100 stopped tenants on one Cell wake concurrently saturating NVMe random IOPS for 30+ seconds causing global Gateway timeouts.
5. **Technical Explanation:** Database wake-up comprises distinct physical phases: (1) Gateway SNI/auth/route check (`~1–2ms`); (2) Gateway-to-Cell `Wake(tenant_id)` RPC over `6PN` (`~1–3ms`); (3) `pg-cell-agent` `flock`, namespace setup (`~2–4ms`), and `postgres` binary initialization + `shared_buffers` mmap + crash recovery (or R2 restore if evicted); (4) local PgBouncer/Socket readiness (`SELECT 1`); and (5) **first query execution** including cold OS page-cache/relcache warming. Claiming a flat "35ms wake-up" or "80ms restore" ignores dirty recovery replay, relcache loading across large schemas, and NVMe I/O contention across co-waking neighbors.
6. **Industry-Standard Solutions:**
   - **Coalesced Single-Flight Wake Engine (`singleflight.Group`)** per `tenant_id` in both `pg-gateway` and `pg-cell-agent`.
   - **Bounded Wait Queue + Cell Concurrent Boot Semaphore** (`max_concurrent_starts = 5` per Cell VM) preventing NVMe disk thrashing during regional wake storms.
   - **Dedicated Warm/Always-On Opt-Out** (`idle_timeout = 0`) for latency-sensitive production tiers (note: scale-to-zero itself stays disabled in Stages 1–2 until Stage 3 validates Group B!).
7. **Solution Comparison:**
   - *Option A — Naive un-throttled parallel `postgres` fork per wake request:* Triggers NVMe I/O storm and CPU contention across Cell—**rejected**.
   - *Option B — Recommended (`ADR-007`, `ADR-008`): `singleflight` Coalescing + Bounded Wait Queue (`200` waiters/tenant) + Cell Boot Concurrency Semaphore (`max 5`) + Honest Tiered Benchmarks:* Collapses 1,000 concurrent hits into 1 clean boot, shields disk IOPS cleanly, and reports true measured warm/crash/cold p50/p95/p99 separately.
8. **Recommended Design (`ADR-007`, `ADR-008`):** Strictly prohibit hardcoded `35ms`/`80ms` latency promises. When scale-to-zero activates in Stage 3: (1) Coalesce concurrent requests per `tenant_id` inside `pg-gateway` and `pg-cell-agent` using `singleflight` + bounded hold queue (`max 200` queued clients; excess fail cleanly with `53300` + `Retry-After`). (2) Gate concurrent `postgres` boots inside each Cell via a `max_concurrent_starts = 5` semaphore preserving sibling NVMe `fsync` latency. (3) Benchmark Group B (`EXP-B1..B5`) measuring **Connection Establish p50/p95/p99** separately from **First-Query Completion p50/p95/p99** across 4 scenarios: clean warm local sleep, dirty crash WAL recovery, large catalog (1,000 tables + `pgvector`), and cold R2 Deep Freeze restore. (4) Offer configurable `idle_timeout = 0` (always-warm) on latency-critical paid databases.
9. **Architecture Changes:** Add `singleflight` + semaphore wake orchestrator in `pg-gateway` and `internal/cell/supervisor`; implement Benchmark Group B harness separating connect vs first-query percentiles.
10. **Dependencies:** Process lock & subreaper lifecycle (`RISK-06`), cooperative drain (`RISK-07`), connection pool caps (`RISK-12`), UX error clarity (`RISK-34`).
11. **Trade-Offs:** Capping concurrent Cell startups (`5` at a time) means if all 100 sleeping tenants wake in the *same second*, the tail batch waits serially behind earlier boots (~0.5–3s queued wait), intentionally protecting live active neighbors from disk stall.
12. **Security Implications:** Wait-queue bounds (`200` per tenant) block wake-storm memory exhaustion DoS targeting sleeping tenants directly from unauthenticated/abused endpoints (`pre-auth wake happens only after valid SNI/tenant existence check, or even stronger: authenticate SCRAM against Control DB verifier BEFORE dispatching Wake!`).
13. **Failure Recovery Strategy:** If a tenant fails startup (corrupt WAL or timeout past 30s), wake caller fails deterministically once with `57P03`, wakes wait queue cleanly with structured error (avoiding hanging all 200 clients until timeout), and triggers automatic PITR/failover diagnostics (`RISK-19`). Note: validating SCRAM credentials against Gateway/Control DB *before* waking a sleeping tenant stops unauthenticated scanners from waking sleeping databases (`Security Bonus` documented in `Section 4`!).
14. **Validation Method:** `EXP-B1`, `EXP-B4`, `EXP-B5` (Benchmark 100, 500, and 1,000 simultaneous wake-up connections across warm, post-crash, 1k-table, and cold-R2 DBs; record connect & first-query p50/p95/p99 separately).
15. **Acceptance Criteria:** Exactly `1` process boot spawned per 1,000 concurrent wake requests (`singleflight` verified); Gateway memory flat under wake storms; empirical p50/p95/p99 tables published prior to Stage 3 production launch.
16. **Remaining Uncertainty:** Real Fly NVMe warm startup time of PG17 inside `CLONE_NEWNS` + `pivot_root` (`200ms` vs `600ms` vs `1.5s` under 1k-table catalogs) and post-crash recovery duration (`UQR-08`).

### RISK-37: Storage Performance
1. **Risk ID & Title:** `RISK-37` — Storage Performance
2. **Severity:** `P2`
3. **Root Cause:** Packing dozens of active PostgreSQL clusters onto one Fly NVMe `ext4` volume funnels concurrent `WAL` `fsync`s, dirty buffer `CHECKPOINT` bursts, random index reads, `pg_basebackup` sequential scans, and bulk `CREATE INDEX` writes through a single host NVMe device queue—plus, had XFS CoW reflinks been retained, CoW fragmentation/amplification would degrade random writes further.
4. **Failure Scenario:** Four neighbors trigger `CREATE INDEX CONCURRENTLY` and bulk `COPY IN` simultaneously while `pg_basebackup` reads a 5 GB tenant on Cell #1. Shared NVMe write queue depth spikes, jumping WAL `fsync` p99 latency from `0.5ms` to `85ms`, stalling OLTP `COMMIT`s across all 80 peaceful neighboring tenants.
5. **Technical Explanation:** PostgreSQL commit latency correlates directly with sequential WAL `write() + fdatasync()` latency (`wal_sync_method = fdatasync`). On Linux `ext4` (`data=ordered` default), concurrent heavy `fsync` calls across one journal (`jbd2`) can exhibit lock/metadata serialization spikes during heavy file creation (`CREATE TABLE`/`pg_wal` segment allocation) or aggressive checkpoint flushes (`checkpoint_completion_target` too low). Applying `cgroups v2` `io.max` (capping per-tenant NVMe BPS and IOPS ceilings on shared tiers), smoothing checkpoints (`checkpoint_completion_target = 0.9`, `checkpoint_timeout = '15min'`), compressing WAL (`wal_compression = zstd`), throttling `pg_basebackup --max-rate`, and promoting I/O-heavy tenants cleanly to Dedicated Cells preserves shared NVMe tail latency.
6. **Industry-Standard Solutions:**
   - Kernel `cgroups v2` `io.max` (BFQ / mq-deadline / direct NVMe IOPS+BPS throttling).
   - Smooth checkpoint pacing + ZSTD WAL compression + throttled backup I/O (`--max-rate`).
   - Hardware `fio` & `pg_test_fsync` profiling prior to committing multi-tenant NVMe density targets.
7. **Solution Comparison:**
   - *Option A — Uncapped shared `ext4` NVMe access across all tenants:* Maximum burst throughput for 1 tenant, **causes severe `fsync` tail spikes (`100ms+`) for every sibling**—**rejected**.
   - *Option B — Recommended (`ADR-008`, `ADR-010`): `cgroups v2` `io.max` Per-Tenant IOPS/BPS Caps + Tuned PG Checkpointing (`0.9`) + Backup `--max-rate` + Empirical Stage 0 `fio` Profiling:* Protects neighbor `fsync` p99 deterministically and moves genuine IOPS-hungry apps to Dedicated VM Cells.
8. **Recommended Design (`ADR-008`, `ADR-010`):** (1) Execute Stage 0.1 empirical profiling on real Fly Volumes (`pg_test_fsync`, `fio` mixed random RW + `fsync` queue tests) to establish genuine host NVMe IOPS/bandwidth knee curves. (2) Configure PG17 shared defaults: `checkpoint_completion_target = 0.9`, `checkpoint_timeout = '15min'`, `wal_compression = zstd` (reduces WAL write volume significantly at low CPU cost), `bgwriter_lru_maxpages = 200`. (3) Throttle background `pg_basebackup`/`pg_combinebackup` with `--max-rate` / `cgroups v2` `io.max` inside an explicit maintenance cgroup. (4) Cap per-tenant `cgroups v2` `io.max` (e.g., `riops`/`wiops` & `rbps`/`wbps` calibrated against Stage 0 NVMe ceiling; fallback monitoring via 1s `/proc/<pid>/io` poller triggers read/write alert & promotion if kernel omits `io` controller). (5) Automatically promote sustained IOPS-bound tenants (`RISK-38`).
9. **Architecture Changes:** Tune shared `postgresql.conf` generator; configure `io.max` rules inside `internal/cell/isolation`; place backup/restore jobs inside bounded maintenance `cgroup`; add `EXP-D4`/`EXP-C4` storage benchmark suite.
10. **Dependencies:** Stage 0 Fly NVMe & `envprobe` check (`RISK-13`), disk quotas (`RISK-17`), Cell capacity density (`RISK-31`), heavy-tenant promotion (`RISK-38`).
11. **Trade-Offs:** Per-tenant `io.max` and backup `--max-rate` cap peak single-tenant bulk index/restore throughput intentionally on shared Cells in order to protect neighbor `COMMIT` `fsync` p99.
12. **Security Implications:** Mitigates NVMe queue-flooding I/O DoS attacks across multi-tenant Cells.
13. **Failure Recovery Strategy:** If Prometheus detects Cell `fsync` p99 exceeding threshold (>10ms sustained) despite `io.max`, telemetry identifies the highest `io.stat` tenant immediately and queues live migration (`RISK-20`) off that Cell (`RISK-38`).
14. **Validation Method:** `EXP-C4` & `EXP-D4` (Multi-tenant `pgbench` TPC-B on Tenant B while Tenant A executes parallel `CREATE INDEX` + `COPY` and backup worker runs `pg_basebackup`, measuring `pg_test_fsync` and OLTP p50/p95/p99).
15. **Acceptance Criteria:** Documented empirical Stage 0 `fio`/`pg_test_fsync` curve on Fly hardware; Tenant B OLTP p99 latency degrades `<25%` while Tenant A runs heavy `CREATE INDEX` + backup runs concurrently.
16. **Remaining Uncertainty:** Whether `cgroups v2` `io.max` throttling effectively throttles *buffered* page-cache dirty writes flushed later by kernel `kworker`/`jbd2` vs direct WAL `fsync` on Fly's exact virtual NVMe driver (`EXP-C4`, `UQR-01`, `UQR-03`).

### RISK-38: Large Tenant Handling
1. **Risk ID & Title:** `RISK-38` — Large Tenant Handling
2. **Severity:** `P2`
3. **Root Cause:** Allowing tenants to grow organically past 5–10 GB or run heavy sustained analytical scans/huge pools inside dense multi-tenant shared Cells destroys shared Linux Page Cache hit ratios, monopolizes shared NVMe capacity/IOPS, slows cold restore RTO linearly, and turns noisy neighbors into constant incident generators.
4. **Failure Scenario:** One "free/starter" hobby app goes viral and scales to a 35 GB database executing analytical group-bys at 100% CPU for 6 hours. It consumes 45% of an 80 GB shared Cell volume and flushes the 8 GB VM Page Cache constantly, degrading 79 neighboring tenants while impossible to accommodate alongside shared-Cell pricing.
5. **Technical Explanation:** Multi-tenant serverless economics depend on statistical multiplexing among small/medium spiky databases (`<=5 GB`, `<1 vCPU` avg). Above that inflection point, dedicated single-tenant VMs (`Fly Dedicated Cell`: tailored `performance-2x/4x/8x`, dedicated volume sized `1.5x–2x` DB, larger `shared_buffers = 25%` RAM, enabled parallel query workers!) are strictly superior both technically (zero noisy neighbors, hardware KVM boundary, fast `shared_buffers`) and economically (clean dedicated SKU margin). Detecting crossing early via continuous telemetry and smoothly promoting via Physical Streaming Live Migration (`RISK-20`) avoids emergency downtime.
6. **Industry-Standard Solutions:**
   - Hard Tier Ceilings on shared infra + Automated / Prompted Graduation to Dedicated Compute Cells (`Supabase Compute Add-ons`, `RDS` instance scaling).
7. **Solution Comparison:**
   - *Option A — Allow multi-10 GB DBs to stay permanently on dense shared Cells:* Ruins neighbor performance and makes shared volume capacity planning chaotic—**rejected**.
   - *Option B — Recommended (`ADR-008`, `ADR-011`): Continuous Workload Classifier + Hard Shared Ceilings (`5 GB` disk / `512 MB` RAM / sustained `CPU/IOPS`) + Live Physical Promotion:* Enforces clear boundaries on shared tiers (`EDQUOT` / `io.max` guard) and graduates growing workloads cleanly via live migration (`RISK-20`) onto Dedicated Firecracker Cells.
8. **Recommended Design (`ADR-008`, `ADR-011`):** Enforce explicit shared-Cell tier thresholds: max **5 GB** physical `PGDATA+WAL`, max **512 MB** `cgroups v2` `memory.max`, max **1.0 vCPU** sustained average over 1h, max **15–25** backend connections. A Control Plane classifier evaluates 5-minute FinOps/cgroup telemetry (`RISK-26`, `RISK-39`): (a) For paid/auto-scale tiers crossing soft watermark (`4 GB` / sustained `>80%` tier CPU/IOPS for 1h), Control Plane provisions a Dedicated Fly Machine + tailored volume (`>=2x` current DB), enables `shared_buffers = 25% RAM` + parallel workers (`>0`), and executes live physical migration (`RISK-20`); (b) For Free/capped plans refusing upgrade at `5 GB`, `ext4 PRJQUOTA` (`RISK-17`) halts growth cleanly at 5 GB until user upgrades plan cleanly.
9. **Architecture Changes:** Build workload classifier job in `internal/control/scheduler` driving `RISK-20` auto-promotion; configure Dedicated Cell Fly app config template (`fly.dedicated.toml` supporting tuned `shared_buffers` & parallel query).
10. **Dependencies:** Physical storage accounting (`RISK-14`, `RISK-17`), Live physical migration (`RISK-20`), FinOps COGS classifier (`RISK-26`), Unit Economics model (`RISK-27`), Cell capacity caps (`RISK-31`).
11. **Trade-Offs:** Automated promotion transitions customer billing from low shared-tier pricing to Dedicated Compute SKUs—requiring transparent customer notifications / explicit plan opt-in (`auto_scale` vs hard-cap `read-only`) so users are never surprised by unexpected Dedicated bills.
12. **Security Implications:** Moving large/heavy tenants onto Dedicated Firecracker VMs grants full KVM hardware isolation (`ADR-005`) while immediately shrinking blast radius on shared Cells.
13. **Failure Recovery Strategy:** If target Dedicated Machine creation hits transient Fly capacity delay during auto-promotion, shared-Cell `cgroups v2` (`io.max`/`cpu.max`/`memory.max`) keep protecting neighboring tenants deterministically until migration slot opens.
14. **Validation Method:** `EXP-C3`, `EXP-C4` + Auto-Promotion End-to-End Drill (Grow a loaded `pgbench` tenant past `4 GB -> 5 GB` / sustained CPU trigger; verify automated classifier provisions Dedicated Cell, runs live `RISK-20` cutover with 0 lost commits, and reclaims shared Cell space cleanly).
15. **Acceptance Criteria:** `0` lost committed transactions during live promotion from shared to Dedicated Cell; shared Cell neighbor p99 latency returns to baseline `<10s` post-eviction; hard cap (`5 GB`) prevents un-upgraded Free tiers from exceeding shared disk share.
16. **Remaining Uncertainty:** Exact economic threshold (`5 GB` vs `10 GB`, sustained CPU %) minimizing total fleet cost across Dedicated Fly `performance-1x` (`$33/mo`) vs dense Shared `performance-4x` (`$132/mo`) packing (`Section 8`, `UQR-07`).

13. **Failure Recovery Strategy:** External Dead-Man's-Switch watchdog pages immediately if internal Alertmanager/Prometheus pipeline stops firing heartbeat signals for >3 minutes.
14. **Validation Method:** Synthetic Alert Fault Injection Suite (Stop R2 mock uploads, push test Cell disk to 85%/92%, pause standby, pause Queue consumer, simulate crash loop; verify exact warn/page triggers within SLA).
15. **Acceptance Criteria:** `100%` (15/15) of required alert rules fire reliably within `<2m` of fault threshold in staging chaos drill and clear cleanly when fault resolves; `0` PII/secrets leaked in alert webhook JSON.
16. **Remaining Uncertainty:** Exact false-positive alert tuning (`for:` durations & WAL spike baselines) once real multi-tenant production traffic mixes organic bulk ETL uploads (`UQR-11`).

### RISK-41: Disaster Recovery
1. **Risk ID & Title:** `RISK-41` — Disaster Recovery
2. **Severity:** `P2`
3. **Root Cause:** Unverified recovery scripts and undocumented failure playbooks fail catastrophically during correlated cloud incidents (whole-region outages, accidental tenant deletion, R2 outages, Control Plane failure, or corrupted backups).
4. **Failure Scenario:** A Fly region outage (`iad`) takes down Primary and Standby Cells simultaneously, or an automated cleanup bug deletes an active tenant's backups cleanly, or Control Plane Metadata DB fails over unexpectedly—and engineers scramble with ad-hoc manual CLIs making destructive irreversible mistakes under stress.
5. **Technical Explanation:** Disaster Recovery reliability depends equally on **pre-engineered data boundaries** (R2 cross-region/multi-zone redundancy, 7-day soft-delete prior to DEK crypto-shredding, immutable verified base/incremental/WAL chains, WAL local spooling reserves during R2 outages, independent Control Plane HA backups) and **quarterly tested GameDay automation** across every single failure mode documented in [issue.md #41](file:///workspaces/cloud/experimental-db/issue.md#L763-L777). Note carefully: Cloudflare R2 stores objects durably within a region/bucket (`Automatic` vs `Jurisdictional` placement), so surviving a *total single-region compute destruction* relies on restoring R2 backups cleanly into a healthy secondary Fly region (`iad` -> `ewr` / `ord`), whereas true R2 outage resilience relies on local Cell WAL retention headroom + physical standbys until R2 recovers (`100%` honest RTO boundaries documented in `Section 9`).
6. **Industry-Standard Solutions:**
   - Version-controlled automated DR runbooks + quarterly chaos GameDay testing covering all 12 scenarios.
   - 7-day soft-delete crypto-shred guard (`RISK-24`), independent Control Plane R2 backup stream, and cross-region evacuation automation.
7. **Solution Comparison:**
   - *Option A — Ad-hoc manual SQL/Fly CLI recovery steps maintained only in wikis:* Fails slowly and dangerously during 3 AM outages—**rejected**.
   - *Option B — Recommended (`ADR-002`, `ADR-011`): Automated Tested DR Playbooks + Soft-Delete Guard + Quarterly Chaos GameDays:* Exercises every one of the 12 failure modes explicitly on isolated staging environments prior to GA and quarterly thereafter.
8. **Recommended Design (`ADR-002`, `ADR-011`):** Document, script, and drill all **12 DR playbooks** (`Section 9.E`):
   1. *Complete Cell Loss:* Auto failover via `RISK-19` (`Pro` -> unique-zone Standby; `Standard` -> healthy Cell R2 restore).
   2. *Complete Region Loss:* Restore R2 verified backups (`base+incr+wal`) into healthy backup Fly region (`ewr`/`ord`) + update Edge Anycast routing (or Geo-Pro multi-region warm standby if purchased).
   3. *R2 Temporary Outage:* Cells retain WAL locally inside bounded reserve (`max_wal_size`/staging headroom) + Standby holds replication slot up to `max_slot_wal_keep_size`; alert fires past 50% WAL buffer; flushes backlog seamlessly on R2 recovery.
   4. *Standby / Replication Link Failure (Pro):* Alert fires immediately (`RISK-40`); commits block cleanly preserving `RPO=0` unless customer/policy explicitly enables bounded degraded async mode (`max_standby_wait` failover rule).
   5. *Control Plane DB Failure:* 3-node multi-zone HA PG auto-failover (`<15s`), backed by continuous R2 PITR; Gateways continue routing live pools transiently; full total loss recovers from Control DB R2 backup + Cell `/vol` inventory reconciliation.
   6. *Accidental Tenant Deletion:* 7-day `SOFT_DELETED` quarantine keeps encrypted R2 chain + intact wrapped DEK -> immediate PITR clone recovery (`<RTO`); hard crypto-shredding fires only past day 7.
   7. *Corrupted Snapshot / `backup_manifest`:* Caught before publish by `pg_verifybackup`; if existing R2 object corrupts on read, recovery automatically falls back to `(prior verified base + contiguous WAL chain)`.
   8. *Corrupted WAL Segment:* Fail closed cleanly—do NOT skip WAL gaps silently (prevents logical corruption); restore cleanly up to exact last contiguous valid LSN prior to damaged segment and notify tenant transparently.
   9. *Stale Replica Promotion:* Blocked by Control Plane serializable promotion lock + epoch check (`RISK-18`); returning stale primary enters `FENCED_QUARANTINE` cleanly.
   10. *Failed Live Migration:* Pre-cutover target failures abort seamlessly with source untouched (`RISK-20`); post-cutover edge failure recovers via new primary's Standby/R2.
   11. *Credential / KEK Compromise:* Bulk rotation API revokes tenant SCRAM secrets (`auth_epoch++` <2s), rotates Fly/R2 tokens, and triggers `KEK` re-wrapping across Control KMS (`RISK-22`, `RISK-24`).
   12. *Mass Tenant Outage (Correlated Multi-Cell Restart):* Priority-tiered recovery queue restores active paid/Pro tenants first while gating concurrent Cell boots (`max_concurrent_starts = 5`) and R2 download concurrency so shared networks/disks do not thrash into secondary collapse (`RISK-36`).
9. **Architecture Changes:** Implement `SOFT_DELETED` 7-day hold + emergency PITR undelete API, bulk credential/DEK rotation endpoints, prioritized recovery queues, and scripted DR drills in `pg-control-plane`.
10. **Dependencies:** R2 backup verification & PITR (`RISK-15`, `RISK-16`), Fencing & Failover (`RISK-18`, `RISK-19`), Control Plane HA (`RISK-32`), Monitoring & Alerts (`RISK-39`, `RISK-40`).
11. **Trade-Offs:** Retaining 7 days of soft-deleted R2 objects adds minor `$0.015/GB-mo` storage (~`$0.0035/GB` per 7d week) cleanly outweighed by preventing irreversible accidental-delete disasters; failing closed on corrupted WAL prioritizes honesty/data integrity over silent inconsistent skipping.
12. **Security Implications:** Revokes all client credentials and blocks login connections immediately upon `SOFT_DELETED` status (remaining data stays AES-256-GCM encrypted until day-7 crypto-shred); bulk rotation runbooks isolate leaked keys rapidly.
13. **Failure Recovery Strategy:** Self-referential DR guarantee: Control Plane backup bucket + KMS recovery seed keys live completely outside customer Cell infrastructure with documented multi-operator recovery quorum (`UQR-12`) so platform bootstrap never suffers circular dependency deadlock.
14. **Validation Method:** Pre-GA & Quarterly GameDay Chaos Suite (`EXP-D3`, `EXP-D5`, `EXP-D6`, executing live staging drills of region evacuation, simulated R2 503 outage, Control DB total loss restore, accidental delete recovery, and 100-tenant staggered mass restore).
15. **Acceptance Criteria:** `100%` (12/12) of DR playbooks executed successfully in isolated staging GameDays prior to GA with measured recovery timings matching published realistic RTO/RPO envelopes (`Section 9.E`).
16. **Remaining Uncertainty:** Real wall-clock mass-evacuation RTO when recovering 1,000+ tenants across regions simultaneously from R2 into fresh Fly Cells under live Cloudflare R2 & Fly network throughput (`UQR-03`, `UQR-11`).
